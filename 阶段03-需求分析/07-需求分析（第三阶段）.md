## 二、用户角色分析

### 2.1 角色定义与职责

本科阶段只设置一个"普通用户"角色（《02》§6.1）。不设置第二种业务角色，不设置组织机构与审批流程。普通用户的职责范围如下。

- 以自然语言提出财经信息问题，并查看系统给出的答案；
- 查看答案对应的来源与证据，包括新闻来源、公告来源与相关事件；
- 查看事件知识图谱，包括实体、事件以及实体之间的路径；
- 查看本会话此前的问答历史记录。

以下内容不属于普通用户的职责，归属后台：文本数据的导入、删除与更新；抽取规则与提示词的维护；图谱写入与向量索引更新；实验配置与评分。划分依据是《02》§6.1 与《04》§7.2 的既定口径——凡是会改变数据、图谱与索引内容，或会改变实验配置的动作，全部归后台。

角色数量的收敛是工作量控制的结果：本课题要验证的是知识图谱在财经问答检索中的作用，把开发精力集中在数据、图谱与检索方法上，而不是分散到用户体系上。

### 2.2 角色功能权限边界

普通用户的功能收敛为四项，按《02》§6.1 与《04》§7.2 的原文逐字表述为：**提问与查看答案、图谱查看、来源与证据查看、历史记录查看**。

**财经信息管理（文本数据的导入、删除、更新）不属于普通用户功能，列为后台系统能力，由作者通过脚本或受控后台入口执行，不对普通用户开放。**后台执行的完整内容包括数据导入、清洗、抽取、图谱更新与向量索引更新（《02》§6.1）。

四项功能与六个功能模块的对应关系是：提问与查看答案对应智能问答，图谱查看对应事件知识图谱，来源与证据查看对应证据追溯，历史记录查看对应历史问答。财经信息管理与财经事件抽取两个模块不向普通用户开放入口。

### 2.3 登录范围的条件性决策

第一版不启用注册与登录，用户直接进入系统即可使用提问与查看答案、图谱查看、来源与证据查看与历史记录功能。理由来自《02》§6.1：系统面向的是公开的财经文本信息，不涉及个人隐私数据与敏感业务数据；在本科毕业设计的演示与实验场景下，登录环节只会增加联调工作量，而对论文的核心问题（RQ1、RQ2、RQ3）没有贡献，因此第一版把用户管理从必需功能中移出。

需要明确的是：**不启用登录不等于匿名用户之间历史记录互相可见。**具体做法是——前端在首次访问时生成 session_id = UUID 并存于浏览器，question 表记录该 session_id，历史记录按 session_id 过滤，从而把不同匿名会话的问答历史隔离开（《02》§6.1）。

与这一决策配套的数据设计口径如下（《02》§6.1、§9.1）。

- user 表在数据模型中**始终建立**，第一版不启用登录业务、该表保持为空（不写入数据），以保证表数量恒为六张、schema 稳定；
- question 与 answer 表仍然保留 user_id 字段，登录未启用时该字段可以为空，这样后续启用登录不需要改动问答主流程的数据结构；
- question 表同时保留 session_id 字段（浏览器生成的 UUID），用于按会话隔离历史记录；
- 表数量恒为六张，不新增表，也不因"不启用登录"而少建表。

这是**条件性决策**，不是永久删除用户功能。若学校论文模板或毕业设计要求明确体现用户管理功能，则最小化开启"仅登录"：只提供登录入口与会话管理，不做注册、不做找回密码、不做多角色与细粒度权限。也就是说，一旦模板有要求，只需要在现有 user 表与后端接口上做最小改动即可满足，而不会影响其余功能与实验口径。

论文写作口径：需求分析一节给出普通用户角色与可选登录的设计考虑；系统实现与测试章节按最终是否启用登录如实说明，不虚构未实现的功能（《02》§6.1）。

## 三、功能需求

### 3.1 编写口径与本体口径

本节的编号规则是：按《02》§6.2 的功能顺序，一个模块一个编号，从 FR-01 起顺序编号，共六条。模块名称逐字照抄《02》§6.2：**财经信息管理、财经事件抽取、事件知识图谱、智能问答、证据追溯、历史问答**。每个模块统一按"需求编号、使用者、功能描述、输入、处理、输出、前置条件、后置条件、边界与不做的事、来源追溯"十个字段展开。

财经事件抽取与事件知识图谱两个模块的对象定义照抄《02》§9.2，不在本文件中改写、增减或合并。三类口径如下。

第一，实体类型为 6 类，标签与中文名称照抄《02》§9.2.1。

| 实体类型（标签） | 中文名称 | 说明 |
| --- | --- | --- |
| Company | 公司 | 上市公司及在财经信息中出现的其他企业主体，是图谱的核心节点，以 stock_code 作为稳定业务唯一标识 |
| Person | 人物 | 公司高管、监管机构人员等与事件相关的人物 |
| Industry | 行业 | 公司所属行业以及事件涉及的行业 |
| Institution | 机构 | 监管机构、交易所、中介机构等 |
| Event | 事件 | 财经事件，本课题的核心知识单元 |
| Policy | 政策 | 与公司或行业相关的政策文件及其主题 |

Product（产品）与 Location（地点）列为可扩展类型，不进入第一版的本体、抽取规则与评测范围（《02》§9.2.1）。

第二，核心事件类型固定为 8 种，逐条照抄《02》§9.2.2：业绩事件、监管事件、股权事件、投资并购事件、重大合同事件、产品事件、政策事件、重大经营事件。第一版固定为以上 8 种核心事件类型，作为抽取、标注与评测唯一的 schema，不再保留浮动的事件类型数量表述（《02》§9.2.2）。

第三，核心关系共 9 条，命名与属性照抄《02》§9.2.3。

```text
(Company)-[:BELONGS_TO {valid_from, valid_to, source_doc_id, source_chunk_id, confidence}]->(Industry)
(Company)-[:SUPPLIES {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:CUSTOMER_OF {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:COMPETES_WITH {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:HAS_EXECUTIVE {source_doc_id, source_chunk_id, confidence}]->(Person)
(Company | Person | Institution)-[:PARTICIPATES_IN {role, source_doc_id, source_chunk_id, confidence}]->(Event)   // role ∈ {主体, 合作方, 涉及方, 监管方, 受影响方}
(Event)-[:ISSUED_BY {source_doc_id, source_chunk_id, confidence}]->(Institution)                                 // 仅政策事件与监管事件
(Event)-[:RELATED_TO {source_doc_id, source_chunk_id, confidence}]->(Policy)
(Event)-[:EVIDENCED_BY]->(Document)                                                                              // 事件与其证据文档；本身即证据关系，不重复携带 source_doc_id
```

| 关系 | 方向 | 属性 | 说明 |
| --- | --- | --- | --- |
| BELONGS_TO | Company → Industry | valid_from、valid_to、source_doc_id、source_chunk_id、confidence | 公司所属行业，带有效时间区间，用于判断关系在查询时间点是否成立 |
| SUPPLIES | Company → Company | source_doc_id、source_chunk_id、confidence | 供应商关系，A 公司向 B 公司供货；方向按信息来源标注 |
| CUSTOMER_OF | Company → Company | source_doc_id、source_chunk_id、confidence | 客户关系，与供应商关系互为反向，按抽取结果确定方向 |
| COMPETES_WITH | Company → Company | source_doc_id、source_chunk_id、confidence | 竞争关系，第一版按抽取方向存一条 |
| HAS_EXECUTIVE | Company → Person | source_doc_id、source_chunk_id、confidence | 公司高管任职关系，必须带齐证据三项属性 |
| PARTICIPATES_IN | Company／Person／Institution → Event | role、source_doc_id、source_chunk_id、confidence | 公司、人物或机构参与事件，role ∈ {主体, 合作方, 涉及方, 监管方, 受影响方} |
| ISSUED_BY | Event → Institution | source_doc_id、source_chunk_id、confidence | 政策事件与监管事件中政策的发布机构或监管处罚的作出机构；其他事件类型不产生该关系 |
| RELATED_TO | Event → Policy | source_doc_id、source_chunk_id、confidence | 事件与相关政策之间的关联，必须带齐证据三项属性 |
| EVIDENCED_BY | Event → Document | 无 | 事件与其证据文档之间的关联，本身即证据关系，不再重复携带 source_doc_id；一个事件可以对应多份文档 |

关系的"命名与属性照抄"包含《02》§9.2.3 表下的两条补充口径，必须一并沿用，否则图谱写入数量与统计口径会不一致。**第一条是去重规则**：同一机构既是政策或监管事件的发布／作出方、又参与该事件时，只写 ISSUED_BY，不再重复写 PARTICIPATES_IN——同一条事实写两份会让路径计数、事件参与主体统计与事件去重逻辑出现重复计算。**第二条是"监管方"role 的适用范围**：该 role 仅用于"参与事件但不是发布／作出方"的机构，发布／作出方一律用 ISSUED_BY 表达。此外，COMPETES_WITH 通常为对称关系，第一版按抽取方向存一条；若行业归属来自外部行业分类而非文本抽取，该分类文件同样作为一份 Document 入库并由 BELONGS_TO 的 source_doc_id 指向它，保证证据链不断（以上均见《02》§9.2.3）。

证据属性口径统一为：**除 EVIDENCED_BY 外，其余 8 条核心语义关系统一携带 source_doc_id、source_chunk_id 与 confidence 三项证据属性**；三项证据属性是必需属性而不是可选补充，其中 BELONGS_TO 另带 valid_from、valid_to。这样处理之后，系统对任意一条事实都能回答"来自哪篇文档、哪个文本块、置信度多少"（《02》§9.2.3）。

事件节点的核心属性为六项，照抄《02》§9.2.4。

| 属性 | 含义 |
| --- | --- |
| event_id | 事件的唯一标识 |
| event_type | 事件类型，取值来自 8 种核心事件类型 |
| event_name | 事件名称 |
| event_time | 事件发生时间 |
| description | 事件描述，一句话说明事件经过 |
| confidence | 抽取置信度，0.0～1.0 之间的数值 |

除以上六项核心属性外，trigger（触发词）作为可选辅助字段保留，仅用于抽取调试与错误分析，不作为查询依据，也不进入检索与实验的判定逻辑（《02》§9.2.4）。participants 与 publish_time 不作为事件属性：参与主体由 PARTICIPATES_IN 关系（含 role 属性）与 ISSUED_BY 关系表达，publish_time 与 source、url 一起归属 document。

时间维度的归属层级照抄《02》§10.1：事件发生时间存放在 Event 节点的 event_time，文档发布时间存放在 Document 节点的 publish_time，关系有效时间以关系属性 valid_from、valid_to 表达，数据截止时间 data_cutoff_time 是数据集版本级属性，与 dataset_version 成对记录在数据集元信息中，不属于任何表（《02》§10.1、§10.3）。

### 3.2 财经信息管理（FR-01）

- 需求编号：FR-01
- 使用者：后台（作者通过脚本或受控后台入口执行），不对普通用户开放。
- 功能描述：由作者通过脚本或受控后台入口实现财经新闻、公告、政策等文本数据的导入、分类、清洗、查询、删除与更新。导入时记录标题、正文、发布时间、来源、URL、涉及公司与入库时间（ingest_time）等字段，保证后续向量化与事件抽取有统一的数据入口。文档新增、修改或删除后，触发一次重新处理流程，使图谱与向量索引与文本内容保持一致（《02》§6.2 功能 1）。
- 输入：待导入的财经新闻、公告、政策等文本数据及其元数据（标题、正文、发布时间、来源、URL、涉及公司）；对已入库文档的修改指令或删除指令；数据集版本级属性 dataset_version 与 data_cutoff_time 的配置值。
- 处理：
  1. 校验文件格式与必填字段，格式或字段不合法时不入库并给出明确提示；
  2. 文档写入 document 表，记录标题、正文、发布时间、来源、URL、涉及公司与 ingest_time；
  3. 按固定长度切分为文本块并写入 document_chunk 表；
  4. 文档新增、修改或删除后，触发一次重新处理流程；
  5. 重新处理过程中按增量方式更新向量索引，文档删除或切分规则调整时整体重建索引；
  6. 同步更新 Neo4j 中受影响的实体、事件与关系；
  7. 重新处理后运行一致性检查，核对抽取结果与图谱节点数量、文本块数与向量条数。
- 输出：可被向量化与事件抽取统一读取的文档数据与文本块数据；更新后的图谱与向量索引；一致性检查结果。
- 前置条件：数据来源为公开可访问的信息（上市公司公告、监管机构公开信息、政策文件与正规财经新闻），并遵循相应网站的访问规范、使用条款与学校毕业设计的相关要求（《04》§7.1、§8.2）；数据集版本级属性已确定；允许的文件格式清单与必填字段清单已确认（《02》§7 不预先限定录入格式，两份清单在实现阶段固定，并与论文第 6 章 6.1 测试环境与实验配置一同记录）。
- 后置条件：document 与 document_chunk 的内容与本次操作一致；图谱与向量索引完成一次重新处理，不残留失效数据；**已被历史回答引用的文档不执行物理删除、保持可回溯**；一致性检查结果可核对（《02》§7 数据一致性）。
- 边界与不做的事：本模块是后台系统能力，不对普通用户开放，不在普通用户用例中；不包含预测与投资决策类的任何处理；边界清单见 8.2 节（《02》§5.1、《04》§7.1）；不承诺 MySQL、Neo4j 与向量索引之间的实时同步，只承诺"变更后重新处理 ＋ 一致性检查"（《02》§7 数据一致性）。
- 来源追溯：《02》§6.2 功能 1；《02》§5.1；《02》§7 数据一致性；《02》§9.3；《02》§10.3；《04》§7.1、§7.2、§8.2。

### 3.3 财经事件抽取（FR-02）

- 需求编号：FR-02
- 使用者：后台（数据处理环节），不对普通用户开放。
- 功能描述：从文本中识别公司、人物、行业、机构、事件、政策六类实体以及时间、关系，并将抽取结果写入知识图谱；抽取结果保留证据来源，便于在问答环节回溯到原文；**除 EVIDENCED_BY 外，其余 8 条核心语义关系均携带 source_doc_id、source_chunk_id 与 confidence 证据属性**；抽取完成后进入实体消歧与事件去重环节（《02》§6.2 功能 2）。
- 输入：document 与 document_chunk 中的财经文本；《02》§9.2 定义的 6 类实体、8 种核心事件类型与 9 条核心关系作为唯一 schema；人工标注的抽取评测集 Dev 与 Test（《02》§12.3）。
- 处理：
  1. 实体识别：按 Company、Person、Industry、Institution、Event、Policy 六类标签输出实体与来源；
  2. 事件抽取：按 8 种核心事件类型输出事件节点，并填写 event_id、event_type、event_name、event_time、description、confidence 六项核心属性；
  3. 关系抽取：按 9 条核心关系输出关系及其方向，其中除 EVIDENCED_BY 外的 8 条携带 source_doc_id、source_chunk_id 与 confidence，BELONGS_TO 另带 valid_from、valid_to；
  4. 时间抽取：区分事件发生时间与文档发布时间，分别归入 Event 节点的 event_time 与 Document 节点的 publish_time；
  5. 证据挂载：事件与证据文档之间建立 EVIDENCED_BY 关系，一个事件可以挂多份文档；
  6. 实体消歧：公司实体以 stock_code 为锚完成对齐，先与别名表匹配，匹配成功则归并到对应的 stock_code 节点，匹配失败进入待消歧列表，人工确认后再写入图谱；
  7. 事件去重：按 event_type ＋ 参与主体 ＋ 时间窗口 ＋ 触发词相似度判定同一事件的多来源描述，四项条件同时满足时判定为同一事件并合并；合并后保留全部证据文档并通过 EVIDENCED_BY 全部挂在合并后的事件节点上，发布时间最早的一份作为主要来源展示，其余来源作为补充证据保留；合并动作记录在抽取日志中；
  8. 图谱写入：把实体、事件、关系与时间信息写入 Neo4j。
- 输出：实体、事件、关系与时间四类抽取结果；带证据属性的图谱写入内容；实体消歧结果与事件合并日志。
- 前置条件：document 与 document_chunk 已就绪；本体 schema 已冻结（6 类实体、8 种核心事件类型、9 条核心关系）；抽取规则与提示词版本已冻结，Test 集在规则冻结后一次性评测，不用于反复调参；Dev 与 Test 两个集合不重叠（《02》§12.3）。
- 后置条件：图谱中的实体、事件与关系均可回溯到具体文档与文本块；同一事件的多份来源挂在同一事件节点上；消歧与去重结果可核查；抽取质量可由实体、事件、关系、时间四类任务的 Precision、Recall 与 F1 说明。
- 边界与不做的事：不研究预测类与投资决策类内容，边界清单见 8.2 节（《02》§5.1、《04》§7.1）；Product（产品）与 Location（地点）不进入第一版本体、抽取规则与评测范围（《02》§9.2.1）；标注过程中发现的本体边界问题记录在标注说明中，不临时增加关系类型（《02》§12.3）；图谱关系只表示公开信息中出现的关联，不得表述为因果关系（《02》§5.3）。
- 来源追溯：《02》§6.2 功能 2；《02》§9.2.1～§9.2.5；《02》§10.1；《02》§12.3；《02》§5.3；《04》§7.1、§7.3。

### 3.4 事件知识图谱（FR-03）

- 需求编号：FR-03
- 使用者：普通用户执行查询与可视化；后台执行写入与维护。
- 功能描述：支持实体查询、事件查询、关系查询、时间查询、多跳路径查询与图谱可视化。用户既可以直接检索某个实体或某类事件，也可以查看实体之间的路径（《02》§6.2 功能 3）。
- 输入：用户选择的实体、事件类型、关系类型或时间区间；自然语言问题经问题分析后得到的实体与时间约束；抽取阶段写入的实体、事件、关系与时间数据。
- 处理：
  1. 解析查询条件，区分实体查询、事件查询、关系查询与时间查询；
  2. 在 Neo4j 中按条件检索节点与关系；
  3. 需要进行多跳查询时，沿 PARTICIPATES_IN、RELATED_TO、ISSUED_BY、EVIDENCED_BY 等关系扩展路径；
  4. 对带时间约束的查询按 Event 节点的 event_time 过滤；
  5. 同一事件存在多份来源时按 Document 节点的 publish_time 排序并去重；
  6. 输出节点、关系与路径的可视化数据，其中每条关系均回溯到 9 条核心关系之一，并按关系类型返回其证据属性：除 EVIDENCED_BY 外返回 source_doc_id、source_chunk_id 与 confidence；EVIDENCED_BY 本身即事件到文档的证据关系，其证据为该关系指向的 Document 节点，不返回这三项属性；
  7. 查询为空时返回明确提示。
- 输出：实体节点、事件节点与关系路径；图谱可视化所需的数据结构；除 EVIDENCED_BY 外的每条关系对应的来源文档与文本块编号、置信度（EVIDENCED_BY 本身即证据关系，其证据为该关系指向的 Document 节点）；查询为空时的明确提示。
- 前置条件：图谱已完成写入并通过一致性检查；本体 schema 未变更；查询条件非空。
- 后置条件：除 EVIDENCED_BY 外的每条展示关系都可回溯到文档与文本块（EVIDENCED_BY 本身即证据关系，其证据为该关系指向的 Document 节点）；路径深度与本次查询所设的检索深度一致；同一事件的多来源展示按发布时间排序。
- 边界与不做的事：不做预测类分析，不提供投资决策结论，边界清单见 8.2 节（《02》§5.1、《04》§7.1）；图谱中的关系只表示公开信息中出现的关联，不能表述为因果关系，也不能由两个公司之间存在供应链关系直接推导出其中一方必然受到影响（《02》§5.3、《04》§7.3）；问题的路径深度标签 gold_hop_depth（问题金标准属性）与消融实验 B／C 组的 1-hop／2-hop（实验自变量）不是同一概念，不得使用同一字段、同一术语或同一统计口径（《02》§12.2）。
- 来源追溯：《02》§6.2 功能 3；《02》§5.3；《02》§9.2.1～§9.2.5；《02》§10.1、§10.2；《02》§12.2；《04》§7.1、§7.3。

### 3.5 智能问答（FR-04）

- 需求编号：FR-04
- 使用者：普通用户。
- 功能描述：用户输入自然语言问题，例如"A 公司最近发生了哪些重大事件？"，系统依次完成问题分析、文本检索、图谱检索、时间过滤、证据排序与大模型生成，返回自然语言回答；问题中的"最近"按 event_time 判定（事件发生时间落在数据截止时间前 30 天以内），并以数据截止时间为基准解释（《02》§6.2 功能 4）。
- 输入：用户提交的自然语言问题；会话标识 session_id（第一版用于历史记录归属）；数据集版本级属性 dataset_version 与 data_cutoff_time。
- 处理：
  1. 问题分析：判定问题类型与是否需要图谱扩展，识别问题中的实体与时间约束；
  2. 文本检索：用问题与实体关键词在向量索引中检索候选文本块；
  3. 图谱检索：按需要执行 0 跳（只进行文本检索）、1 跳（文本检索 ＋ 一跳图谱关系）或 2 跳（文本检索 ＋ 两跳图谱关系）扩展；
  4. 时间过滤：带时间约束的问题按 event_time 过滤事件节点，并沿关系做扩展；
  5. 证据排序：把向量检索结果与图谱检索结果合并排序；上下文超出预算时按固定裁剪规则裁剪，裁剪发生在证据排序之前，裁剪顺序为**先裁剪与问题实体无关的远端图谱路径，再依据向量检索的原始排名从后往前裁剪文本块**，且不使用证据排序的结果，以保证消融 D 组与 E 组得到完全相同的证据集合（《02》§12.4、§12.6）；候选证据不足 K 的题目在测试集构建阶段调整，不进入正式实验；**该约束只适用于测试集构建阶段**：题目一旦入库，不得因该题实验时的实际候选数少于 K 而将其排除，空缺位置记为未命中并按原指标定义计算（《02》§12.7）；
  6. 大模型生成：基于证据生成自然语言回答，模型不得使用数据截止时间之后的信息，也不得在证据不足时用训练语料中的时间信息补全答案；
  7. 落库：question 记录问题与提问时间，answer 记录回答，answer_evidence 记录答案引用的证据。
- 输出：自然语言回答；本次问题所用相对时间的判定区间与数据截止时间说明；供证据追溯使用的证据集合；使用了图谱扩展时的图谱路径。
- 前置条件：文本已入库并完成向量索引构建与图谱写入；Embedding 模型与大语言模型接口可调用；问题非空且长度在接口限制之内；实验期间使用同一套固定的模型、参数与提示词配置（《02》§12.4）。
- 后置条件：question、answer、answer_evidence 三条记录可关联还原本次问答；回答页面固定显示"数据截至：YYYY-MM-DD"；答案中注明所用判定区间（《02》§13）。
- 边界与不做的事：不提供预测与投资决策类回答，边界清单见 8.2 节（《02》§5.1、《04》§7.1）；定量实验只使用可核验的事实型问题，开放式分析问题只用于 Demo 展示与案例分析、最多保留 1～2 例、必须在页面与答案中同屏标注"模型分析（非公开事实）"、不作为核心准确率依据、不参与图谱增强效果的判定、不计入任何指标（《02》§12.9）；"最新／最近／近期"一律以 event_time 判定，不以 publish_time 判定，也不以系统运行当天为基准（《02》§10.3）。
- 来源追溯：《02》§6.2 功能 4；《02》§10.2、§10.3；《02》§11.3；《02》§12.1、§12.4、§12.7、§12.9；《02》§13；《04》§7.3。

### 3.6 证据追溯（FR-05）

- 需求编号：FR-05
- 使用者：普通用户。
- 功能描述：答案下方展示回答来源、新闻来源、公告来源、相关事件，以及**使用了图谱扩展时**的图谱路径；**若本次回答未使用图谱扩展，则显式标注"本次回答未使用图谱扩展"**。用户可以从答案直接定位到具体文档、文本块与图谱关系，这是本系统的重点展示功能（《02》§6.2 功能 5）。
- 输入：answer_evidence 记录（含文档编号与文本块编号）；文档元数据（来源类型、发布时间、文档编号、URL）；本次回答是否使用图谱扩展的标记；使用了图谱扩展时该次回答检索到的路径。
- 处理：
  1. 从 answer_evidence 取本次回答引用的全部证据，每条证据包含文档编号与文本块编号；
  2. 按来源类型分类展示：回答来源、新闻来源、公告来源与相关事件；
  3. 判断本次回答是否使用了图谱扩展；
  4. 使用了图谱扩展时展示图谱路径，路径上的每条关系回溯到 9 条核心关系之一，其中除 EVIDENCED_BY 外给出 source_doc_id、source_chunk_id 与 confidence，EVIDENCED_BY 的证据为其指向的 Document 节点；
  5. 未使用图谱扩展时，在该区域显式标注"本次回答未使用图谱扩展"，不留空，也不展示虚构路径；
  6. 提供从答案到原文的定位入口，展示来源类型、发布时间与文档编号。
- 输出：证据列表；图谱路径区域或其显式标注；可用于点击查看原文的定位信息。
- 前置条件：本次回答已生成；answer_evidence 已写入；若问题为开放式分析问题，页面已具备"模型分析（非公开事实）"的标注区域。
- 后置条件：每条证据均可定位到具体文档与文本块；证据列表中的记录均来自 answer_evidence 表；图谱路径中的每条关系均可回溯到《02》§9.2.3 定义的 9 条核心关系之一（《02》§13）。
- 边界与不做的事：0 跳问题（仅凭文本检索即可回答）以及未启用图谱扩展的实验组（Baseline 1、Baseline 2 与消融 A 组）客观上不存在图谱路径，**不得强行生成或展示虚构的图谱路径**（《02》§13）；图谱关联只表示公开信息中出现的关联，不得表述为因果结论（《02》§5.3）；本模块不新增证据类型，不引入独立于 answer_evidence 的证据来源。
- 来源追溯：《02》§6.2 功能 5；《02》§5.3；《02》§9.2.3；《02》§12.7；《02》§12.9；《02》§13。

### 3.7 历史问答（FR-06）

- 需求编号：FR-06
- 使用者：普通用户查看本会话历史；后台维护数据表。
- 功能描述：保存用户问题、提问时间、回答与引用证据，支持后续查看，同时为实验统计提供数据来源。第一版不启用登录时，历史记录按浏览器生成的 session_id 过滤，不同匿名会话之间不互相可见；启用登录后可把会话关联到 user_id（《02》§6.2 功能 6）。
- 输入：会话标识 session_id（第一版）或 user_id（条件下启用登录后）；已生成的回答与引用证据；提问时间。
- 处理：
  1. 用户提交问题时写入 question，记录问题、提问时间与 session_id；
  2. 回答生成后写入 answer，通过 question_id 与对应问题关联；
  3. 本次回答引用的证据写入 answer_evidence，通过 answer_id 与对应回答关联；
  4. 用户查看历史记录时，后端按 session_id 过滤 question（启用登录后可按 user_id 关联）；
  5. 通过 question_id 与 answer_id 关联还原完整的问答历史，并按提问时间展示；
  6. 用户选择其中一条记录时，回看该次回答及其引用证据——回看只还原 question、answer 与 answer_evidence 三表的内容，**不重新渲染**当时展示的图谱路径视图（图谱路径存于 answer.graph_path 字段，**不建立独立的路径表**，因此表数量仍为六张）；如需查看相关图谱关系，回到 UC-03 重新查询。
- 输出：按会话隔离的历史问答列表，包含问题、提问时间、回答与引用证据。
- 前置条件：提问已完成且回答已生成；question 已写入 session_id。
- 后置条件：同一浏览器会话可以回看此前的问答；不同匿名会话之间不互相可见；历史记录可用于实验统计。
- 边界与不做的事：**历史记录不需要独立的表**——question 记录问题、answer 记录回答、answer_evidence 记录答案引用的证据，三者通过 question_id 与 answer_id 关联即可还原完整的问答历史，表数量仍为六张（《02》§6.2 功能 6、§9.1）；不做多角色与细粒度权限，第一版不启用登录时也不提供跨会话或跨用户的全局历史；历史记录不涉及个人隐私数据（《02》§6.1）。
- 来源追溯：《02》§6.2 功能 6；《02》§6.1；《02》§9.1；《02》§12.7。

## 四、用例分析

### 4.1 用例总览

系统的参与者有两类：普通用户，以及作者本人——作者不在前台出现，通过脚本或受控后台入口在后台执行数据处理，下文与用例表中简称为"后台"（这是操作位置，不是一个独立的系统角色）。普通用户的用例有五个，后台的用例有两个，此外还存在一个条件性的"登录"用例。角色与用例的对应关系如下表。

| 参与者 | 用例编号 | 用例名称 | 前置说明 |
| --- | --- | --- | --- |
| 普通用户 | UC-01 | 提交问题并获取答案 | 第一版无需登录；若条件下开启"仅登录"，则在提交问题之前增加一个登录步骤 |
| 普通用户 | UC-02 | 查看答案与证据来源 | 以本次回答已生成并写入 answer_evidence 为前提 |
| 普通用户 | UC-03 | 查看图谱（含多跳路径查询） | 以图谱已完成写入为前提 |
| 普通用户 | UC-04 | 查看历史记录 | 第一版按 session_id 过滤；若条件下开启"仅登录"，则在查看历史记录之前增加一个登录步骤 |
| 后台 | UC-05 | 后台导入财经文本 | 由作者通过脚本或受控后台入口执行 |
| 后台 | UC-06 | 后台变更财经文本并触发重新处理 | 由作者通过脚本或受控后台入口执行，覆盖修改与删除两种操作 |
| 普通用户 | UC-07 | 条件下的登录 | 仅当学校模板或毕业设计要求明确体现用户管理时开启，采用最小化的"仅登录" |

普通用户的五个用例（提交问题、查看答案、查看来源、查看图谱、查看历史记录）中，提交问题与查看答案在一次交互中连续完成，查看答案与查看来源在同一区域完成，因此在 4.2 节的用例详述中合并为两条：UC-01 提交问题并获取答案、UC-02 查看答案与证据来源；查看图谱与查看历史记录分别对应 UC-03 与 UC-04。合并后，4.2 节中普通用户的用例条目为四条，功能范围与上述五个用例完全一致；后台的两个用例对应 UC-05 与 UC-06，条件性用例对应 UC-07。

用例关系示意如下。

```text
普通用户（第一版为匿名会话，会话标识 session_id）
 ├── 提交问题
 ├── 查看答案
 ├── 查看来源
 ├── 查看图谱
 ├── 查看历史记录
 └── 登录（条件下开启；开启时在"提交问题"与"查看历史记录"之前执行）

后台（作者，通过脚本或受控后台入口）
 ├── 导入财经文本
 └── 变更财经文本并触发重新处理

关系说明：
普通用户 ── 提交问题 ──→ 返回答案、判定区间说明与证据（FR-04）
普通用户 ── 查看来源 ──→ 来源分类、图谱路径或未使用图谱扩展的标注（FR-05）
普通用户 ── 查看图谱 ──→ 实体、事件与多跳路径（FR-03）
普通用户 ── 查看历史记录 ──→ 按 session_id 过滤的问答历史（FR-06）
后台 ── 导入财经文本 ──→ 统一入库（FR-01）
后台 ── 变更财经文本并触发重新处理 ──→ 重新处理与一致性检查（FR-01）
```

普通用户提交问题后，系统返回答案、证据来源，以及使用了图谱扩展时的图谱路径；若本次回答未使用图谱扩展，则标注"本次回答未使用图谱扩展"。用户可以进一步查看原始文档与知识图谱可视化结果，也可以在历史记录中回看此前的问答。第一版不启用登录时，上述用例全部对匿名用户开放，但历史记录按浏览器生成的 session_id 过滤，不同匿名会话之间不互相可见（《02》§6.3）。

**财经信息管理（导入、删除、更新）不在普通用户的用例中**，属于后台系统能力，不对普通用户开放（《02》§6.3）。**若按《02》§6.1 的条件下开启"仅登录"，则在提交问题与查看历史记录之前增加一个登录步骤，其余用例不变。**

### 4.2 用例详述

#### UC-01 提交问题并获取答案

- 参与者：普通用户。
- 前置条件：文本已入库并完成向量索引构建与图谱写入；Embedding 模型与大语言模型接口可调用；问题非空且长度在接口限制之内；第一版无需登录，若条件下开启"仅登录"，则本用例以登录成功为前置条件。
- 主流程：
  1. 用户进入问答页面，页面固定显示"数据截至：YYYY-MM-DD"；
  2. 用户输入自然语言问题并提交，前端携带浏览器生成的 session_id；
  3. 系统校验输入非空且长度在限制之内；
  4. 问题分析：判定问题类型与是否需要图谱扩展，识别实体与时间约束；
  5. 文本检索：在向量索引中检索候选文本块；
  6. 图谱检索：按问题需要执行 0 跳、1 跳或 2 跳扩展；
  7. 时间过滤：带时间约束的问题按 event_time 过滤；"最近"解释为 event_time 落在数据截止时间前 30 天以内，"最新"取符合条件的、event_time 最大的事件，"近期"取数据截止时间前 90 天以内，与《02》§10.3 的判定规则表一致；
  8. 证据排序：合并文本检索与图谱检索的结果并排序；
  9. 大模型生成：基于证据生成答案，不使用数据截止时间之后的信息，不在证据不足时用训练语料中的时间信息补全答案；
  10. 落库：写入 question（含 session_id 与提问时间）、answer、answer_evidence；
  11. 返回答案，页面同时显示"数据截至：YYYY-MM-DD"与本次问题所用的判定区间；
  12. 若问题为开放式分析问题，在页面与答案中同屏标注"模型分析（非公开事实）"，不计入任何指标。
- 备选流程／异常流程：
  - A1 输入为空：提示用户输入问题，不调用检索与模型接口（《02》§7 异常处理）；
  - A2 模型接口超时：按统一封装设置超时与重试，仍失败时给出明确提示，页面不失效，且错误提示不泄露密钥与内部堆栈信息；对相同问题可使用缓存结果（《02》§7、《04》§8.4 风险五）；
  - A3 图谱查询为空：返回文本检索得到的证据并说明图谱侧无匹配；此时按未使用图谱扩展处理并标注"本次回答未使用图谱扩展"（《02》§7、《02》§13）；
  - A4 问题涉及数据截止时间之后的信息：按数据截止时间解释判定基准并说明数据边界，不编造数据截止时间之后的事实（《02》§10.3）；
  - A5 0 跳问题或未启用图谱扩展的实验组：正常返回文本证据，并在图谱路径区域标注"本次回答未使用图谱扩展"，不展示虚构路径（《02》§13）；
  - A6 开放式分析问题：按第 12 步标注"模型分析（非公开事实）"，只用于答辩演示、页面展示与失败案例分析，不作为核心准确率依据，不计入任何指标（《02》§12.9）。
- 后置条件：question、answer、answer_evidence 三条记录可关联还原本次问答；本次问答可在历史记录中回看；若属于定量实验问题，其指标按《02》§12.7 的口径统计。
- 涉及的功能需求编号：FR-04、FR-05、FR-06；触发图谱扩展时同时涉及 FR-03。

说明：本用例必须向用户说明"最新／最近／近期"类问题的判定基准是数据截止时间而不是系统运行当天，一律按 event_time 判定，答案中注明所用判定区间（《02》§10.3、§13）。

#### UC-02 查看答案与证据来源

- 参与者：普通用户。
- 前置条件：本次回答已生成，answer_evidence 已写入。
- 主流程：
  1. 用户在答案下方进入证据区域；
  2. 查看回答来源、新闻来源、公告来源与相关事件；
  3. 查看每条证据的来源类型、发布时间与文档编号；
  4. 点击证据进入原文，定位到具体文档与文本块；
  5. 查看图谱路径区域：使用了图谱扩展时展示路径，未使用时显示"本次回答未使用图谱扩展"。
- 备选流程／异常流程：
  - B1 本次回答未使用图谱扩展：在图谱路径区域显示"本次回答未使用图谱扩展"，不留空，也不展示虚构路径（《02》§13）；
  - B2 证据对应的原文访问受限：保留来源类型、发布时间与文档编号，并提示原文访问受限；
  - B3 开放式分析问题：页面已同屏标注"模型分析（非公开事实）"，与公开事实分区展示（《02》§12.9）。
- 后置条件：用户可以逐条核对答案的依据，每条证据均可定位到文档与文本块。
- 涉及的功能需求编号：FR-05；展示了图谱路径时同时涉及 FR-03。

#### UC-03 查看图谱（含多跳路径查询）

- 参与者：普通用户。
- 前置条件：图谱已完成写入并通过一致性检查；查询条件非空。
- 主流程：
  1. 用户选择查询条件，可以是实体、事件、关系或时间区间；
  2. 提交查询；
  3. 系统在 Neo4j 中检索匹配的实体、事件与关系；
  4. 按需要沿图谱关系做 1 跳或 2 跳扩展；
  5. 带时间约束的查询按 Event 节点的 event_time 过滤；
  6. 以可视化方式展示实体、事件与路径；
  7. 查看路径上除 EVIDENCED_BY 外每条关系的 source_doc_id、source_chunk_id 与 confidence（EVIDENCED_BY 的证据为其指向的 Document 节点）。
- 备选流程／异常流程：
  - C1 图谱查询为空：提示未检索到匹配的实体、事件或路径，并说明可调整实体名称或时间区间（《02》§7 异常处理）；
  - C2 同一事件存在多份来源：按 publish_time 排序展示，发布时间最早的一份作为主要来源，其余作为补充证据（《02》§9.2.5）；
  - C3 查询涉及的关系不在 9 条核心关系之内：不临时增加关系类型，按本体适用边界记录并提示（《02》§12.3）。
- 后置条件：除 EVIDENCED_BY 外的每条展示关系均可回溯到文档与文本块（EVIDENCED_BY 本身即证据关系，其证据为该关系指向的 Document 节点）；路径深度与本次查询设定的检索深度一致。
- 涉及的功能需求编号：FR-03；查看关系证据属性时同时涉及 FR-02。

#### UC-04 查看历史记录

- 参与者：普通用户。
- 前置条件：本会话此前提问已完成；question 已写入 session_id；若条件下开启"仅登录"，则本用例以登录成功为前置条件。
- 主流程：
  1. 用户打开历史记录页面；
  2. 前端携带浏览器中的 session_id；
  3. 后端按 session_id 过滤 question；
  4. 通过 question_id 与 answer_id 关联还原回答与引用证据；
  5. 按提问时间展示历史问答列表；
  6. 用户选择其中一条记录，回看该次回答与其引用证据。
- 备选流程／异常流程：
  - D1 session_id 缺失（例如浏览器存储被清空）：生成新的 session_id，历史记录为空，不展示其他匿名会话的记录（《02》§6.1）；
  - D2 条件下启用"仅登录"：先完成登录，历史记录按 user_id 关联；
  - D3 历史记录为空：给出明确提示，不显示空白页面。
- 后置条件：用户可回看本会话的问答（只还原 question、answer 与 answer_evidence 三表内容，**不重新渲染**当时展示的图谱路径视图——图谱路径存于 answer.graph_path 字段、**不建立独立的路径表**，因此历史回看不涉及虚构路径的问题）；不同匿名会话之间的历史记录互不可见。
- 涉及的功能需求编号：FR-06。

#### UC-05 后台导入财经文本

- 参与者：后台（作者，通过脚本或受控后台入口执行）。
- 前置条件：数据来源为公开可访问的信息并符合《04》§8.2 的合规要求；允许的文件格式清单与必填字段清单已确认（与 FR-01 同一口径，《02》§7 不预先限定录入格式）；数据集版本级属性 dataset_version 与 data_cutoff_time 已确定。
- 主流程：
  1. 选择待导入的财经新闻、公告或政策文本；
  2. 校验文件格式与必填字段；
  3. 写入 document 表，记录标题、正文、发布时间、来源、URL、涉及公司与 ingest_time；
  4. 按固定长度切分为文本块并写入 document_chunk 表；
  5. 触发一次重新处理流程，使图谱与向量索引与文本内容保持一致；
  6. 运行一致性检查并记录结果。
- 备选流程／异常流程：
  - E1 文件格式错误（指不属于允许格式清单的文件）：给出明确提示并跳过该文件，不产生半写状态；允许格式清单在实现阶段固定并与论文 6.1 测试环境一同记录（《02》§7 异常处理）；
  - E2 必填字段缺失：提示缺失字段并拒绝入库；
  - E3 重复文档：按文档标识去重处理，不重复入库。
- 后置条件：新文档可被向量化与事件抽取统一读取；一致性检查结果可核对。
- 涉及的功能需求编号：FR-01。

#### UC-06 后台变更财经文本并触发重新处理

- 参与者：后台（作者，通过脚本或受控后台入口执行）。
- 前置条件：目标文档已入库；变更范围已确定。
- 主流程：
  1. 选择要修改或删除的文档；
  2. 执行修改或删除；
  3. 触发一次重新处理流程；
  4. 按增量方式更新向量索引；文档删除或切分规则调整时整体重建索引；
  5. 更新 Neo4j 中受影响的实体、事件与关系；
  6. 运行一致性检查，核对抽取结果与图谱节点数量、文本块数与向量条数；
  7. 记录本次变更与检查结果。
- 备选流程／异常流程：
  - F1 重新处理中断：记录中断位置，重新运行后按同一流程完成，避免残留失效数据；
  - F2 一致性检查结果不一致：报告差异，并按整体重建方式重新构建索引后再检查；
  - F3 变更影响多个事件节点：按实体消歧与事件去重的既有规则处理，合并动作写入抽取日志；
  - F4 待删除文档已被 answer_evidence 引用：不执行物理删除，只使该文档进入"不可再用于新检索"的处理状态并给出说明，历史回答的引用证据保持不变（FR-06 的历史可回溯要求）。
- 后置条件：图谱与向量索引与文本内容保持一致，不残留失效数据；**已被历史回答引用的文档保持可回溯**；本条口径为"变更后重新处理 ＋ 一致性检查"，不承诺 MySQL、Neo4j 与向量索引之间的实时同步（《02》§7 数据一致性）。**被历史回答引用的文档：**若待删除文档已被 answer_evidence 引用（即曾作为某次历史回答的证据），不执行物理删除，该请求只允许使文档进入"不可再用于新检索"的处理状态（从向量索引中移除、不再进入后续检索候选，但 document、document_chunk 记录与图谱 Document 节点保留），以保证历史回答的引用证据仍然完整可回溯——这是 FR-06"历史记录能还原引用证据"的必要条件。
- 涉及的功能需求编号：FR-01；重新处理过程涉及 FR-02 与 FR-03。

#### UC-07 条件下的登录

- 参与者：普通用户（仅当学校论文模板或毕业设计要求明确体现用户管理时开启）。
- 前置条件：模板或毕业设计要求已确认；登录范围已按最小化口径确定为"仅登录"。
- 主流程：
  1. 用户进入系统；
  2. 系统显示登录入口；
  3. 用户提交登录凭据；
  4. 后端校验凭据，口令以摘要形式存储，不保存明文口令；
  5. 建立会话，用户进入提交问题与查看历史记录流程；
  6. 其余用例保持不变。
- 备选流程／异常流程：
  - G1 条件未满足（第一版默认）：不显示登录入口，用户直接进入提交问题与查看历史记录流程；
  - G2 凭据校验失败：提示失败并允许重试，错误提示不泄露内部信息；
  - G3 会话过期：用户重新登录后继续使用；
  - G4 该用例不做的事：不做注册、不做找回密码、不做多角色与细粒度权限（《02》§6.1）。
- 后置条件：历史记录可在启用登录后按 user_id 关联；若未启用登录，则按 session_id 隔离会话。
- 涉及的功能需求编号：FR-06（历史记录归属）；本用例是 UC-01 与 UC-04 的前置步骤。

以上七个用例中，UC-01～UC-04 为普通用户用例，UC-05 与 UC-06 为后台用例，UC-07 为条件下开启的用例。**财经信息管理（导入、删除、更新）不在普通用户的用例中**；**若按条件下开启"仅登录"，则在提交问题与查看历史记录之前增加一个登录步骤，其余用例不变**（《02》§6.3）。

## 五、非功能需求

本节按《02》§7 非功能需求表的六项逐项编号，从 NFR-01 起顺序编号，每项包含需求说明、**可量化或可验证**的验收口径与验证方法（与《02》§7 表头"验收口径（可量化或可验证）"一致：能给出数值目标的给出数值目标，不能给出数值目标的给出明确的二元判定条件或核查清单，不写无法判定的表述）。验证方法对应《02》§15 第六章的测试类型（6.1 测试环境与实验配置、6.3 抽取实验、6.4 功能测试、6.5 接口测试、6.6 性能测试）。

### 5.1 NFR-01 响应时间

- 需求说明：问答请求需要在可接受的时间内返回，检索与生成的耗时要能分段统计，便于定位性能瓶颈（《02》§7）。
- 验收口径（可量化或可验证）：在统一的测试环境下记录平均回答耗时与 P95 耗时，并分别记录向量检索、图谱查询与大模型生成的耗时；该口径在第 12 节系统指标与论文第 6 章性能测试中保持一致（《02》§7、§12.7）。
- 验证方法：对应论文 6.6 性能测试——按统一测试环境执行问答请求，记录平均耗时、P95 耗时与三段耗时明细。

### 5.2 NFR-02 并发能力

- 需求说明：系统需支持小规模并发访问，不因并发请求出现崩溃或数据错乱（《02》§7）。
- 验收口径（可量化或可验证）：**10 个用户并发发起问答请求，系统不崩溃、不出现数据错乱，接口成功率不低于 95%**；《02》§12.7 的系统指标同时要求**连续 100 次请求的成功率不低于 95%**，系统不崩溃、不出现数据错乱。两项口径在论文第 6 章性能测试中使用同一套记录方式。
- 验证方法：对应论文 6.6 性能测试——分别执行 10 用户并发场景与连续 100 次请求场景，记录接口成功率与数据一致性观察结果。

### 5.3 NFR-03 可维护性

- 需求说明：采用前后端分离与模块化设计，模块边界清晰；模型接口地址、数据库连接、检索参数等集中在配置文件中管理（《02》§7）。
- 验收口径（可量化或可验证）：更换大模型 API 或 Embedding 模型时不需要修改前端代码；按部署说明可在新环境中完成一次完整部署（《02》§7）。
- 验证方法：对应论文 6.4 功能测试——核查配置项集中管理情况，并按部署说明完成一次部署核查；环境信息在 6.1 测试环境与实验配置中记录。

### 5.4 NFR-04 数据一致性

- 需求说明：不做实时同步。文档新增、修改或删除后，由系统触发重新处理并更新 Neo4j，必要时重建或增量更新向量索引；提供一致性检查手段（《02》§7）。
- 验收口径（可量化或可验证）：文档变更后通过一次重新处理流程完成图谱与向量索引更新，不残留失效数据；提供一致性检查手段，可核对抽取结果与图谱节点数量、文本块数与向量条数（《02》§7、§9.3）。
- 明确的限度：本项**不承诺** MySQL、Neo4j 与向量索引之间的实时同步；三者承担不同职责，实时同步超出本科阶段可实现与可验证的范围，也会引入与课题核心问题无关的工程复杂度（《02》§7）。
- 验证方法：对应论文 6.4 功能测试——执行一次文档变更并触发重新处理，运行一致性检查语句，核对三项数量并记录结果；数据集版本信息在 6.1 测试环境与实验配置中记录。

### 5.5 NFR-05 异常处理

- 需求说明：对模型接口超时、图谱查询为空、输入为空、文件格式错误等异常给出明确提示（《02》§7）。其中"文件格式错误"的判定依据是允许的文件格式清单，该清单在实现阶段固定并与论文 6.1 测试环境一同记录（《02》§7），以保证该场景可以构造、可以判定。
- 验收口径（可量化或可验证）：构造不少于 6 类异常场景逐一测试，系统不出现未捕获异常导致的页面失效或服务中断，错误提示不泄露密钥与内部堆栈信息（《02》§7）。
- 验证方法：对应论文 6.4 功能测试——按异常场景清单逐项执行，记录系统提示与页面状态；场景清单至少覆盖模型接口超时、图谱查询为空、输入为空、文件格式错误四类，并在此基础上补足至不少于 6 类。

### 5.6 NFR-06 系统安全性

- 需求说明：API 密钥不写入前端代码，接口做输入校验与请求频率限制；口令加密存储的要求仅在启用登录功能的条件下适用（《02》§7）。
- 验收口径（可量化或可验证）：**密钥仅保存在后端环境变量或配置文件中**，问答接口具备输入长度与请求频率的基本限制；若启用登录，则口令以摘要形式存储，不保存明文口令（《02》§7、§6.1）。
- 验证方法：对应论文 6.5 接口测试——核查密钥存放位置与前端代码，执行输入长度与请求频率限制的接口测试；启用登录时补充口令存储形式的核查。

## 六、可行性分析

### 6.1 与《04》§8 的关系

本节是《04》§8 可行性分析的展开，口径与《04》§8.1～§8.4 完全一致，不引入《04》§8 之外的新论据。展开的方式是把已有结论落到需求层面：技术可行性对应本文件的技术需求边界，数据可行性对应数据来源与规模需求，时间可行性对应阶段工期与需求范围，风险与对策对应需求阶段需要防范的范围蔓延与验收风险。

### 6.2 技术可行性

《04》§8.1 的结论是：本课题所用技术均为成熟方案——Vue 3 负责前端页面，Python 与 FastAPI 负责后端接口，MySQL 存储业务数据与文档元数据，Neo4j 提供图存储与多跳查询，FAISS 作为向量索引与向量检索组件完成语义检索，Embedding 模型与大语言模型通过 API 调用，Docker 统一运行环境；这些组件均有公开文档与成熟的社区资料，学习成本可控，单人即可完成开发。

在需求层面的展开有三点。第一，检索、图谱扩展、时间过滤与证据排序由后端代码直接实现，不依赖额外的检索框架，模块边界清晰，调试时容易定位问题环节，这与 FR-04 中"问题分析 → 文本检索 → 图谱检索 → 时间过滤 → 证据排序 → 大模型生成"的分步需求一致。第二，数据规模按第一版到第三版逐步扩展，单台个人计算机即可承载向量索引与图数据库，因此 FR-01 的数据导入与重新处理需求、FR-03 的图谱查询需求在既定部署规模内可以满足。第三，技术选型不引入额外的高学习成本组件，本文件据此不提出任何新增技术需求，具体不引入清单见 8.2.2。

### 6.3 数据可行性

《04》§8.2 的结论是：数据来源选取公开可访问的信息（上市公司公告、监管机构公开信息、政策文件与正规财经新闻），并遵循相应网站的访问规范、使用条款与学校毕业设计的相关要求；系统与论文仅用于毕业设计的研究与演示，保留原始来源、来源类型与发布时间等元数据，不提供任何投资建议，不涉及个人隐私数据。

在需求层面的展开有四点。第一，数据准备按"先小后大"三版推进——第一版 10 家公司、100 篇文本，用于跑通数据导入、清洗、事件抽取、图谱写入、向量检索与问答的完整流程；第二版扩展到 50 家公司、500 篇文本；第三版扩展到 100 家以上公司、1000 篇以上文本，用于最终对比实验与消融实验。这与 FR-01 的统一入库需求、FR-02 的抽取需求相互支撑。第二，第一版不使用股吧数据，股吧内容仅列为后续可扩展的数据来源，这一口径写入 8.2.2。第三，数据截止时间 data_cutoff_time 为数据集版本级属性，与 dataset_version 成对记录在数据集元信息中，不由任何单篇文档携带，也不采用"取所有文档最晚时间"的推导口径；每篇文档入库时记录 ingest_time，并保留 publish_time。第四，系统对外统一显示"数据截至：YYYY-MM-DD"，"最近""最新""近期"等相对时间表述一律以该版本属性为基准、并按 event_time 判定，而不是以系统运行当天为基准（《02》§10.3、§13）。

由此可以判断：数据的来源范围、规模梯度与元数据口径，足以支撑第二节至第五节提出的角色需求、六个功能模块与三组实验的需求，不需要引入边界之外的数据来源。

### 6.4 时间可行性

《04》§8.3 的结论是：本课题总周期约为 4～5 个月，按 12 个阶段与四个里程碑推进，每个阶段都有明确产出物，论文写作与开发同步进行；数据准备与事件抽取阶段的工期中已经包含抽取评测集的人工标注（开发集 Dev 建议 60 条 ＋ 测试集 Test 200 条，合计约 250～300 条）以及实体消歧与事件去重的实现与核查，这两项工作不在时间压缩范围之内；时间紧张时可以削减功能扩展，但优先保证普通 RAG 与知识图谱增强问答跑通。

《04》§9.1 给出的需求分析阶段工期为 1 周，主要产出为用户角色分析、功能需求、非功能需求与用例说明，与本文件的第二节至第五节一一对应。需求范围按《02》§5.1 与《04》§7.1 的边界清单收敛，因此本阶段产出的需求条目不超出既定工期；后续如遇时间紧张，取舍原则仍是优先保证普通 RAG 与知识图谱增强问答跑通，而不是扩大需求范围。

## 八、本阶段不做的事（非目标）

### 8.1 阶段非目标

第一，本阶段不做系统设计。总体架构、功能模块设计、数据库设计、本体设计、接口设计属于第 4 阶段与论文第四章的内容（《02》§15 第四章、§16.1）；本文件只给出需求条目与验收口径，不给出这些条目的实现方案。

第二，本阶段不做开发。本阶段不产生任何代码、不产生任何数据、不产生任何实验结论；本文件中出现的全部指标均为需求与验收口径，不是运行结果。

第三，本阶段不引入任何新功能与新技术的需求。需求范围以《02》§5.2 与《04》§7.2 的重点研究清单为上限，以《02》§5.1 与《04》§7.1 的不研究清单为下限；凡属第 4 阶段或后续阶段的实现方案，不在本阶段作为需求提出。

### 8.2 边界清单

#### 8.2.1 不研究清单（《02》§5.1 与《04》§7.1）

| --- | --- |
| 股票涨跌预测 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |
| 股票价格预测 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |
| 自动交易 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |
| 投资买卖建议 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |
| 收益率预测 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |
| 量化交易策略 | 不研究，不作为系统功能，也不在论文中作出任何承诺 |

系统不提供买卖建议，不输出目标价或收益预测，不接入交易接口。答辩中被问及相关问题时的回答口径是：本系统的定位是财经信息的组织、检索与问答，不涉及预测与投资决策（《02》§5.1、《04》§7.1）。

这条边界同样适用于文献引用：本课题只引用与信息组织、检索与问答相关的方法，不引用预测与回测类工作的预测结论（《04》§7.1）。

#### 8.2.2 明确不引入的技术与做法（《02》§8.4、§6.1、§7，《04》§7.1）

- 不引入 LangChain 与 LlamaIndex，避免框架把检索与拼装流程封装成黑盒，导致消融实验无法逐项控制变量；
- 不引入 Milvus、Qdrant、Weaviate 等独立向量数据库系统，也不引入 Elasticsearch 等独立检索引擎；向量检索使用 FAISS，其定位是向量相似度检索库（索引库），与独立向量数据库系统定位不同；
- 不引入 Kafka、微服务架构与 Kubernetes，系统按单体后端加前端分离的方式部署在一台机器上，已经能够满足 10 个并发用户的小规模访问要求；
- 不引入股吧数据源，第一版的数据来源限于公开可访问的上市公司公告、监管机构公开信息、政策文件与正规财经新闻；
- 不引入多角色权限体系：本科阶段只设置一个普通用户角色，不做注册，不做找回密码，不做细粒度权限控制；
- 不承诺 MySQL、Neo4j 与向量索引之间的实时同步，一致性口径为"变更后重新处理 ＋ 一致性检查"（《02》§7）。

### 8.3 本阶段的范围守卫

需求分析阶段最容易出现的问题是范围蔓延——把《02》§5.1 与《04》§7.1 已明确不研究的内容，或把 8.2.2 已明确不引入的技术与做法，当作"需求"写进来（《06》第六节风险提示）。本文件第三条需求、第六节可行性分析与 8.2 节的边界清单共同承担这一守卫作用：任何需求条目必须在第七节的追溯矩阵中找到《02》或《04》的具体节号作为来源，找不到来源的条目不得写入本文件。
