# 用户测试方案与验收标准（UAT）

> **本文件用途**：把「进行用户测试，根据体验进行优化升级」这件事**先定标准、再动手**。
> 测试对象：A 股信息披露问答系统（Vue 3 前端 `:5173` ＋ FastAPI 后端 `:8000` ＋ MySQL ＋ Neo4j ＋ 向量索引）。
> **本文件在测试开始前写成**——参与者、任务、判据都是预先定下的，不是事后按结果编的。
> 日期：2026-10-17

---

## 一、为什么这件事现在做：前端此前**没有做过真实浏览器验证**

前端自己的 `README.md` 第 65 行把这条如实登记为已知限制：

> **无浏览器自动化**：本环境无 Playwright／Selenium，页面的可用性以「构建成功 ＋ dev server 200 ＋ 代理联通 ＋ 组件内对每个接口的调用点清单」为证据，**未做真实浏览器点击验证**（作者目视验收）。

也就是说：此前所有「页面可用」的结论都来自**读代码**，不是**点页面**。本次先把这条补上，再谈优化。
（本机实际可用 Playwright 1.64.1 ＋ Chromium——本方案即用它做真实浏览器走查。）

## 三、参与者设定（5 类，刻意包含「没读过论文的人」）

项目此前的验收几乎都由**知道系统内部口径的人**完成。用户测试要补的正是反面：**不知道 `【回答】`／`is_graph_extended`／`图谱写源` 这些词的人，能不能自解释地把事办成。**

| 代号 | 参与者 | 他要办的事 | 为什么设这一类 |
| --- | --- | --- | --- |
| P1 | 投研分析师 | 快速问一家公司的多跳关系题，并**速读**答案 | 系统的目标用户；关心「多久出答案、答案能不能扫」 |
| P2 | 研究生（写论文） | 把一条答案**连同证据与图谱路径引用进论文** | 系统的最强「可追溯性」承诺，只有这一类人会真的用到底 |
| P3 | 合规／风控 | 核对一条关系**凭什么成立**、数据截至到哪天 | 检验「证据可追溯」是否只是文案 |
| P4 | 首次来访者（手机端） | 打开首页，**60 秒内**自己搞明白「这是什么、能问什么、从哪开始」 | 检验首屏自解释性；答辩现场的第一印象 |
| P5 | 键盘／无障碍用户 | **只用键盘**完成一次提问 | 检验焦点可见性与 ARIA |

## 四、任务清单与判据（预先定下）

每个任务都写明「完成判据」与「阻断判据」。**完成判据未达成＝功能缺陷；阻断判据命中＝P0。**

| 编号 | 参与者 | 任务 | 完成判据 | 阻断判据（P0） |
| --- | --- | --- | --- | --- |
| T1 | P4 | 打开 `/`，不看任何说明，说出这系统能问什么 | 首屏出现**可点击**的示例问题；可见文本 ≥400 字；1440 宽与 390 宽下**横向溢出 ≤2px** | 首屏无入口／横向溢出 >16px |
| T2 | P1 | 在 `/ask` 输入一个真实多跳问题并提交 | 点击后**后端确实收到 `POST /api/qa/ask`**；等待期有可见进度；最终落到 `/answer/<id>` | 点击后无 POST／无限等待无反馈／超过 8 分钟不出答案 |
| T3 | P2 | 打开一条答案，逐项核对四段结构并点开一条证据的原文 | 四段固定段头**逐段存在**；「查看原文上下文」点得开且看得到原文 | 四段缺失／证据打不开 |
| T4 | P3 | 在 `/graph` 检索一家公司 → 看邻居 → 输入一个不存在的实体 → 点节点 | 真实实体**搜得到**；搜不到时**画布不留上一个锚点的数据**；空结果文案不像报错 | 空结果时旧数据仍在（会被读成「搜到的就是这个」） |
| T5 | P5 | 只用 Tab 走一遍 `/ask` | 每个焦点元素都有**可见焦点样式**；无 ARIA 断裂引用 | 焦点不可见 |
| T6 | P4 | 390×844 下走 `/ask`／`/graph`／`/history` | 三页横向溢出 ≤2px | 溢出 >16px |
| T7 | P1 | 打开一条长答案，判断能否速读、能否二次使用 | 最长单行 <220 字；页面给出「复制／导出／引用」入口 | — |

**全局判据（每个任务都查）**：浏览器控制台与网络**零错误**（含 429）。

## 五、优化升级的验收标准（第二轮的门槛）

优化不是「改了就算」，要过这五条：

1. **请求预算**：一次完整走查（首屏 → 提问 → 图谱 → 搜两次 → 历史 → 回看）发出的 `/api/*` 请求数，必须落到后端限流窗口（**60 次／60 秒／来源 IP**，以 `/api/health` 豁免）以内，或在其超出时**有明确的、用户可见的限流提示**——**不允许再出现「被限流」被显示成「没有这家数据」**。
2. **判据不变**：第四节所有**完成判据**在第二轮必须全部达成，且**阻断判据零命中**。
3. **不回归**：前端 67 例单元测试、Python 289 例单元测试全绿；`npm run build` 成功。
4. **不破坏阶段门禁**：`工具/验收第9阶段.py`（58 项）与 `工具/跨文档核验.py`（15 项）仍通过——**后端 `config.py` 的限流参数 60／60 是第 9 阶段门禁锁定的登记参数，本次不改它**（改它要同步《25》《10-部署/README》与门禁基线，属于口径变更，不在「体验优化」范围内）。
5. **诚实性不变**：所有空态、错误态、计数都必须来自真实接口返回；**不得为了好看而弱化「未检索到／未接入」这类如实呈现**，也不得引入任何演示数据。

## 六、测试装置与证据落点（可复现）

| 装置 | 位置 | 作用 |
| --- | --- | --- |
| UAT 主脚本 | `交付物/03-代码/前端/测试/uat/跑UAT.mjs` | 按 T1～T7 真实浏览器走查：逐步截图、记录控制台错误与失败请求、量每页耗时 |
| 请求预算探针 | `交付物/03-代码/前端/测试/uat/测请求预算.mjs` | 逐页计数 `/api/*` 请求，量化一次走查花掉多少限流额度 |
| 证据目录 | `交付物/03-代码/前端/测试/uat/证据/<轮次>/` | 截图 ＋ 每步可见文本的 JSON 快照 ＋ 浏览器错误 ＋ `UAT-结果.json` 汇总 |

装置本身的两处**自证纪律**（首版踩过的坑，已修并留痕）：

* 提交按钮必须锚到 `#q` 与 `button.btn--quiet`：首版用了宽泛的 `.btn--primary`，取到的是 hero 的「开始提问」（只做 `scrollIntoView`），于是「点击提交」根本没发出 POST，后端从未收到 `/api/qa/ask`——**那是装置缺陷，不是产品缺陷**，必须修装置而不是报产品 bug；
* 答案到达必须按「URL 进入 `/answer/`」判定：首版用 `/【回答】/` 判到，而提问页的 placeholder 与正文说明里就含「【回答】／事件是什么？」字样，0.6 秒就误报「答案出现」。

## 七、本轮不做的（划清边界，避免越界改口径）

* **不改后端限流参数**（60／60 是门禁登记值）：见第五节第 4 条。
* **不改论文、答辩材料、数据集、图谱、实验读数**：体验优化不触碰已收口的交付物。
* **不引入任何被《02》排除的技术**（无 UI 组件库、无大型可视化框架、无 LangChain／Milvus／Kafka／K8s）。
* **不重做视觉设计**：本轮只修可用性缺陷，设计语言（暗色 ＋ 红黑 ＋ 吸顶 ＋ 背景曲线）保持不变。
