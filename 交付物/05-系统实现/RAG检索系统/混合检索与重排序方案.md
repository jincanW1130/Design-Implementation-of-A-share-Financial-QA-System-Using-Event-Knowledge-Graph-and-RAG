## 一、现状与问题

### 1.1 现有检索链路（已冻结）

```
问题
  ├─ 向量通道：BAAI/bge-small-zh-v1.5 → FAISS → Top-N（N=20）
  └─ 图谱通道：实体解析 → 1/2 跳子图 → 事件证据块（G1～G7）
        ↓
     并集去重（merge_candidates；向量侧按 vector_rank，图谱侧按路径顺序）
        ↓
     时间过滤（apply_time_filter）
        ↓
     Token 预算裁剪（trim_to_budget，预算 3600）
        ↓
     Top-K = 10（keep_top_k）
        ↓
     证据排序（order_evidence，E 组启用）
```

对应实现：`检索/pipeline.py` 的 `collect_vector_candidates()`、`collect_graph_candidates()`、
`merge_candidates()`、`apply_time_filter()`、`trim_to_budget()`、`keep_top_k()`、`order_evidence()`；
向量侧 `检索/vector_search.py` 的 `LocalEmbedder`、`VectorSearcher.search()`。

### 1.2 实测短板

| 现象 | 读数 | 说明 |
| --- | --- | --- |
| 核心集 108 题 Recall@K | A 组（纯向量）0.7761；C 组（+2 跳图谱）0.8730 | 图谱通道带来 +9.7 个百分点，但仍有约 12.7% 的 gold 块未召回 |
| Complete Evidence Recall@K | 30 题预实验五组均为 0.5667 | 平均只有 56.7% 的题能把**全部** gold 块找齐 |
| MRR | 核心集 A 0.5852／C 0.6076 | 首个命中位置仍偏后，说明排序而非「能否找到」是主要瓶颈之一 |
| 精确串匹配 | 无独立通道 | 股票代码、公司简称、公告标题、数字指标等**字面强信号**目前只能靠稠密向量隐式表达 |
| 冷启动 | 检索独立复跑约 6.48 s（含模型加载约 6.44 s） | 增加通道时若再加载一个大模型，会进一步放大冷启动 |

**结论**：优先补一个**轻量、确定性、无需联网**的词汇通道，并采用排名融合而非分数加权；
Rerank 作为第二阶段可选项，必须受延迟预算约束。

## 二、总体设计

### 2.1 三阶段渐进路线

| 阶段 | 内容 | 默认状态 | 预计收益 | 风险 |
| --- | --- | --- | --- | --- |
| P1 | 字符 n-gram / BM25 词汇通道 + RRF 融合 | **默认关闭**，实验组 F | Recall 提升，尤其代码/名称/数字 | 索引体积、分词口径 |
| P2 | 融合后 Top-M（如 50）→ Cross-Encoder 重排 → Top-K | 默认关闭，实验组 G | MRR、Top-1 准确性 | CPU 延迟、模型体积 |
| P3 | 查询改写/实体扩展（可选） | 不做，仅留接口 | 长尾问法 | 引入新的不确定性 |

**约束**：A～E 五组的冻结结果不得改变；新通道只能以**新实验组**出现，默认开关关闭，
配置、题集、指标口径与现有实验完全一致，便于同口径对比。

### 2.2 P1：词汇通道（BM25 / 字符 n-gram）

**为什么不用另一个稠密模型**：本机已有 bge-small-zh-v1.5，再引入一个 embedding 模型会增加
内存与冷启动；而词汇通道恰好补足稠密向量对「精确串」不敏感的问题。

**索引对象**：`chunks.jsonl` 的 5018 个文本块（`config.CORPUS["chunks"] = 5018`）。

**分词方案（二选一，建议 A）**：

- **A. 字符 n-gram（推荐，零依赖）**：中文按 1～3 字符滑窗，英文/数字按连续串切分；
  对股票代码（6 位数字）、公司简称、指标数字天然友好。优点是无需词典、完全确定性、离线。
- **B. jieba + BM25**：中文分词后建 BM25。效果通常更好，但引入词典与分词版本差异，
  且公司简称可能被切碎；需把 jieba 版本锁进 `requirements.txt`。

**实现要点**：

1. 新模块：在 `检索` 组件下新增 `lexical_index`（Python 模块，本轮未创建）：
   - `build_index(chunks) -> LexicalIndex`：构建倒排表与文档长度统计；
   - `LexicalIndex.search(question, n) -> [{chunk_id, doc_id, lexical_score, lexical_rank}]`；
   - 索引落盘 `检索/lexical_index/`（或 `交付物/04-数据与知识图谱/` 下的导出版本目录），
     文件含 `schema`、`corpus_hash`、`tokenizer` 版本，**哈希不符即拒绝加载**。
2. 接入点：`检索/pipeline.py` 的 `collect_vector_candidates()` 同级新增
   `collect_lexical_candidates(lexical_index, question, n)`，返回结构与向量侧同构
   （`rows`/`timing`/`n`），**不改变** `VectorSearcher` 的既有语义。
3. RRF 融合接入点：`merge_candidates()` **之前**（或新增 `fuse_rankings()` 再调用
   `merge_candidates()` 的向量槽位）。建议新增：

   ```python
   def fuse_vector_and_lexical(vector_rows, lexical_rows, k_rrf=60) -> list[dict]:
       """RRF：score = Σ 1/(k_rrf + rank)；输出按融合分降序，保留两路原始排名。"""
   ```

   融合结果写回 `vector_rows` 的形状（`vector_rank` 改为融合排名，另存
   `vector_rank_raw`、`lexical_rank`、`rrf_score` 以便追溯），从而**不改**
   `merge_candidates()` 的下游契约。
4. 图谱侧不受影响：图谱候选仍按路径顺序进入并集；两路同时命中仍只保留一条
   （`hit_by` 增加 `"lexical"`，排序权重不变）。
5. 预算与 Top-K 不变：融合只改变「哪些块进入候选」，`trim_to_budget()` 与
   `keep_top_k()` 的口径保持原样，便于对比。

**推荐参数（首轮实验）**：

| 参数 | 值 | 理由 |
| --- | --- | --- |
| 词汇通道候选数 | 20（与 N 对齐） | 保持「两路各 N」的对称性，便于解释 |
| RRF 常数 `k_rrf` | 60 | 信息检索常用默认值，对排名头部不敏感 |
| n-gram 范围 | 1～3 | 覆盖单字、双字词、三字公司简称/术语 |
| 最小字符过滤 | 空白与纯标点剔除 | 避免噪声词占据倒排 |

**预期收益（需实验验证，不作为结论）**：
- 股票代码、公告标题、指标名类问题的 Recall@K 与 MRR 提升最明显；
- 语义改写类问题可能持平或略降，这正是必须做消融的原因。

### 2.3 P2：Cross-Encoder 重排序（可选）

**候选来源**：融合后的 Top-M（建议 M=50，即 N=20 向量 + 20 词汇 + 图谱新增块，去重后取前 50）。

**模型选择**：

| 方案 | 模型 | 体积/延迟 | 适用 |
| --- | --- | --- | --- |
| 推荐 | `BAAI/bge-reranker-base`（中文） | CPU 上 50 对约 0.3～1.0 s（估） | 本地离线、与现有 bge 系一致 |
| 备选 | `BAAI/bge-reranker-v2-m3` | 更大更慢 | 有 GPU 时 |
| 不推荐 | 在线 rerank API | 引入外部依赖与费用 | 与本项目离线纪律冲突 |

**接入点**：`检索/pipeline.py` 的 `merge_candidates()` 之后、`trim_to_budget()` 之前，新增：

```python
def rerank_records(records, question, reranker, top_m=50, top_n=None) -> dict:
    """对前 top_m 条按 (question, chunk_text) 交叉编码打分，重排后截断到 top_n；其余保持原序。"""
```

- 只重排**前 M 条**，其余保持原顺序，保证长尾不被完全打乱；
- 分数与原 `similarity`／`vector_rank` 分开保存（`rerank_score`、`rerank_rank`），
  不覆盖原字段，便于复核；
- 失败回退：模型不可用/超时 → 记 WARNING 并**原样返回**输入顺序，不阻塞问答；
- 延迟预算：端到端当前平均 14.994 s、P95 37.048 s（`系统指标/NFR_readings.md`），
  rerank 目标增量 ≤ 1 s；若超过 1.5 s 则只在离线实验启用。

**触发条件（建议）**：仅在候选数 > K 且问题包含以下信号时启用——6 位股票代码、书名号/引号
内的专名、数字指标、或融合分数头部与第 K 名差距小于阈值。其余情况跳过以省延迟。

> **第 10 轮实现差异（2026-10-18）**：复核发现本系统第③／④／⑤步各自用同一套分层排序键
> 重新排序，合并阶段的列表顺序**不参与**后续选择。若严格按上面的位置接入，重排结果会被
> 下游覆盖，成为"看起来接入了、实际无效果"的空接口。故第 10 轮落地的是**可插拔呈现顺序
> 包装器**（`增强/reranker.py`，默认 `None` 不启用）：在 `pipeline` 输出之后只改最终证据顺序，
> 不增删证据、不改变 Recall@K（MRR 可能变化）。若未来要做真正改变候选集合的 Cross-Encoder
> 重排，必须作为**新实验组**在「④ 保留 K」之前引入，并同步重跑 A～E 的冻结口径，不能走
> 默认链路。

## 三、实验设计（不改变冻结结果）

### 3.1 新组别

| 组 | 定义 | 用途 |
| --- | --- | --- |
| F1 | C + 词汇通道（RRF） | 验证 P1 |
| F2 | D + 词汇通道（RRF） | 验证 P1 与时间过滤叠加 |
| G1 | F1 + Cross-Encoder 重排 | 验证 P2 |

A～E 及 B1 保持不动；F/G 单独输出，不并入既有报告的总平均。

### 3.2 题集与指标

- **开发集**：30 题预实验问题集（`交付物/06-实验与评测/对照产出_v13/`），用于调参；
- **确认集**：正式 120 题（核心集 108 题用于判定），**只看一次**，防止过拟合；
- **指标**：Recall@K、Precision@K、MRR、Complete Evidence Recall@K（与 `检索/metrics.py` 完全一致）；
- **业务指标**：AA/Completeness/Faithfulness（复用现有评分口径），仅对 F/G 与 C 做同题对比；
- **延迟**：检索段耗时、端到端耗时、P95；rerank 增量单独计时。

### 3.3 判定门槛（预登记，避免事后挑指标）

| 指标 | 通过条件 |
| --- | --- |
| Recall@K（核心集） | ≥ C 组 + 2.0 个百分点 |
| Complete Evidence Recall@K | 严格大于 C 组 |
| MRR | 不低于 C 组 |
| 端到端 P95 | 增量 ≤ 1.5 s |
| AA/Faithfulness | 不下降（允许 ±0.02 的评分噪声） |

任一硬门槛不满足 → 不启用该通道。

## 四、工程与可维护性

### 4.1 配置与开关

- 在 `检索/config.py` 增加**新**开关（不改变现有 `SWITCH_NAMES` 的语义）：
  `lexical_enabled`、`rrf_k`、`rerank_enabled`、`rerank_model`、`rerank_top_m`；
- 默认全部关闭；配置精度与现有 `SIMILARITY_DECIMALS = 8` 一致，保证可复现；
- 任何模型名、路径、阈值不得写死在脚本里（沿用 `config.py` 的既有纪律）。

### 4.2 索引构建与版本

- 构建脚本放 `工具/` 目录（脚本名拟为「构建词汇索引」，本轮未创建），输出带 `corpus_hash` 与 `tokenizer_version`；
- 启动时校验哈希；不匹配则**自动禁用词汇通道并记 WARNING**，绝不静默使用旧索引；
- 索引文件体积预估：5018 块、1～3 字符 n-gram，倒排表预计数十 MB 量级，需实测；
- 清理/重建流程写入部署手册。

### 4.3 可观测性

- 每次检索的 trace 增加：`lexical_candidates`、`rrf_dual_hit`、`rerank_used`、
  `rerank_seconds`、回退原因；
- 日志只记 ID 与统计，不打印问题原文（沿用现有脱敏纪律）；
- 指标接入 `系统指标/` 的读数文件，不改变现有 NFR 读数口径。

### 4.4 风险与回退

| 风险 | 缓解 |
| --- | --- |
| 词汇通道放大量词/标点噪声 | n-gram 过滤 + 停用标点 + 实验验证 |
| RRF 改变既有候选顺序，影响可复现性 | 新开关默认关闭；字段保留原始排名 |
| Rerank 模型冷启动/内存 | 懒加载 + 超时回退；只在实验启用 |
| 索引与语料版本漂移 | `corpus_hash` 校验，不匹配即禁用 |
| 与图谱通道叠加后预算被挤占 | 预算口径不变；观察 `trim_to_budget()` 的裁剪统计 |
| 延迟超预算 | 触发条件 + Top-M 限制 + 超时回退 |

## 七、实测：BM25／字符 n-gram 离线对照（2026-10-18，第 10 轮）

**性质**：纯离线诊断。只用 30 题预实验集与现有 `chunks.jsonl`；向量侧取现有
`VectorSearcher.search(question, 10)`，词汇侧取新增的纯 Python BM25（`增强/lexical_search.py`，
字符 1～3 n-gram，`k1=1.5`、`b=0.75`）；**未跑 LLM、未联网、未改题集／gold／K／N，
未接入默认链路**。向量与词汇各取 Top-10；RRF 用两路 Top-20 融合后取 Top-10，仅作诊断。

### 7.1 平均读数（30 题，K=10）

| 通道 | Recall@10 | MRR | Complete@10 | Hit@1 | Hit@10 | 首个 gold 平均位次 |
| --- | --- | --- | --- | --- | --- | --- |
| 向量（现有基线） | 0.6781 | 0.6589 | 0.5667 | 0.5667 | 0.8333 | 1.92 |
| BM25（字符 n-gram） | 0.6448 | **0.6811** | 0.5333 | 0.5667 | 0.8333 | **1.68** |
| RRF（向量＋BM25） | **0.7179** | **0.6828** | **0.6000** | 0.5667 | **0.9000** | 1.85 |

- **BM25 单独使用不如向量**：Recall@10 低 3.33 个百分点，Complete 低 3.33 个百分点；
  但 MRR 高 2.22 个百分点、首个命中平均位次提前 0.24 位，说明它**排序头部更准、覆盖率不足**。
- **逐题 R@10**：BM25 相对向量 5 胜／16 平／9 负。胜题集中在**精确串**（PE-26／28 从 0 提到 1.0、
  PE-27 从 0 到 0.5、PE-15 +0.33、PE-11 +0.14）；负题集中在**多 gold、语义改写**题
  （PE-22 −0.6、PE-23 −0.5、PE-24 −0.5、PE-30 −0.67、PE-16 −0.5）。
- **RRF 融合**相对向量：Recall@10 **+3.98 个百分点**、Complete@10 **+3.33 个百分点**、
  MRR **+2.39 个百分点**、Hit@10 **+6.67 个百分点**；Hit@1 持平。它同时缓解了 BM25 的多数
  负题，但 PE-16／PE-23 仍由"向量命中"退化为"两路均未命中"，说明融合不是无损的。

### 7.2 工程读数

| 项 | 读数 |
| --- | --- |
| 词汇索引规模 | **332,768 个不同 n-gram token（词表规模）**、2,287,765 条 posting；n-gram token 总出现数 3,506,128 |

### 7.3 结论与边界

1. 词汇通道确实补足了稠密向量对**代码、专名、精确数字**的不敏感；但单用会损失语义改写题，
   **不能替代**向量通道。
2. RRF 在 30 题开发集上四项指标均有正向读数，达到本方案 §3.3 的"Recall +2.0 个百分点"门槛；
   但这是**开发集、离线、独立 Top-K** 的诊断，尚未经过 108 题核心集与确认集，**不得据此默认启用**。
3. 下一步（若继续）：以实验组 F1（C + RRF 词汇通道）在正式题集同口径复跑，并做题型拆分与
   逐题误差分析；通过 §3.3 全部门槛后才考虑切换默认。
4. 局限：n-gram 未做停用词／标点加权；BM25 参数未调；RRF 的 `k_rrf=60` 为常用默认值，
   未做敏感性分析。以上均登记为后续工作。
