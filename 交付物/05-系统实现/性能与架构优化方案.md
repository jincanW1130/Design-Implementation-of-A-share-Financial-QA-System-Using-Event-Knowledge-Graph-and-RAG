## 一、性能

### 1.1 MySQL 索引设计与失效场景

**问题**：六表的主键、唯一键、联合索引是否覆盖真实查询；是否存在函数运算、隐式转换、前缀 `%` 等失效写法。

**现状（实测）**：六表按 DDL 注释口径共 **14 个普通二级索引**（含 `uk_user_username`；`SHOW INDEX` 的非 PRIMARY 索引共 **18 组**——差额为 `uk_chunk_doc_index`／`uk_chunk_vector_id` 两个唯一键与 `fk_question_user`／`fk_ae_chunk` 两个 FK 自动索引），另有各表主键。

| 表 | 主键／唯一键 | 与查询相关的普通索引 |
| --- | --- | --- |
| `question` | PK `question_id` | `idx_q_session_time(session_id, ask_time)`、`idx_q_task_type` |
| `answer` | PK `answer_id` | `idx_a_question_id(question_id)`、`idx_a_create_time` |
| `answer_evidence` | PK `(answer_id, chunk_id)` | `idx_ae_answer_id`、`idx_ae_doc_id`、`idx_ae_evidence_type`、FK `chunk_id` |
| `document` | PK `doc_id` | `idx_doc_publish_time`、`idx_doc_ingest_time`、`idx_doc_category` |
| `document_chunk` | PK `chunk_id`；UK `(doc_id, chunk_index)`、UK `vector_id` | `idx_chunk_doc_id` |
| `user` | PK `user_id`；UK `username` | — |

EXPLAIN 实测：历史列表走 `idx_q_session_time`＋`idx_a_question_id`，`Backward index scan`，无 filesort；历史总数 COUNT 覆盖索引（`Using index`）；后台文档列表走 `idx_doc_publish_time`；按 `doc_id` 取块走 `uk_chunk_doc_index`；按 `answer_id` 取证据走 `PRIMARY`。

> 口径注：实验脚本里的简化 JOIN 样本（不含 `evidence_count` 相关子查询）在 30 行小表上被优化器选为全表扫描；上句结论来自**实际接口 SQL**（`qa_service.history_list`）的 EXPLAIN。2026-10-19 复跑仍为 `idx_q_session_time`＋`Backward index scan`，COUNT 走覆盖索引。

失效场景核查：

* 后端 SQL 中**没有 `LIKE`，更没有 `LIKE '%x%'`**；模糊匹配只出现在 Neo4j 实体名检索。
* WHERE 子句未对索引列做函数／表达式运算；时间比较直接比较列本身。
* 参数由 PyMySQL 绑定为 Python `int`，无隐式转换。
* `(doc_id, chunk_index)` 联合唯一键同时覆盖“按文档取块”和“按块序号排序”。

**结论**：当前查询集合下不需要新增索引；新增索引反而拖慢写入，索引设计维持六表 DDL。

> **三件套**：实现位置 `交付物/03-代码/后端/db.py`、`交付物/03-代码/后端/api/history.py`；证据 `交付物/05-系统实现/前后端系统集成/_工作底稿/SQL慢查询与索引_第6轮.json`；复跑 `python 工具\实验_SQL慢查询与索引.py`。

**后续若数据量增长**：① 用 `performance_schema.events_statements_summary_by_digest` 找 `SUM_NO_INDEX_USED>0` 或扫描行数偏高的语句；② 对候选做 `EXPLAIN ANALYZE`；③ 只在最左前缀与过滤／排序键都匹配时新增；④ DDL 先写迁移脚本并在副本库验证。

### 1.2 慢查询、SQL 优化与冗余索引

**慢查询现状**：`slow_query_log=OFF`、`long_query_time=10`，项目运行至今未开启慢日志，不能凭空声称有慢查询；改用 `performance_schema` 读取真实语句汇总（读数为第 6 轮窗口样本；2026-10-19 复跑确认这两个开关未变）。高频业务语句平均值 **0.125～0.456 ms**；没有任何业务语句接近 10 秒阈值；最慢的常规语句是后台文档列表的 JOIN＋GROUP BY **对照写法**（max 14.1 ms；生产的相关子查询写法为 0.336 ms）。

**SQL 优化实测**：

| 查询 | 当前写法（相关子查询） | JOIN + GROUP BY 改写 | 结论 |
| --- | --- | --- | --- |
| 历史列表（20 行/页） | **0.666 ms** | 7.106 ms | 保留子查询 |
| 后台文档列表（20 行/页） | **0.336 ms** | 4.165 ms | 保留子查询 |

原因：页面只取 20 行，相关子查询最多 20 次索引探测；JOIN+GROUP BY 要先聚合全部证据或文本块再排序。

**其他核查**：

* **禁止 `select *`：已满足**；`api/`、`services/` 中所有语句显式列出字段。
* **事务足够短**：问答落库在单个事务内 UPSERT `question`、`answer`、重建 `answer_evidence`，只涉及本问的 1＋1＋至多 10 行；只读接口不显式开事务。
* **分页有上界**：`PAGE_SIZE_MAX=200`、`PAGE_MAX=100000`；超大页码在参数层以 1002 拒绝，不会拼进 SQL。

**冗余索引（实测，但本轮不删除）**：

| 索引 | 判定依据 | 占用 |
| --- | --- | --- |
| `answer_evidence.idx_ae_answer_id(answer_id)` | 与 PK `(answer_id, chunk_id)` 最左前缀重复；EXPLAIN 从未选中 | 16 KB |
| `document_chunk.idx_chunk_doc_id(doc_id)` | 与 UK `(doc_id, chunk_index)` 最左前缀重复；EXPLAIN 选择 `uk_chunk_doc_index` | 144 KB |

六表 DDL 是唯一规格，验收门禁按该规格核对索引清单；删除会改动冻结结构，风险远大于 160 KB 收益。因此只登记证据，不改 DDL。

**游标分页（方案级，语义已被测试钉住）**：历史列表当前 `LIMIT %s OFFSET %s` 在 30 行规模下亚毫秒；若累积到百万级，按 `(ask_time, question_id)` 做键集分页：

```sql
SELECT q.question_id, a.answer_id, q.question_text, q.ask_time, a.answer_text,
       (SELECT COUNT(*) FROM answer_evidence ae WHERE ae.answer_id = a.answer_id) AS evidence_count
FROM question q JOIN answer a ON a.question_id = q.question_id
WHERE q.session_id = %s
  AND (q.ask_time, q.question_id) < (%s, %s)
ORDER BY q.ask_time DESC, q.question_id DESC
```

### 1.5 缓存体系（进程内已落地＋Redis 方案级）

**已落地：进程内 TTL＋LRU**。`交付物/03-代码/后端/cache.py` 用标准库 `OrderedDict`＋`RLock`，TTL 到期惰性删除、容量满后 LRU 淘汰；`get_or_load()` 在锁内加载，避免同一 key 并发击穿；读写深拷贝，异常不缓存；缓存的是接口 `data` 区块，信封每次重建。

> 作者清单中的 **Caffeine** 属于 Java 生态；本项目后端为 Python，以标准库实现等价的「TTL＋LRU＋加载互斥」，不额外引入 JVM 进程。多级缓存中的 Redis 层见本节末尾的方案。

### 1.11 检索冷启动与常驻检索（方案级）

**判断**：冷启动约 **77%** 消耗在 `torch`／`transformers` 导入（1.1095＋4.2227＝5.3322 s），模型权重加载 0.6822 s，真正的检索计算只有约 0.032 s。因此“优化检索算法”对冷启动没有意义；能缩短的是进程与框架初始化。同进程复用实测：首次构造 `VectorSearcher` 6.1764 s；同一进程第 1 题 31.724 ms；后续 11 题 P50 **17.651 ms**、P95 **19.038 ms**。

**可落地方案**：常驻预热检索进程——后端启动后拉起一个检索子进程并常驻，`/api/qa/ask` 通过管道／本地队列复用。按上表，单题可从约 6.3 s 降到约 18 ms（另加 IPC 开销），是唯一数量级收益。**为什么现在不做**：问答链路目前每次 ask 启动独立子进程，是为了隔离 `检索/config.py` 与 `问答/config.py` 两套同名模块；改成常驻服务需要新的进程协议、超时／重启／并发控制与 E2E 回归，属于架构改动。**第一步**：先做“单进程预热＋健康检查”原型，再用同一组 30 题比对检索结果逐字段一致；之后加超时自动重启与串行队列，最后做多 worker。

**判定不做**：① 避免重复 `from_pretrained`——核查链路只构造一次 `LocalEmbedder`，无重复加载；② `torch.set_num_threads` 调参——检索侧固定 1 线程以保证排序确定性，多线程会改变浮点累加顺序与并列处理的可复现性；③ 导入裁剪——`transformers` 的 4.22 秒主要来自包初始化，惰性导入只是把成本推迟到首次提问；换 ONNX 会改变编码口径与实验读数。

**模块解耦与通信（作者原文三.2）**：

* **依赖注入（装配期注入，不做 DI 容器）**：`main.create_app()` 把限流窗口／阈值、请求体上限等参数注入中间件；图谱后端由 `BACKEND_FACTORIES` 注册表＋`register_backend()` 注入；`TTLCache` 允许注入 `clock`（单测直接拨表）；后台鉴权由 FastAPI `Depends(require_admin)` 注入。组件拿的是**参数／工厂／协议**，不在业务代码里 new 具体实现。

* **事件驱动（边界）**：本机运行时**没有事件总线、消息队列或 pub/sub**。课题名称中的“事件驱动”指**以 `Event` 节点为中心的知识图谱数据模型**（事件属性、事件—主体／机构／政策关系、证据回链），不是进程内事件驱动架构；运行时仍是同步请求—响应＋离线批处理。若将来要引入运行时事件驱动（任务状态机、MQ 削峰），落点与第一步见 §3.5 与 §3.6，不在单机进程里模拟。

### 3.4 集群化与高可用（方案级）

**方案**：

1. **服务无状态化（边界已写清）**：后端进程不持有**会话状态**——`session_id` 由前端 `crypto.randomUUID()` 生成并随请求携带，服务端只把问答记录落 MySQL；因此除 `qa_runs` 运行留痕目录与进程内缓存／限流计数外，服务本身无会话状态，可直接横向复制。`qa_runs` 当前是本机临时目录，多实例前需改为共享存储或每实例独立目录；进程内缓存与限流计数也需外置（见下条）。
2. **限流与缓存外置（Redis）**：当前限流计数、市场数据缓存为进程内；多实例下改用 Redis 滑动窗口／TTL 键，保证跨实例一致；生产形态用 **Redis 主从／Cluster**，本机未安装（见 §3.6）。
3. **数据库高可用**：MySQL 主从＋只读副本承担历史与元数据查询，写路径保留主库；图谱与向量索引按版本化快照分发到各实例，升级时先构建新版本再原子切换。
4. **健康检查与滚动升级**：`/api/health` 已区分 MySQL／Neo4j／向量索引／模型配置四项；负载均衡按该探针摘除不健康实例，滚动升级时保证至少一个实例可用。
5. **熔断**：外部实时源可在现有降级之上加“连续失败 N 次 → 冷却 M 秒”的轻量熔断；本机只有单用户演示流量，当前以“一次重试＋立即降级”为足够。

**为什么现在不做**：本机为单实例演示环境，没有第二台应用节点、Redis 或数据库从库；按“不伪装实现”的既定纪律，集群、分布式限流、跨实例缓存与熔断器均只给方案，不在单机进程里模拟。

**要做的话第一步**：先把后端无状态化（共享 `qa_runs` 或每实例独立目录）并在单机起两个 worker 做会话与限流回归；再引入 Redis 做限流／缓存外置；最后接 MySQL 从库与负载均衡。

### 3.5 异步任务、IO 与并发（方案级）

* **文件 IO**：数据准备脚本已用 `jsonl` 流式读写与原子替换；上传解析类任务应改为分块读取（固定缓冲），禁止一次性 `read()` 超大文件。冷文件／原始公告可迁对象存储，本机不引入对象存储，仅在方案中保留。
* **网络连接池**：MySQL 已用进程内单连接＋线程锁；生产应改为连接池（如 DBUtils／SQLAlchemy Pool）并设置连接／读取超时。Neo4j 驱动自带连接池，当前每次请求建／关会话，高并发下应复用 driver。LLM 的 `urllib` 无连接复用，生产可改 `httpx`／`requests.Session`。
* **指数退避重试**：只对网络错误、连接超时、HTTP 5xx 重试，最多 2 次，基础 0.5 s、指数 ×2、加 ±20% 抖动；HTTP 4xx 与“正文为空”不盲目重试。
* **并发模型**：IO 密集（数据库、LLM）用线程池／协程；CPU 密集（BGE 编码、FAISS）用独立进程池并限制并发。后端问答链路已有 `_ASK_LOCK` 串行化，避免 CPU 打满；生产应按 CPU 核数配置工作进程与并发上限，并区分读接口与问答接口的线程池。
* **异步任务队列（方案级）**：文档解析、入库、图谱更新、向量化属于长任务，应入 MQ（RabbitMQ／Kafka 或轻量 Redis Stream）削峰，接口只返回任务号；问答接口不阻塞等待。**为什么现在不做**：本机无 MQ，引入属于新增服务。**第一步**：定义任务表与状态机 → 生产者只写任务 → 消费者幂等处理（以 `doc_id`／内容哈希去重）→ 失败重试与死信 → 前端轮询／SSE 展示进度。

> **三件套**：实现位置 `交付物/03-代码/后端/db.py`、`交付物/03-代码/后端/services/qa_service.py`；证据：本节；复跑：—

### 4.2 重复提问的幂等复用

**口径**：同一 `(session_id, question_text)` 已有非空回答时，`/api/qa/ask` 直接复用最近一条，**不再调用模型、不新增 question／answer／evidence 行**；响应带 `reused=true` 与 `notice`。只在本会话内复用；其他会话的相同问题不会被读到。`/api/admin/experiment/ask` 显式传 `reuse=False`，每次都跑新链路，保证受控实验的可比性。

**前端**：命中复用时带 `?reused=1` 跳到答案页，页头如实说明“已问过，复用的是当时落库的那一份”。

**实测**：对 S-001 的 `question_id=30` 原样重问 → 耗时 **0.02 s**、`reused=true`、返回同一 `question_id=30／answer_id=30`、证据 10 条；库计数保持 **30／30／293** 不变。

**边界**：题干内部的空白差异不会被归一（只有首尾空白与 `\t\r\n` 折叠），因此“同一语义、不同空格”会被视为新问题；更激进的语义去重需要另做归一化键，本轮不做（避免把不同问题误判为同一问）。

> **三件套**：实现位置 `交付物/03-代码/后端/services/qa_service.py`；证据 `交付物/03-代码/测试/test_g_backend_api.py`；复跑 `python -m pytest 交付物/03-代码/测试/test_g_backend_api.py -q`。

### 4.3 会话管理与单轮边界

**已落地**：

* 会话号：浏览器首次访问生成 UUID，存 `localStorage['qa-console-session-id']`；所有历史请求自动带 `session_id`（也支持 `X-Session-Id` 头）。
* 持久化：历史记录落 MySQL 三表，刷新／重启浏览器后仍可回看本会话记录。
* 切换与重置：历史页展示完整当前会话号，新增“重置会话”按钮。重置只生成新 UUID、清空前端只读缓存，**不删除任何服务端记录**；确认框明确写出“旧记录仍在库中，只是本页不再显示”。
* 隔离实测：S-001 列表 30 条；其他会话列表 0 条；S-001 可读 `question_id=1`；其他会话读同一条 → HTTP 404／`code=2001`；缺 `session_id` → HTTP 400／`code=1002`。
* 诚实性修正：历史页空态原写“在地址栏改 `/history?session_id=S-001`”，但该页从不读取地址栏会话参数，照做无效；已删除这句，改为如实说明会话隔离与重置的影响。

**单轮边界（不做多轮）**：第一版问答契约是单轮：请求体只有 `question + session_id`，会话号用于留痕与隔离，不参与 Prompt 组装；链路不读取历史轮次。若后续要做多轮，方案是：在 `answer.py` 装配 Prompt 时按 `session_id` 取最近 N 轮（问题＋答案摘要），设独立 token 预算并从证据预算中扣减；同时在 `question` 表增加 `turn_index`／`parent_question_id`。这会改变 Prompt 版本与可复现口径，需与论文／实验冻结口径同步，故不在本轮擅自实现。

### 6.2 Web 安全

* **SQL 注入：不成立**。全库检索未发现把用户输入拼进 SQL 的 f-string；动态值一律 `%s` 参数化，表名／列名只走固定白名单辅助函数（如 `_col()`）。实测注入串 `' OR '1'='1`、`S-001' UNION SELECT …--`、`1 OR 1=1` 分别返回 0 条／0 条／1002，未出现库名、表名或异常栈。`LIKE` 的 `%`／`_` 通配符仍按普通字符语义工作（搜索 `%` 会匹配较多实体），这是查询语义而非注入，登记为可接受的次要行为。
* **XSS：当前数据下不可利用；图谱 SVG 仍有未转义插值（如实登记）**。`AnswerSections.vue` 先对正文做 `&<>` 转义，再把 `[证据N]` 替换成固定锚点；其他页面文本走 Vue 插值自动转义；外部链接固定 `target="_blank" rel="noopener"`。**但 `lib/graph.js` 的 `mountGraph` 用 `innerHTML` 拼接 SVG，`n.label`、`n.sub`、`s.title`、`s.source`、`s.url` 等动态值只有部分经过 `esc()`**。2026-10-19 只读复核：3607 个图谱节点名称中 `<`／`>` **0**、`"` **1**、`&` **2**（会破坏属性结构，但无脚本执行）；709 条文档标题无 HTML 标记，709 条 URL 全部 http(s)、无 `javascript:`；且系统无上传端点、图谱由离线精选流水线生成。故当前**不可利用**，作为潜在存储型 XSS 登记 §6.7；修复方向：所有 HTML 文本／属性 sink 统一转义或改用 DOM API／`textContent`，并补 DOM 级测试。
* **CSRF：不适用**。系统不使用 Cookie 会话：会话号是前端 localStorage 里的随机 UUID，管理端用自定义请求头 `X-Admin-Token`（浏览器不会自动附带）；CORS 只允许 `http://localhost:5173` 与 `http://127.0.0.1:5173`，实测其他 Origin 无 `Access-Control-Allow-Origin`。
* **基础加固**：响应头 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` 实测均存在；请求体上限 64 KiB（70 KiB 请求被 1001 拒，不进入业务逻辑）；每请求带 `X-Request-Id`。

### 6.5 文件上传（不适用）

**本系统没有文件上传端点**：文档导入走 `POST /api/admin/documents` 的 JSON 正文（`title/content/source/...`），不是 multipart 文件上传；因此“上传漏洞”当前不适用。本轮**不虚构**一个上传功能。

### 7.1 配置分层

配置文件仍以 `交付物/03-代码/后端/config.local.json` 为准，加载顺序固定为：

```text
① 基配置        ASHARE_CONFIG_FILE（缺省 config.local.json）
② 环境叠加文件  config.<ASHARE_ENV>.local.json（存在才叠加；与基配置同文件则跳过）

```

### 8.2 指标

**决策：挂在 `/api/health`，不新增 `/api/metrics`**。新增路由会改变 OpenAPI 路径／操作数，需同步验收脚本的登记；本项目规模与单进程架构不需要独立指标服务。

```json
GET /api/health
{
  "status": "ok",
  "mysql": {...}, "neo4j": {...}, "vector_index": {...}, "model_config": {...},
  "metrics": {
    "window_seconds": 60, "history_seconds": 300, "uptime_seconds": 83.6,
    "requests": {"total": 3, "window": 1, "qps": 0.02, "errors_window": 0, "error_rate": 0.0},
    "routes": {
      "POST /api/qa/ask": {"count_window": 1, "qps": 0.02, "errors_window": 0,
                           "error_rate": 0.0, "avg_ms": 10758.3, "p50_ms": 10758.3,
                           "p95_ms": 10758.3, "p99_ms": 10758.3}
    },
    "qa": {"success": 1, "failure": 0, "success_rate": 1.0},
    "retrieval": {"vector_searches": 1, "graph_queries": 1, "evidence_total": 10,
                  "empty_results": 0, "reused_answers": 0, "evidence_avg": 10.0,
                  "kb_hit_rate": 1.0},
    "llm": {"calls": 1, "failures": 0, "failure_rate": 0.0,
            "total_seconds": 3.068, "avg_seconds": 3.068},
    "rate_limit": {"hits": 0}
  }
}
```

* `status` **仍只由四项依赖探针决定**；`metrics` 只是摘要，不参与就绪判定；
* 指标在进程内、线程安全（`deque`＋锁），重启清零；单进程口径，多 worker 不聚合；
* 每路由最多 2000 个样本、最多 128 个路由键，超出归入 `__other__`，防止探测制造高基数；
* `metrics` 快照异常时只返回 `{"available": false, "info": "异常类型"}`，不返回堆栈或凭据。

指标口径（覆盖作者原文八.2 的全部点名项）：

| 作者要求 | 落点 | 定义 |
| --- | --- | --- |
| QPS | `requests.qps`、`routes[*].qps` | 最近 60 s 请求数 ÷ 60 |
| 平均 | `routes[*].avg_ms` | 最近 300 s 样本的算术平均 |
| P95／P99 | `routes[*].p95_ms`／`p99_ms` | 最近 300 s 样本的最近邻百分位（另给 P50） |
| 错误率 | `requests.error_rate`、`routes[*].error_rate` | HTTP ≥ 400 占 60 s 窗口请求数 |
| RAG 召回数 | `retrieval.evidence_total`／`evidence_avg` | 非复用问答链路累计证据条数／平均每条链路条数 |
| LLM 失败率 | `llm.failure_rate`（＋`calls`／`failures`／`total_seconds`／`avg_seconds`） | `answer_trace.jsonl` 的 attempts：请求失败或返回空正文计失败；重试逐次计数 |
| 知识库命中率 | `retrieval.kb_hit_rate` | 非复用链路中「有可引用证据」的次数 ÷ 非复用链路次数 |

**边界**：全部为进程内整数／浮点计数，不保存问题、答案或 Prompt 文本；重启清零、多 worker 不聚合。LLM 失败率只统计已产出 `answer_trace.jsonl` 的尝试；链路在产出 trace 之前失败的请求，仍由 `qa.failure` 与 HTTP 错误率覆盖。2026-10-19 第 8 轮复验后补齐了平均、LLM 失败率与知识库命中率三项聚合，接口形状仍为 `/api/health.metrics` 的**新增字段**，不新增路由。

**实测**：真实请求后 60 s 窗口 `qa.success=1`、`POST /api/qa/ask` 的 P50／P95／P99 均为 10758.3 ms、错误率 0、限流命中 0；健康路由样本 P50 97.5 ms、P95 497.2 ms（含冷启动那次）。与访问日志的 10758.3 ms 一致，说明指标记录与日志计时同源。

### 8.3 一次真实请求的全链路取证

用一个新会话对题库第 1 题发起真实 `POST /api/qa/ask`（保证不命中复用），后端以 `ASHARE_LOG_PATH` 落盘；同时用同一问题、同一 C 组、同一冻结参数直接运行 `run_query.py`，取得检索侧分阶段耗时。两次运行是不同进程，故读数按“后端日志＋`answer_trace.jsonl`＋独立检索复跑”三处交叉说明，**不伪称同一次采样**。

**追踪边界（如实说明）**：本机**没有 OpenTelemetry／Jaeger／SkyWalking 等跨服务追踪系统**，也没有跨进程 trace context 传播。当前实现是**单进程内的链路串联**：同一个 `X-Request-Id` 由请求 ID 中间件写入响应头与每行日志，问答服务再把 `out_dir` 传给检索子进程，`answer_trace.jsonl` 的 `attempts` 提供每次 LLM 调用的耗时与状态；把「请求 → 检索 → 图谱 → LLM」串起来靠的是 **request_id ＋ out_dir ＋ answer_trace 三者的关联**，不是分布式 span／traceId 传播。跨服务追踪作为方案级目标保留（需引入 OpenTelemetry SDK 与 collector），不在单进程演示版伪实现。

### 10.1 输入格式兼容

| 输入形态 | 处理函数 | 结论 |

**现状**：所有接口路径为 `/api/<资源>`，**无版本号**；成功 `{data, meta}`，错误固定 `{code, message}`（唯一例外：2003 额外带 `retained_for_history`）；OpenAPI 3.1.0 由 FastAPI 自动生成，`/openapi.json`、`/docs`、`/redoc` 默认可用。当前 **31 路径／34 操作**，`components.schemas` 只有 `HTTPValidationError`／`ValidationError`，错误响应使用内联 schema。

**2026-10-19 复验（现状核对）**：`/openapi.json` 实测 **OpenAPI 3.1.0**、`info.version=stage9-t4-skeleton`、**31 路径／34 操作／2 schema／6 属性／170 条错误样例**；`nginx.conf` 只有 `location /api/`，后端无 `/api/v1` 路由，OpenAPI 路径中也没有 v1。因此**版本化仍是方案级、未实施**；当前“旧接口兼容”体现为唯一现行前缀 `/api/*` 未被改动，未来落地 v1 时按下方方案保留 `/api/*` 作为别名。

**版本化推荐方案（方案级）**：Nginx 层路径前缀重写——对外提供 `/api/v1/*`，内部仍保持 `/api/*`：

```nginx
location /api/v1/ {
    rewrite ^/api/v1/(.*)$ /api/$1 break;
    proxy_pass http://backend:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Request-Id $request_id;
    proxy_read_timeout 320s;
    proxy_send_timeout 320s;
}
```

要点：`rewrite ... break` 只改内部 URI；`/api/*` 旧路径继续保留为 v1 别名；前端当前仍调 `/api/*`，无需改动；OpenAPI 可另起一份“对外契约”，不需要改后端 `openapi.json`；未来 v2 新增 `location /api/v2/`，v1 保持冻结。

**为什么现在不做**：当前无外部客户端，改路径会增加联调面；任务口径要求“只写方案，不真的改接口路径”。**第一步**：在 Nginx 加 rewrite 并保留旧路径，做双路径逐字节回归。

**版本生命周期与弃用**：新增兼容字段／接口 → MINOR；字段语义变更／删除、错误码语义变更 → MAJOR，新前缀，旧版本保留至少一个发布周期；弃用响应头 `Deprecation: true`＋`Sunset: <HTTP-date>`；K／N／预算／g／Prompt 版本／模型版本变更属 MAJOR，禁止同版本内静默切换。

**兼容性测试建议**：① 对 `/openapi.json` 做快照，检查 path／method／必填字段／错误码表变化；② 同一请求分别打 `/api/*` 与 `/api/v1/*`，断言响应 JSON 逐位相等；③ 前端 `npm run test`＋构建、后端路由测试；④ 弃用演练。

### 11.1 日志轮转

`errors.setup_logging()` **始终**挂 `StreamHandler(stderr)`；仅当 `config.LOG_PATH` 有值（`config.local.json` 的 `log_path` 或环境变量 `ASHARE_LOG_PATH`）时，再追加一个 `logging.handlers.RotatingFileHandler`：单文件 **10 MiB**、保留 **5** 个历史文件、UTF-8、`delay=True`。目录不存在会自动创建；目录不可写时只记 WARNING、服务照常启动。**不配置时一个文件 handler 都不挂**，行为与引入该能力之前完全一致。

也就是说，**日志轮转默认关闭**：本机 `config.LOG_PATH=None`（`config.local.json` 无 `log_path`、`ASHARE_LOG_PATH` 未设），运行态只出 stderr，不创建任何日志文件；要落盘轮转必须显式配置。轮转**仅按大小**触发（`maxBytes=10 MiB`）并按 `backupCount=5` 清理最旧文件，**未实现按时间/日期切割**（作者原文的“按大小/时间”取“按大小”这一支）。

**验证**：`交付物/03-代码/测试/test_m_log_rotation.py`（4 个用例，全部离线写到 `tmp_path`）：

| 用例 | 断言 |
| --- | --- |
| 不设 `LOG_PATH` | 仅有 1 个 stderr handler，无 FileHandler，不创建任何文件 |
| 设 `LOG_PATH` | 目录自动创建、中文日志 UTF-8 写入、`maxBytes`／`backupCount` 取自 `LOG_ROTATION` |
| 轮转生效 | `max_bytes=512`、`backup_count=2` 连续写入 40 行 → 出现 `.1`／`.2`，不超过 2 个历史文件，`.3` 不存在 |
| 路径不可用 | 父路径是普通文件 → 仅记 WARNING，不挂文件 handler、不抛异常 |

容器形态下 `docker-compose.yml` 已把 `ASHARE_LOG_PATH` 指到 `/app/logs/backend.log`，并由 `backend-logs` 命名卷承载，容器重建后日志不丢。

## 十二、算法

### 12.1 检索链路总览（已冻结）

```
问题
  ├─ 向量通道：BAAI/bge-small-zh-v1.5 → FAISS → Top-N（N=20）
  └─ 图谱通道：实体解析 → 1/2 跳子图 → 事件证据块（G1～G7）
        ↓
     并集去重（merge_candidates；向量侧按 vector_rank，图谱侧按路径顺序）
        ↓
     时间过滤（apply_time_filter）
        ↓
     Token 预算裁剪（trim_to_budget，预算 3600）
        ↓
     Top-K = 10（keep_top_k）
        ↓
     证据排序（order_evidence，E 组启用）
```

对应实现：`交付物/03-代码/检索/pipeline.py` 的 `collect_vector_candidates()`、`collect_graph_candidates()`、`merge_candidates()`、`apply_time_filter()`、`trim_to_budget()`、`keep_top_k()`、`order_evidence()`；向量侧 `交付物/03-代码/检索/vector_search.py` 的 `LocalEmbedder`、`VectorSearcher.search()`。组 C：`graph_depth=2`、`time_filter=False`、`evidence_sort=False`；最终证据顺序固定，路径／事件三元组计入预算但不计入 K。

**实测短板**：核心集 108 题 Recall@K A 组（纯向量）0.7761、C 组（+2 跳图谱）0.8730；Complete Evidence Recall@K 30 题预实验五组均为 0.5667；MRR 核心集 A 0.5852／C 0.6076。精确串匹配（股票代码、公司简称、公告标题、数字指标）目前只能靠稠密向量隐式表达。这构成 §12.2 的动机。

### 12.2 BM25、字符 n-gram 与 RRF

**定位与边界**：BM25／字符 n-gram 是**工程增强**，不是论文实验的一部分——① 不进入 A～E 实验组，不改变任何既有实验读数；② 不修改 `检索/`／`问答/`／`数据准备/` 的既有文件，也不重跑论文实验；③ 不调用大模型、不联网，纯本地算法；关键词结果**不是证据链的一部分**。

**实现**：

| 层 | 落点 | 行为 |
| --- | --- | --- |
| 算法 | `交付物/03-代码/增强/lexical_search.py` | 中文 1～3 字符 n-gram＋标准 BM25（k1=1.5、b=0.75），纯标准库 |
| 服务 | `交付物/03-代码/后端/services/hybrid_search.py` | 只读 `chunks.jsonl`；启动不建索引，首次调用惰性构建一次（进程内单例、双检锁）；构建耗时记日志；构建／查询失败降级为空结果，接口不 500 |
| 接口 | `GET /api/search/keywords?q=<问题>&k=5` | `k` 缺省 5、上限 20；`q` 必填并复用 `params.validate_question`；返回 `{items, total, took_ms, index_ready}`，每条 `{chunk_id, doc_id, title, snippet, score}`，`snippet` 截断约 200 字 |
| 空结果增强 | `POST /api/qa/ask` 的 `empty=true` 分支 | 追加 `related_chunks`（≤3 条）与 `engineering_enhancement=true`；前端渲染“关键词相关原文（工程增强，非正式证据）”，明确标注不属于证据链、不作为答案依据；为空时保持原文案不变 |

**线上读数（`chunks.jsonl` 5018 块）**：posting **2,287,765**、avgdl **698.71**、首次调用（含模块加载与建索引）约 **1.24 s**；建成后单次 Top-5 查询 **P50 约 10.8 ms**（20 次采样）。PE-01 的 Top-5 为 `1001000 / 1001001(gold) / 1048011 / 1088015 / 1120015`，与离线对照脚本一致。

**离线对照（30 题，K=10）**：

| 通道 | Recall@10 | MRR | Complete@10 | Hit@1 | Hit@10 |
| --- | --- | --- | --- | --- | --- |
| 向量（现有基线） | 0.6781 | 0.6589 | 0.5667 | 0.5667 | 0.8333 |
| BM25（字符 n-gram） | 0.6448 | **0.6811** | 0.5333 | 0.5667 | 0.8333 |
| RRF（向量＋BM25） | **0.7179** | **0.6828** | **0.6000** | 0.5667 | **0.9000** |

RRF 相对向量：Recall@10 **+3.98 个百分点**、Complete@10 **+3.33 个百分点**、MRR **+2.39 个百分点**、Hit@10 **+6.67 个百分点**；Hit@1 持平。BM25 单独使用 Recall 低 3.33 个百分点，但 MRR 高 2.22 个百分点，说明它“排序头部更准、覆盖率不足”，不能替代向量通道。

**正式集复验（120 题，K=10）**：

| 通道 | R@10 | MRR | Complete@10 | Hit@1 | Hit@10 |
| --- | --- | --- | --- | --- | --- |
| 向量（现有基线） | 0.7972 | 0.5961 | 0.7417 | 0.4667 | 0.8500 |
| BM25（字符 n-gram） | **0.8875** | **0.7533** | **0.8500** | **0.6583** | **0.9250** |
| RRF（向量＋BM25，诊断） | 0.8764 | 0.6967 | 0.8333 | 0.5667 | 0.9167 |

**如实结论**：正式题大量复用公告标题与精确数字／专名，天然有利于字符匹配；BM25 四项指标全面高于独立向量 Top-10，但**不得外推为 A～E 组读数，也不据此默认启用 BM25**。RRF 在正式集上没有超过 BM25 单路（R@10 −1.11 pp），只超过向量；两套题集方向不一致，说明融合收益对题集构成敏感。若要把词汇通道或 RRF 转为默认，必须按预登记实验组（F1＝C＋词汇、F2＝C＋RRF）跑 A～E 全套并做题型拆分与显著性检验。

**为什么现在不做默认接入**：题集复用标题／精确数字，收益不可外推；改链路会牵动冻结实验口径与答案契约。**第一步**：以 F1／F2 预登记实验组在正式集同口径复跑，通过 Recall +2.0 pp、Complete 严格大于 C、MRR 不低于 C、端到端 P95 增量 ≤1.5 s、AA／Faithfulness 不下降的门槛后再评估。

### 12.3 可插拔 Rerank

`交付物/03-代码/增强/reranker.py` 提供 `rerank_records(records, question, reranker=None)` 与 `RerankedRunner`：

* 默认 `None`：原样返回同一对象，不改变候选集、顺序与字段；
* 自定义 reranker：必须返回原集合的**排列**；`_check_permutation` 校验长度、元素身份与重复，不合法即抛错，绝不静默兜底；
* 只重排、不增删：`rerank_result` 保持结果信封的其余字段不变；
* 以包装器形式接在 `pipeline` 输出之后，只改最终证据顺序，不改变 Recall@K（MRR 可能变化）；`pipeline.py` 未改动。

**接入状态（2026-10-19 复验）**：接口已就绪但**未接入默认检索链路**——`检索/pipeline.py` 不 import `增强/reranker.py`，A～E 组与线上问答输出不受影响；默认 `None` 时原样返回同一对象，自定义重排必须返回原集合的排列，非法即抛错，绝不静默兜底。

**Cross-Encoder 重排（方案级）**：候选为融合后 Top-M（建议 M=50），推荐 `BAAI/bge-reranker-base`（CPU 上 50 对约 0.3～1.0 s，估）；延迟预算端到端增量 ≤1 s，超过 1.5 s 则只在离线实验启用；失败回退为原序。**为什么现在不做**：本机无该模型，且真正的候选集重排必须作为新实验组在“④ 保留 K”之前引入并重跑 A～E，不能走默认链路。**第一步**：在离线环境用 30 题开发集测增量延迟与 MRR，再决定是否进入预登记实验组。

### 12.4 装配账目守卫与答案机检门禁

**装配账目守卫**（`交付物/03-代码/问答/assemble.py` 的 `assemble_case()`）：现场重算 `text_tokens = Σ(每条 evidence.token_count)`，再合成 `total = text + path_tokens + event_triple_tokens`，断言其等于上游 trace 的 `total_tokens`——不一致直接 `SystemExit`，不静默按任一值继续。其他自检：证据数 ≤ K；证据顺序必须等于 `final_evidence_chunk_ids`；总 token 不得超 3600；trace 的 K/N 必须等于配置的 10/20；图谱载荷原样透传；语料查找必须成功。返回 `checks` 六项，供上游汇总。

**答案机检门禁**（`交付物/03-代码/问答/answer.py::gate`）：11 个失败项，全部通过 `passed` 才为真——引用越界、缺少引用、日期不可回溯、图谱段与 `graph_used` 不一致、正文泄漏“无图谱”系统标记、正文泄漏系统段小标题、命中禁词、证据回链不完整、空答案、数据截至／判定区间段缺失或不匹配、开放式题缺少固定分析标注（无开放式题时记不适用并通过）。作用域：引用／泄漏类只看模型正文；日期与禁词看答案全文；开放式标注按题集 `task_type` 判定，不靠关键词猜。
