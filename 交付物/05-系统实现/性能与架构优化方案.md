## 1. MySQL 优化（附录一.1）

### 1.1 索引设计与索引失效场景

**问题.** 需要确认六表的主键、唯一键、联合索引是否覆盖真实查询；是否存在函数运算、
隐式转换、前缀 `%` 等导致索引失效的写法。

**现状（实测）.** 六表共 14 个普通二级索引（DDL 注释口径），另有各表主键、唯一键：

| 表 | 主键／唯一键 | 普通索引（与查询相关的） |
| --- | --- | --- |
| `question` | PK `question_id` | `idx_q_session_time(session_id, ask_time)`、`idx_q_task_type` 等 |
| `answer` | PK `answer_id` | `idx_a_question_id(question_id)`、`idx_a_create_time` |
| `answer_evidence` | PK `(answer_id, chunk_id)` | `idx_ae_answer_id`、`idx_ae_doc_id`、`idx_ae_evidence_type`、FK `chunk_id` |
| `document` | PK `doc_id` | `idx_doc_publish_time`、`idx_doc_ingest_time`、`idx_doc_category` |
| `document_chunk` | PK `chunk_id`；UK `(doc_id, chunk_index)`、UK `vector_id` | `idx_chunk_doc_id` |
| `user` | PK `user_id`；UK `username` | — |

EXPLAIN 实测（`ashare_qa` 库）：

| 查询 | 选择索引 | 观察 |
| --- | --- | --- |
| 历史列表（会话 + 时间倒序 + LIMIT/OFFSET） | `q`: `idx_q_session_time`；`a`: `idx_a_question_id` | `Backward index scan; Using index`，无 filesort |
| 历史总数 COUNT | 同上 | `Using index` |
| 后台文档列表（发布时间倒序） | `idx_doc_publish_time` | `Backward index scan; Using index` |
| 按 `doc_id` 取块 + `chunk_index` 排序 | `uk_chunk_doc_index` | `Using index`，无 filesort |
| 按 `answer_id` 取证据 | `PRIMARY` | 联合主键前缀命中；仅 10 行做 rank filesort |

失效场景核查：

* 后端 SQL 中**没有 `LIKE`，更没有 `LIKE '%x%'`**（全仓 `api/`、`services/` 检索确认）；
  模糊匹配只出现在 Neo4j 的实体名检索里，与 MySQL 索引无关。
* WHERE 子句没有对索引列做函数运算或表达式运算；时间比较在 SQL 中直接比较列本身。
* 参数由 PyMySQL 绑定为 Python `int`，不会把 BIGINT 列与字符串比较，无隐式转换。
* `document_chunk` 的 `(doc_id, chunk_index)` 联合唯一键同时覆盖「按文档取块」和
  「按块序号排序」两个用途。

**结论.** 当前查询集合下不需要新增索引；新增索引反而会拖慢写入。索引设计维持六表 DDL。

**若后续数据量增长再评估的实施步骤.**

1. 用 `performance_schema.events_statements_summary_by_digest` 找出 `SUM_NO_INDEX_USED>0`
   或 `SUM_ROWS_EXAMINED/COUNT_STAR` 偏高的语句；
2. 对候选语句执行 `EXPLAIN ANALYZE`，确认是全表扫描而非统计信息滞后；
3. 只在联合索引最左前缀与过滤条件、排序键都匹配时才新增；新增后用同一组语句做前后
   对比，并观察写入延迟；
4. 所有 DDL 变更先写迁移脚本并在副本库验证，再落到主库。

### 1.2 慢查询分析与冗余索引清理

**问题.** 需要以实测数据判断是否存在慢查询；识别长期不用的冗余索引。

**慢查询实测.**

* `slow_query_log = OFF`、`long_query_time = 10.000000`、`log_output = FILE`；
  项目运行至今未开启慢日志，不能凭空声称有慢查询。
* `performance_schema = ON`。按 `SUM_TIMER_WAIT` 排序的前列语句（`ashare_qa`）：

| 语句（摘要） | 次数 | 平均耗时 | 扫描行数 |
| --- | --- | --- | --- |
| 历史列表（JOIN + 证据数相关子查询） | 53 | 0.469 ms | 12 402（累计） |
| 后台文档列表（块数相关子查询） | 53 | 0.155 ms | 7 950（累计） |
| 历史总数 COUNT | 53 | 0.121 ms | 3 180（累计） |
| 证据明细（`answer_evidence` JOIN `document`） | 53 | 0.119 ms | 1 590（累计） |
| 相邻文本块（`doc_id` + `chunk_index BETWEEN`） | 53 | 0.114 ms | 53（累计） |

  另有 1 条一次性语句 `SELECT question_id FROM question WHERE question_id > ?` 记录 11.33 ms，
  仅扫描 1 行，属于一次性的冷启动/探针语句，不在业务热路径。

**冗余索引（实测，但本轮不删除）.**

| 索引 | 判定依据 | 占用 |
| --- | --- | --- |
| `answer_evidence.idx_ae_answer_id(answer_id)` | 与 PK `(answer_id, chunk_id)` 的最左前缀完全重复；EXPLAIN 选择 `PRIMARY`，该索引从未被选中 | 16 KB |
| `document_chunk.idx_chunk_doc_id(doc_id)` | 与 UK `(doc_id, chunk_index)` 的最左前缀重复；EXPLAIN 选择 `uk_chunk_doc_index` | 144 KB |

**本机为何不直接删除.** 六表 DDL 是唯一规格（《10》表 4-6 与 4.4.2 逐字对齐），
验收门禁按该规格核对索引清单；删除会改动冻结结构，风险远大于 160 KB 的收益。
因此本轮只登记证据，不改 DDL。

**若实施的具体步骤.**

1. 在生产副本库执行 `ALTER TABLE ... DROP INDEX ...`，观察 1 周；
2. 对比 `SHOW INDEX`、慢查询、写吞吐；确认无回退后进入正式迁移脚本；
3. 回退语句：`ALTER TABLE answer_evidence ADD INDEX idx_ae_answer_id(answer_id);`
   `ALTER TABLE document_chunk ADD INDEX idx_chunk_doc_id(doc_id);`
4. 生产环境建议：`SET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=0.2;
   SET GLOBAL log_output='FILE';`，定期用 `mysqldumpslow`／`pt-query-digest` 汇总，
   并在业务低峰清理长期无 `COUNT_STAR` 的索引。

### 1.3 SQL 优化（禁 `select *`、子查询、事务、分页）

**问题.** 检查是否一次拉全表、是否用嵌套子查询、事务是否过长、分页是否有上界。

**实测与结论.**

1. **禁止 `select *`：已满足。** 全仓检索 `api/`、`services/`，没有任何 `SELECT *`；
   所有语句显式列出字段。
2. **相关子查询 vs JOIN 改写（实测对比，保留子查询）：**

   | 查询 | 当前写法（相关子查询） | JOIN + GROUP BY 改写 | 载荷是否一致 |
   | --- | --- | --- | --- |
   | 历史列表（20 行/页） | **0.666 ms** | 7.106 ms | 一致 |
   | 后台文档列表（20 行/页） | **0.336 ms** | 4.165 ms | 一致 |

   原因：页面只取 20 行，相关子查询最多 20 次主键/二级索引探测；JOIN+GROUP BY 要先聚合
   全部 293 条证据或 5018 个文本块再排序，当前规模下反而慢一个数量级。故**不改写**。
   当单会话历史达到数十万行、聚合成本被摊薄后可再评估。
3. **事务：已足够短。** 问答落库在单个事务内依次 UPSERT `question`、`answer`、
   重建 `answer_evidence`，只涉及本问的 1 行 + 1 行 + 至多 10 行，无跨请求长事务；
   只读接口不显式开事务。
4. **分页上界：已具备。** `history.py` 的 `PAGE_SIZE_MAX=200`、`PAGE_MAX=100000`；
   图谱接口复用同一上界（`api/graph.py` 的 `PAGE_SIZE_MAX=200`）。超大页码在参数层
   以 1002 拒绝，不会拼进 SQL。
5. **游标分页（大偏移方案，未实施）：** 历史列表当前 `LIMIT %s OFFSET %s` 在 30 行规模
   下亚毫秒；若历史累积到百万级，OFFSET 会随页码线性退化。方案是按
   `(ask_time, question_id)` 做键集分页：

   ```sql
   SELECT q.question_id, a.answer_id, q.question_text, q.ask_time, a.answer_text,
          (SELECT COUNT(*) FROM answer_evidence ae WHERE ae.answer_id = a.answer_id)
            AS evidence_count
   FROM question q JOIN answer a ON a.question_id = q.question_id
   WHERE q.session_id = %s
     AND (q.ask_time, q.question_id) < (%s, %s)   -- 上一页最后一行；首页传 (NOW(), MAX)
   ORDER BY q.ask_time DESC, q.question_id DESC
   LIMIT %s;
   ```

   接口新增 `cursor`（base64 编码的 `ask_time|question_id`）并保留 `page` 兼容；
   现有 `idx_q_session_time(session_id, ask_time)` 可直接支撑，无需新索引。

### 1.4 表结构优化与冷热分离

**问题.** 字段类型是否合理、是否存在可拆分的大表、历史财经事件如何归档。

**字段类型审计（实测取值上限）.**

| 字段 | 当前类型 | 实测最大值 | 评估 |
| --- | --- | --- | --- |
| `question.question_text` | TEXT | 82 字 | 可收窄为 `VARCHAR(1024)`（冻结结构，未改） |
| `document.content` | LONGTEXT | 49 852 字 | 合理，需容纳长公告 |
| `answer.answer_text` | LONGTEXT | 4 256 字 | 合理；`max_tokens=16384` 下仍有增长空间 |
| `document_chunk.content` | TEXT | 512 字 | 可收窄为 `VARCHAR(2048)`（冻结结构，未改） |
| 编号／外键 | BIGINT | — | 合理 |
| `gold_hop_depth`／`time_constraint`／`is_graph_extended` | TINYINT | 0/1/2 | 用 TINYINT 正确，无需 INT |
| `question.session_id` | CHAR(36) | UUID | 定长正确 |
| `answer.graph_path` | JSON | — | 无需独立路径表 |

**空间现状（实测）.** `document` 9.5 MB、`document_chunk` 7.1 MB、`answer` 1.3 MB、
`answer_evidence` 0.1 MB，合计约 18 MB；709 篇文档、5018 块、30 条问答。当前**远未达到**
需要拆表或归档的规模，故本机不建归档表。

**冷热分离方案（历史财经事件归档）.**

* 热表保留最近 12 个月或最近 1 万条问答；冷数据迁到同构 `*_archive` 表
  （`question_archive`／`answer_archive`／`answer_evidence_archive`），归档表**不建外键**，
  只保留主键与查询索引。
* 文本块与文档：`answer_evidence` 对 `document`／`document_chunk` 是 `ON DELETE RESTRICT`，
  被证据引用的文档**不得物理删除**；只归档「发布时间早于阈值且无证据引用」的文档。
  归档时 `document.content` 可迁到对象存储，热表只留元数据与对象键。
* 迁移步骤：
  1. 建归档表（同一 DDL，去掉外键）；
  2. 按 `doc_id`/`question_id` 区间 `INSERT INTO ... SELECT ... LIMIT 1000` 分批迁移，
     每批独立短事务；
  3. 校验行数与校验和（`COUNT(*)`、`SUM(CRC32(...))`）一致；
  4. 应用层先双读（热表无记录再读归档表），稳定后再删热表数据；
  5. 保留回滚脚本与备份。
* 触发阈值建议：单表 > 5 GB 或问答 > 500 万条，或历史列表 P95 > 100 ms。

## 2. 架构级优化（本机不引入新服务，只给方案）

### 2.1 读写分离（1.5）

**问题.** 问答/检索读多写少，单库同时承担写入与历史查询，规模上升后读会挤占写。

**方案.** MySQL 一主一从（或一主多从），主库只写 `question`／`answer`／`answer_evidence`，
从库承担历史列表、后台列表等只读查询；使用半同步复制 + 延迟监控；应用侧按事务边界路由，
写后立即读仍走主库（避免复制延迟读不到）。

**本机为何不实施.** 本机只有单个 MySQL 8.4.9 实例（`max_connections=151`），没有第二台
数据库实例，也没有复制环境；引入从库属于新增服务，违反本轮约束。

**若实施的具体步骤.**

1. 准备同版本从库，配置 `server_id`、`gtid_mode=ON`、`binlog_format=ROW`；
2. `CHANGE REPLICATION SOURCE TO ...` 建立复制，确认 `Seconds_Behind_Source=0`；
3. 数据访问层拆 `read_conn`／`write_conn` 两个连接池，只读接口显式走从库；
4. 对「提问后立刻回看」的请求强制主库；对列表类接口容忍毫秒级延迟；
5. 从库故障时自动降级回主库（开关 + 告警），并压测验证。

### 2.2 缓存体系（1.6）

**问题.** 高频实体、热点文档元数据、历史列表与重复问题会被反复查询；向量检索还要
加载模型与索引，冷启动成本高。

**方案（多级缓存）.**

* **本地缓存**：Java 生态为 Caffeine；本项目后端是 Python，等价实现是进程内
  `cachetools.LRUCache`（或标准库 `OrderedDict` + TTL），只缓存小对象：
  实体 brief、文档元数据、图谱单跳结果、历史列表首页。容量建议 1～5 万条。
* **分布式缓存**：Redis 作为第二级，键空间按 `实体/文档/问答/检索结果` 分前缀；
  本地未命中再读 Redis，仍未命中回源 MySQL/Neo4j 并回填。
* **TTL 策略**：图谱结构类 24 h；文档元数据 1 h；历史列表 30 s～5 min（写后主动失效）；
  检索结果 10 min（问题文本 + 开关 + 数据版本参与键）；空结果 60 s。
* **穿透**：空值缓存（短 TTL）+ 布隆过滤器挡不存在的 ID。
* **击穿**：热点键互斥锁（Redis `SET NX PX`）或「逻辑过期 + 后台刷新」；
  进程内用单飞（single-flight）合并并发回源。
* **雪崩**：TTL 加随机偏移（±10%），Redis 哨兵/集群高可用，回源限流与熔断。
* **预热**：服务启动时加载高频公司（如成交额/问答覆盖 Top 100）、常用问题与图谱一跳。
* **更新策略（Cache Aside）**：写库成功后删除缓存（不是先删后写）；删除失败进重试队列；
  读路径为「读缓存 → 未命中读库 → 回填」。

**本机为何不实施.** 本机没有 Redis、没有 Caffeine（Python 后端），也未安装任何缓存组件；
新增 Redis 属于新增服务，本轮明确禁止。当前 MySQL 单查询 0.1～0.7 ms、图谱查询毫秒级，
缓存的边际收益低于其一致性风险。

**若实施的具体步骤.**

1. 先埋点统计键的访问频次与命中率，确定 Top-N 热键；
2. 引入 Redis（单机起步，生产再上哨兵/集群），封装 `Cache` 接口，
   本地 LRU 与 Redis 实现同一协议，便于灰度和回退；
3. 从只读、弱一致的实体/文档元数据开始接入，验证命中率与延迟；
4. 再接入历史列表与检索结果，补「写后失效」与空值缓存；
5. 压测穿透、击穿、雪崩三类场景，并做缓存与库的一致性对账。

### 2.3 IO／网络／并发与异步任务（附录一.4 其余条目）

* **文件 IO**：数据准备脚本已用 `jsonl` 流式读写与原子替换；上传解析类任务应改为
  分块读取（固定缓冲），禁止一次性 `read()` 超大文件。冷文件/原始公告可迁对象存储，
  本机不引入对象存储，仅在方案中保留。
* **网络连接池**：MySQL 已用进程内单连接 + 线程锁；生产应改为连接池（如 DBUtils/
  SQLAlchemy Pool）并设置连接/读取超时。Neo4j 驱动自带连接池，当前每次请求建/关会话，
  高并发下应复用 driver。LLM 的 `urllib` 无连接复用，生产可改 `httpx`/`requests.Session`。
* **指数退避重试**：只对网络错误、连接超时、HTTP 5xx 重试，最多 2 次，基础 0.5 s、
  指数 ×2、加 ±20% 抖动；HTTP 4xx 与「正文为空」不盲目重试。
* **并发模型**：IO 密集（数据库、LLM）用线程池/协程；CPU 密集（BGE 编码、FAISS）用
  独立进程池并限制并发。后端问答链路已有 `_ASK_LOCK` 串行化，避免 CPU 打满；
  生产应按 CPU 核数配置工作进程与并发上限，并区分读接口与问答接口的线程池。
* **异步任务队列**：文档解析、入库、图谱更新、向量化属于长任务，应入 MQ
  （RabbitMQ/Kafka 或轻量 Redis Stream）削峰，接口只返回任务号；问答接口不阻塞等待。
  本机无 MQ，不实施。实施步骤：定义任务表与状态机 → 生产者只写任务 → 消费者幂等处理
  （以 `doc_id`/内容哈希去重）→ 失败重试与死信 → 前端轮询/SSE 展示进度。

## 3. RAG 与知识图谱专属优化（附录一.3）

### 3.1 文档分块策略（1.7）

**问题.** 块太短会丢上下文，块太长会浪费 Token 且稀释相似度；需要判断当前参数是否合理，
以及是否需要语义分块。

**现状与实测（只统计、不重跑建库）.**

* 封版参数（`数据准备/config.py` 的 `CHUNK`，明确「改参数等于换数据集版本」）：
  `target_chars=400`、`max_chars=512`、`min_chars=128`、`overlap_chars=50`、
  `boundary_priority` 11 级、`strip_rules=True`。
* 5018 个块、709 篇文档的字符长度分布：
  min 83／P10 245／P50 377／P90 431／P95 468／P99 503／max 512，均值 357.7；
  Token 长度：min 64／P50 331／P90 387／P95 424／max 500，均值 317.5。
* <128 字的块 7 个（0.14%，多为文档末尾）、>512 字 0 个、纯空白块 0 个、
  含控制字符 0 个；重复文本 14 块（0.28%）；相邻块 50 字重叠命中率 95.2%
  （4102/4309，其余为标点/空白归一化后的边界差异）。每篇文档块数 1～151，中位数 4。

**判断.** 当前块长集中在 245～468 字，与 `target_chars=400` 一致，没有超长块；
<128 字的少量尾块属于正常收尾。分块参数已封版，本轮**不改参数、不重跑全量建库**。

**语义分块方案（若实施）.** 在字符边界优先级之上增加「句子/段落完整性」评分：
先按段落/句号切分，再在目标长度附近选择语义边界（而非硬切字符）；用标题/小标题作为
强边界；对表格单独解析并保留表头。实施后必须重建数据集、重算向量、重跑 A～E 组，
并重新生成全部实验读数，因此不能作为「顺手优化」。

### 3.2 Embedding 优化（1.8）

**现状（实测）.** `BAAI/bge-small-zh-v1.5`（512 维、CLS、归一化、CPU）：
批量 32 已启用；5018 块建库总耗时 98.358 s，其中模型加载 7.248 s、编码 91.109 s
（约 55 块/秒）。`max_seq_length=512`，与块长上限匹配。

**可优化点.**

1. **批量**：batch=32 已在用；CPU 上继续增大 batch 可能吃内存但吞吐提升有限，
   建议在部署机压测 16/32/64 后取最优，并记录到建库元数据。
2. **去重缓存**：当前数据中重复文本 14/5018（0.28%），全量建库收益极小；
   真正的价值在**增量入库**：以 `sha256(块文本 + 模型版本 + 归一化参数)` 为键缓存向量，
   新文档只编码未命中的块。步骤：建 `embedding_cache.jsonl`（hash → vector_id/向量）
   → 入库前批量查 hash → 未命中再编码 → 命中直接复用。
3. **轻量/量化**：float32 向量约 5018×512×4 ≈ 10.3 MB，内存压力很小；
   int8 量化可降到约 2.6 MB，但会改变相似度与实验排名，属于「换检索口径」，
   必须重建索引并重跑评测，不作为本轮改动。换更小模型同理，且会改变数据集版本。

**本机为何不实施.** 分块/向量数据是封版资产，重建会改变 v2.1 数据集与全部实验读数；
缓存对当前 5018 块的全量建库收益仅 0.28%。故只给增量方案，不动现有产物。

### 3.3 向量检索优化（1.9）

**现状（实测，单题）.** `VectorSearcher.search` 端到端 **11.2 ms**：
查询编码 **8.2 ms**、全量排名 **2.9 ms**（其中 FAISS 精确检索 0.47 ms、Python 排序约 2.4 ms）。
索引为 `IndexFlatIP`，`ntotal=5018`，对 5018 个向量做一次精确内积，
Top-N=20、最终 K=10 均从 `检索/config.py` 读取，不写死。

**判断.** 5018 个 512 维向量用 Flat 精确检索只需 0.47 ms；HNSW/IVF 的近似召回损失
会改变实验可复现性，当前规模**没有收益**。TopK 已经是可配置项（N=20、K=10）。

**若数据量增长的方案.**

* **规模阈值**：向量数 > 50 万或单次检索 > 50 ms 时切换到 HNSW；
  HNSW 参数建议 `M=16`、`efConstruction=200`、查询 `efSearch=64`（以召回率-延迟曲线定值）。
* **IVF**：百万级且内存受限时用 `IndexIVFFlat`，`nlist≈4√N`、`nprobe` 取 8～32，
  需要训练集且必须重跑召回评测。
* **过滤无关向量**：FAISS Flat 不支持元数据过滤；可在检索前按时间窗/文档集合生成
  `IDSelector`（IDMap2 或 `search_preassigned`），或按 `doc_id` 分区建子索引；
  过滤条件必须与检索侧时间过滤保持同一口径，避免 A～E 组不可比。
* **TopK/ef 调参流程**：固定评测集 → 扫 N/ef → 画召回率-延迟曲线 → 以召回优先选点 →
  写回 `检索/config.py` 并登记版本。

### 3.4 图谱查询优化（1.10，已落地）

**问题.** Neo4j 后端的 G6 与路径接口存在两类 N+1：

1. `g6_time_filter` 对**每个**通过/剔除的事件逐个调 `event_chunk_ids()`，
   而后者每次都执行一遍 G5 证据查询；
2. `/api/graph/paths` 的 `_path_payload` 对路径上的**每个节点**调 `brief()`，
   `_path_in_window` 又对每个节点调 `label_of()`/`_raw_node()`——每条都是一次 Cypher；
3. `/api/admin/extraction/events` 先对**全部** 1098 个事件算证据文档数，再分页。

**已落地的改动与前后读数（同一台机器、同一 Neo4j 5.26.31）：**

| 场景 | 改前 | 改后 | 说明 |
| --- | --- | --- | --- |
| G6 时间过滤（167 个“业绩”事件） | **1244.35 ms** | **65.83 ms**（↓94.7%） | 逐事件 G5 → 一条 `IN $ids` 批量取块 |
| 其中批量取证据块 | 571.42 ms | **7.73 ms** | 167 次 Cypher → 1 次 |
| 路径响应整形（18 条路径 / 54 节点） | 81.0～129.5 ms | **约 3.3 ms**（含一次批量取节点 3.2 ms） | 逐节点 brief → `raw_nodes()` 一次 |
| 路径时间窗过滤（同上） | 80.8～104.4 ms | **0.05 ms** | 复用批量属性表 |
| 后台抽取事件证据计数 | 37.33 ms（1098 事件） | **2.50 ms**（当前页 20 条） | 先分页再计数 |

一致性验证：

* 批量取块与逐事件 `g5_event_evidence()["chunk_ids"]` 对全部 167 个事件**逐项相等**（差异 0）；
* 路径整形改前/改后载荷在 18 条路径上 **Python 对象完全相等**；时间窗过滤结果完全相等；
* 内存后端 `检索/graph_query.py` **未改一个字节**，G6 语义仍以第 7 阶段实现为准。

**代码位置与做法.**

* `services/graph_service.py`：新增常量 `_BATCH_EVENT_CHUNK_IDS` 与
  `event_chunk_ids_batch()`；G6 先一次取回 `passed + removed` 的块集合，再做并集/差集。
  入池条件（排除 `EVIDENCED_BY`、只收非空 `source_chunk_id`、按 `(长度, 值)` 排序）
  与 G5 逐字一致。
* `api/graph.py`：`GraphReader.raw_nodes()` 用一条
  `MATCH (n) WHERE n.node_id IN $ids RETURN properties(n)` 批量取属性；
  `briefs()` 在其上组装简述；`/api/graph/paths` 对全部路径节点只取一次，
  `_path_in_window` 与 `_path_payload` 共用该表（保留逐节点回退，兼容既有测试桩）。
* `api/admin.py`：`extraction_events` 先 `items[start:start+size]`，只对当前页计数；
  `total` 仍是过滤后的全量条数，响应结构不变。

**索引评估（实测，未改）.** Neo4j 已有 7 条按标签的 `node_id` 唯一约束（背后是 RANGE 索引），
但业务 Cypher 多用无标签的 `MATCH (n {node_id:$id})`，执行计划为 `AllNodesScan`。
实测把无标签匹配改写为 7 标签联合（`Company|Person|…|Document`）后：
节点解析 1.90→2.15 ms、G1 2.83→2.52 ms、G6（167 id）6.79→10.01 ms，
有快有慢且整体无收益；当前 3607 个节点规模下全图扫描本身只要 1～2 ms。
故**不新增索引、不改 Cypher 匹配形态**，避免破坏两个后端同形与既有寻径语义。

**结果缓存方案（未实施）.** 图谱结果按「接口 + 规范化参数 + 图谱版本」做进程内 LRU
（如 10 min TTL，容量 1000），实体 brief/文档元数据可更久；写图谱后按版本号整体失效。
本机单用户、查询毫秒级，缓存收益低于一致性风险；生产接入时与 §2.2 的 Cache Aside 一并做。

**其余可优化项（记录、不改）.** `/api/graph/entities` 空关键词全量列举 3607 节点实测
115 ms、`all_events()` 1098 事件 39 ms；均已有分页/接口边界，当前可接受。
若并发上升，可在 Cypher 侧先分页或按标签拆分查询。

### 3.5 LLM 优化（1.11）

**现状（30 条真实回答的 `answer_trace.jsonl` 实测）.**

| 指标 | 数值 |
| --- | --- |
| Prompt Token（中位数／P95／最大） | 3536／3818／4089 |
| 生成 Token（中位数／最大） | 701.5／8148 |
| Context Token Budget 使用（中位数／最大） | 3306／**3599**（预算 3600） |
| 其中文本块 Token 中位数 | 3102.5（约 93.9%） |
| 其中图谱路径/三元组 Token 中位数 | 220.1 / 29.0 |
| 单题总耗时（中位数／P95／最大／30 题合计） | 3.50 s／15.76 s／33.61 s／199.2 s |
| 重试次数 | 30 题全部 1 次成功（无空正文） |

**结论.**

1. **Prompt 裁剪已生效**：预算 3600，实测最高 3599，说明裁剪逻辑正在边界上工作；
   文本块占约 94%，图谱占约 7%，继续压 Prompt 只能先减少证据块数，会直接损害引用完整性，
   因此不再压缩。可选的精细化方案是「按问题类型动态预算」（关系型多给图谱、
   事实型多给文本），但属于检索引擎口径调整，需重跑 A～E 组。
2. **超时**：`timeout_seconds=300`，远高于实测最大 33.61 s；该值同时覆盖推理型模型的
   长推理，属于安全上限，不建议下调。生产可把「连接超时」和「读取超时」拆开
   （如 10 s + 120 s），在保留长推理余量时更快发现网络故障。
3. **空正文重试**：已按冻结规则实现「请求成功但正文为空 → 同配置再试一次」；
   30 题实测未触发。**网络错误/5xx 不重试**，这是实验可复现性要求下的已知限制。
4. **结果缓存**：相同问题（归一化后）在同一数据版本下可命中缓存，TTL 建议 24 h；
   键必须包含问题文本、A～E 组开关、数据版本、Prompt 版本、模型版本。
   不建议做「语义相似即复用」的模糊缓存——会引入答非所问与不可复现风险。
5. **异步调用**：问答接口当前同步等待 LLM（后端以子进程方式调用）。
   方案是任务化：提交后返回 `task_id`，后台执行检索+生成，前端轮询或 SSE 接收；
   任务超时可取消，失败可按错误类型重试。本机无 MQ，可用线程池 + 任务表起步，
   但会改变现有同步接口契约，需单独评审。

**本机为何不直接改.** `问答/config.py` 与调用层的模型、temperature、max_tokens、
超时与重试规则均由第 8 阶段任务书冻结，改动会使既有回答与实验记录不可复现；
本轮只做实测与方案，不动问答组件。

## 6. 高可用与容错降级（附录三.4／3.6，第 2 轮登记）

### 6.1 已落地的容错能力（单机形态）

| 能力 | 实现位置 | 行为 |
| --- | --- | --- |
| 接口限流 | `后端/middleware.py` | 按来源 IP 滑动窗口（默认 60 次/60 秒），超限 1004＋HTTP 429；`/api/health` 豁免 |
| 输入防线 | `后端/params.py`、`GuardMiddleware` | 请求体 ≤64 KiB；问题 1～500 字、拒绝控制字符；非法输入在进入业务前返回 1001／1002 |
| 超时与整树终止 | `services/qa_service.py` | 问答子进程超时整树终止（Windows `taskkill /T`、POSIX `killpg`），并显式回收管道 |
| 外部源降级 | `services/market_service.py` | 行情／公告／新闻失败返回 `connected=false`＋`reason`＋空列表，绝不编造数据；只做一次网络层重试 |
| 异常分离 | `errors.py` | 业务异常 `ApiError` 与未捕获异常分离；响应体只有 `{code, message}`，堆栈与 `detail` 只进日志 |
| 请求 ID | `errors.py` | 每个请求一个 ID（可沿用客户端 `X-Request-Id`），写入日志上下文与响应头，**不进响应体** |
| 启动自愈 | `main.py`、`qa_service.cleanup_qa_runs()` | 过期运行目录清理失败只记日志，不阻断服务启动 |

### 6.2 集群化方案（本机不实施）

1. **服务无状态化**：后端进程不持有会话状态（`session_id` 由前端生成并随请求携带），
   可直接横向复制；`qa_runs` 临时目录需改为共享存储或每实例独立目录。
2. **限流与缓存外置**：当前限流计数、市场数据缓存为进程内；多实例下改用 Redis
   滑动窗口／TTL 键，保证跨实例一致（见 §2.2）。
3. **数据库高可用**：MySQL 主从＋只读副本承担历史与元数据查询，写路径保留主库；
   图谱与向量索引按版本化快照分发到各实例，升级时先构建新版本再原子切换。
4. **健康检查与滚动升级**：`/api/health` 已区分 MySQL／Neo4j／向量索引／模型配置四项；
   负载均衡按该探针摘除不健康实例，滚动升级时保证至少一个实例可用。
5. **熔断**：外部实时源可在现有降级之上加「连续失败 N 次 → 冷却 M 秒」的轻量熔断；
   本机只有单用户演示流量，当前以「一次重试＋立即降级」为足够，故未引入额外状态机。

### 6.3 判定不做的理由

本机为单实例演示环境，没有第二台应用节点、Redis 或数据库从库；按「不伪装实现」的
既定纪律，集群、分布式限流、跨实例缓存与熔断器均只给方案，不在单机进程里模拟。

### 7.1 边界场景与重复提问（四.1）

**输入边界（`POST /api/qa/ask` 实测）**

| 输入 | 实测响应 | 是否进入业务逻辑 |

| `question` 为空白串 | HTTP 400／`code=1001` | 否 |
| `question` 501 字（上限 500） | HTTP 400／`code=1001` | 否 |
| 含 NUL 等控制字符 | HTTP 400／`code=1001` | 否 |
| 含 `experiment_group` 等分组开关／未登记字段 | HTTP 400／`code=1002` | 否 |
| `session_id` 37 字符（上限 36） | HTTP 400／`code=1002` | 否 |
| 请求体不是合法 UTF-8 JSON | HTTP 400／`code=1002`（仍是 `{code,message}` 信封） | 否 |
| 无任何可引用证据（查询型空结果） | HTTP 200／`empty=true` ＋中性提示（不是错误） | 是（正常业务空结果） |

规则来源是 `params.validate_question()`：trim 后 1～500 字；拒绝 C0 控制符与 DEL，
`\t\r\n` 折叠为空格；`GuardMiddleware` 在路由前再拦一道超长／非法 JSON（纵深防御）。
前端 `AskView.vue` 增加 500 字实时计数、超限与不可见控制字符的**提交前**拦截；实测
501 字时页面直接报错且**没有发出** `/api/qa/ask`。

**重复提问的幂等复用（本轮新增）**

- 口径：同一 `(session_id, question_text)` 已有非空回答时，`/api/qa/ask` 直接复用最近一条，
  **不再调用模型、不新增 question／answer／evidence 行**；响应带 `reused=true` 与 `notice`。
- 隔离：只在本会话内复用；其他会话的相同问题不会被读到。
- 实验通道不受影响：`/api/admin/experiment/ask` 显式传 `reuse=False`，每次都跑新链路，
  保证受控实验的可比性。
- 前端：命中复用时带 `?reused=1` 跳到答案页，页头如实说明「已问过，复用的是当时落库的那一份」。
- 实测：对 S-001 的 `question_id=30` 原样重问 → 耗时 **0.02 s**、`reused=true`、
  返回同一 `question_id=30／answer_id=30`、证据 10 条；库计数保持 **30／30／293** 不变。
- 边界：题干内部的空白差异不会被归一（只有首尾空白与 `\t\r\n` 折叠），因此
  「同一语义、不同空格」会被视为新问题；若要更激进的语义去重，需要另做归一化键，
  本轮不做（避免把不同问题误判为同一问）。

### 7.2 会话管理（四.2）

**已落地**

- 会话号：浏览器首次访问生成 UUID，存 `localStorage['qa-console-session-id']`；
  所有历史请求自动带 `session_id`（也支持 `X-Session-Id` 头）。
- 持久化：历史记录落 MySQL 三表，刷新／重启浏览器后仍可回看本会话记录。
- 切换与重置：历史页展示**完整当前会话号**，新增「重置会话」按钮。重置只生成新 UUID、
  清空前端只读缓存，**不删除任何服务端记录**；确认框明确写出「旧记录仍在库中，只是本页不再显示」。
- 隔离实测：S-001 列表 30 条；其他会话列表 0 条；S-001 可读 `question_id=1`；
  其他会话读同一条 → HTTP 404／`code=2001`；缺 `session_id` → HTTP 400／`code=1002`。
- 诚实性修正：历史页空态原写「在地址栏改 `/history?session_id=S-001`」，但该页从不读取
  地址栏会话参数，照做无效。已删除这句，改为如实说明会话隔离与重置的影响。

**未做（如实登记）：多轮上下文。** 第一版问答契约是**单轮**：请求体只有
`question + session_id`，会话号用于留痕与隔离，不参与 Prompt 组装；链路不读取历史轮次。
若后续要做多轮，方案是：在 `answer.py` 装配 Prompt 时按 `session_id` 取最近 N 轮
（问题＋答案摘要），设独立 token 预算并从证据预算中扣减；同时在 `question` 表增加
`turn_index`／`parent_question_id`。这会改变 Prompt 版本与可复现口径，需与论文／实验冻结
口径同步，故不在本轮擅自实现。

### 7.3 交互：加载、超时与取消（四.4）

- 分页：历史列表已有上一页／下一页与页码读数；本轮未改分页契约。
- 加载态：提问页显示已等待秒数；提问按钮在等待期间禁用。
- 超时：后端链路超时 **300 s**（`config.ANSWER.timeout_seconds`，超时整树终止子进程）；
  前端 `askQuestion` 默认 **320 s** 兜底超时，避免无限等待。
- 取消：新增「取消等待」按钮（`AbortController`）。**取消只停止浏览器这一次等待**，
  HTTP 没有反向取消通道，后端子进程可能仍会跑完并写入本会话历史——界面文案按此如实提示。
  实测：拦截 `/api/qa/ask` 并延迟，点击取消后请求立即结束，页面显示中性提示
  「请求已取消……后端可能仍会完成生成并写入本会话历史」。
- 限流交互：保留既有的「429／1004 退避重试一次」与限流横幅；本轮未改其判据。

部署环境变更，需在专门一轮做并复验 E2E。

### 7.5 Web 安全（六.1）

- **SQL 注入：不成立。** 全库检索未发现把用户输入拼进 SQL 的 f-string；动态值一律
  `%s` 参数化，表名／列名只走固定白名单辅助函数（如 `_col()`）。实测注入串
  `' OR '1'='1`、`S-001' UNION SELECT …--`、`1 OR 1=1` 分别返回 0 条／0 条／1002，
  未出现库名、表名或异常栈。`LIKE` 的 `%`／`_` 通配符仍按普通字符语义工作
  （搜索 `%` 会匹配较多实体），这是查询语义而非注入，登记为可接受的次要行为。
- **XSS：不成立（当前渲染面）。** 所有 `v-html` 使用点已逐一核对：`AnswerSections.vue`
  先对正文做 `&<>` 转义，再把 `[证据N]` 替换成固定锚点；`lib/graph.js` 的 `EXT`
  是静态 SVG 常量。其余文本走 Vue 插值自动转义；外部链接固定
  `target="_blank" rel="noopener"`。
- **CSRF：不适用。** 系统不使用 Cookie 会话：会话号是前端 localStorage 里的随机 UUID，
  管理端用自定义请求头 `X-Admin-Token`（浏览器不会自动附带）；CORS 只允许
  `http://localhost:5173` 与 `http://127.0.0.1:5173`，实测其他 Origin 无
  `Access-Control-Allow-Origin`。
- **基础加固**：响应头 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、
  `Referrer-Policy: no-referrer` 实测均存在；请求体上限 64 KiB（70 KiB 请求被 1001 拒，
  不进入业务逻辑）；每请求带 `X-Request-Id`。

### 7.6 接口安全：限流与令牌（六.2）

- 限流为**按来源 IP 的滑动窗口**：默认 60 次／60 秒，`/api/health` 豁免；
  实测连续读请求在第 60 次后返回 HTTP 429／`code=1004`，并带 `Retry-After: 60`。
  仅在后端显式配置信任代理时才读 `X-Forwarded-For`，否则用直连地址，避免伪造头绕过。
- 计数表有 10 万 IP 上限，防止内存被无限撑大。
- 管理令牌只存在未跟踪的 `config.local.json`；不打印、不写日志、不入报告。
- 写接口另有未登记字段／分组开关（1002）、必填缺失（1003）、长度与类型校验。

### 7.7 敏感信息与日志脱敏（六.3）

- 扫描 `git ls-files` 全部 **7140** 个跟踪文件：明文口令、API Key／Secret、绝对用户路径
  （`C:\Users\…`）**均为 0 命中**；管理员令牌值在跟踪文件中 **0 次出现**。
  `config.local.json` 已被 `.gitignore` 忽略（`git check-ignore` 实测命中）。
- 日志脱敏（本轮新增）：问题正文不再直接进日志——空结果与复用日志只记
  `len=… sha256=前12位`；链路的 stdout／stderr 尾部在写日志前按问题原文替换为摘要。
- 残余风险（如实登记）：
  1. 问题正文仍作为 `--question` 参数传给子进程，**同机同用户**可在进程列表中看到；
     要彻底消除需改成临时文件／stdin 传递并同步改第 8 阶段入口，属跨阶段改动，本轮不做。
  2. stdout 脱敏按「原文精确匹配」；若上游把中文转成 `\uXXXX` 形式输出，则匹配不到。
  3. `config.local.json` 是明文本地配置（已被 Git 忽略，但未做磁盘加密）。生产部署应改用
     操作系统密钥环／密钥管理服务，并收紧文件 ACL。
  4. 数据库账户过高（见 §7.4 残余风险）。

### 7.8 文件上传安全（六.5）

**本系统没有文件上传端点**：文档导入走 `POST /api/admin/documents` 的 JSON 正文
（`title/content/source/...`），不是 multipart 文件上传；因此“上传漏洞”当前不适用。
本轮**不虚构**一个上传功能。若未来增加上传，按下列顺序校验（缺一不可）：

1. 鉴权：仅管理员（现有 `X-Admin-Token`），不提供匿名上传；
2. 大小：在反向代理与应用两层限制（当前应用层请求体上限 64 KiB，需要大文件时单独放开
   该路由并设独立上限，不能全局放开）；
3. 类型：扩展名白名单＋服务端魔数校验（`python-magic` 之类），拒绝双扩展名与可执行类型；
4. 文件名：不使用客户端文件名入库／落盘，改用服务端随机 ID，防路径穿越与覆盖；
5. 存储：存到 Web 根目录之外，下载走受控接口，禁止目录列表；
6. 内容：解析前隔离（受限目录／低权限进程），解析库保持版本更新；入库前仍走现有
   「去重 → 清洗 → 质量校验」流水线；
7. 审计：记录上传人、时间、大小、哈希与解析结果。

**相关不一致（登记，不在本轮改）**：`config.API_LIMITS.document_content_max_bytes`
为 16 MiB，但全局请求体上限是 64 KiB，经 HTTP 导入的正文实际上限是 64 KiB；更大的正文
只能走离线脚本。两处口径需要后续统一（要么给文档导入单独放开上限，要么把 16 MiB 改为
64 KiB 并在文档中写明）。

1. **常驻预热检索进程**：后端启动后拉起一个检索子进程并常驻，`/api/qa/ask` 通过管道／
   本地队列复用该进程。按上表，单题从约 6.3 秒降到约 18 ms（另加 IPC 开销），是唯一
   数量级收益。**本轮不做**：问答链路目前每次 ask 启动独立子进程，是为了隔离
   `检索/config.py` 与 `问答/config.py` 两套同名模块；改成常驻服务需要新的进程协议、
   超时／重启／并发控制与 E2E 回归，属于架构改动，按任务口径只给方案与实测上界。
2. **避免重复 `from_pretrained`**：核查链路只构造一次 `LocalEmbedder`，无重复加载；
   本轮不改。
3. **`torch.set_num_threads` 调参**：检索侧固定为 1 线程以保证排序确定性；改成多线程
   会改变浮点累加顺序与并列处理的可复现性，且对导入耗时无帮助。**判定不做**。
4. **导入裁剪**：`transformers` 的 4.22 秒主要来自包初始化，惰性导入只是把成本推迟到
   首次提问；换 ONNX／其他推理栈会改变编码口径与实验读数。**判定不做**。
5. 若后续做常驻进程，建议顺序：先做「单进程预热＋健康检查」→ 再加超时自动重启与
   串行队列 → 最后做多 worker 支持；每步都用同一组 30 题比对检索结果逐字段一致。

### 8.2 向量索引：Flat 与 IVF／HNSW 离线对比

**实验纪律.** 只在内存里另建近似索引，**不写回数据集、不替换默认索引**；查询向量用
30 道预实验题经同一份本地 BGE（CLS＋L2 归一化）编码。评价 ANN Recall@10（与
`IndexFlatIP` 精确 top-10 的交集／10）、gold 命中率、`index.search()` 的 P50／P95 与
序列化体积。脚本：`工具/实验_向量索引对比.py`；底稿：
`交付物/05-系统实现/RAG检索系统/_工作底稿/向量索引对比_第6轮.json`。

**环境与语料.** Python 3.12.10、FAISS 1.15.1、numpy 2.5.1、CPU、`torch_num_threads=1`；
语料 **5018×512**、`IndexFlatIP`（归一化后内积即余弦）、30 题编码耗时 0.5338 秒。

| 索引配置 | Recall@10 均值 | Recall@10 最小 | gold@10 | P50（ms） | P95（ms） | 序列化字节 |
| --- | --- | --- | --- | --- | --- | --- |
| **FlatIP（默认／精确基线）** | **1.0000** | **1.0000** | **0.8333** | **0.1876** | **0.2403** | 10,276,909 |
| IVF-Flat nlist=64 nprobe=8 | 0.8700 | 0.4000 | 0.8000 | 0.0476 | 0.0548 | 10,448,731 |
| IVF-Flat nlist=64 nprobe=16 | 0.9433 | 0.5000 | 0.8333 | 0.0842 | 0.0916 | 10,448,731 |
| IVF-Flat nlist=64 nprobe=32 | 0.9900 | 0.9000 | 0.8333 | 0.1136 | 0.1367 | 10,448,731 |
| IVF-PQ nlist=64 M=32 nbits=8 nprobe=8 | 0.6733 | 0.3000 | 0.8333 | 0.0662 | 0.0706 | 856,772 |
| IVF-PQ nlist=64 M=32 nbits=8 nprobe=16 | 0.6900 | 0.3000 | 0.8333 | 0.0871 | 0.0922 | 856,772 |
| IVF-PQ nlist=64 M=32 nbits=8 nprobe=32 | 0.6933 | 0.3000 | 0.8667 | 0.0863 | 0.1334 | 856,772 |
| HNSW M=32 efConstruction=200 efSearch=32 | 0.9700 | 0.6000 | 0.8333 | 0.0453 | 0.0550 | 11,638,938 |
| HNSW M=32 efConstruction=200 efSearch=64 | **0.9933** | 0.9000 | 0.8333 | **0.0766** | **0.0892** | 11,638,938 |
| HNSW M=32 efConstruction=200 efSearch=128 | 1.0000 | 1.0000 | 0.8333 | 0.1424 | 0.1606 | 11,638,938 |

**结论.**

1. **默认索引保持不变**：5018 条向量的精确检索只需 **0.1876 ms**（P50），近似索引
   即便快 2～4 倍也只有 0.1 ms 量级，相对单题编码（约 28 ms）可忽略；而近似会改变
   top-10 集合与并列顺序，破坏实验可复现性。
2. 若未来规模上升，**HNSW efSearch=64** 是本机数据上的最佳折中：Recall@10 0.9933、
   P50 0.0766 ms；`efSearch=128` 可到 1.0000 但延迟翻倍。IVF-Flat 要达到 0.99 需
   `nprobe=32`，P50 反而高于 HNSW；IVF-PQ 在 5018 条训练样本上召回仅 0.69，
   且最小 Recall 只有 0.3，不适合作为当前语料的默认。
3. 切换近似索引必须作为**新实验口径**：重建索引、重跑 A～E 组并更新论文读数；
   本轮只出对比数据，不切换。

### 8.5 只读热点接口的进程内 TTL＋LRU 缓存

**设计.** 新增 `交付物/03-代码/后端/cache.py`：标准库 `OrderedDict`＋`RLock`，
TTL 到期惰性删除、容量满后按 LRU 淘汰；`get_or_load()` 在锁内加载，避免同一 key
并发击穿；读写均深拷贝，响应调用方改不到缓存对象；异常不缓存（404／参数错误不会
留下空值）；缓存的是接口 `data` 区块，`errors.ok()` 每次重新生成信封，因此 `meta`
仍取当前配置，**响应内容不变**。

**接入点.**

| 接口 | 缓存键 | 说明 |
| --- | --- | --- |
| `GET /api/config/meta` | 固定 `"meta"` | 数据集元信息，只读 |
| `GET /api/graph/entities/{id}` | 规范化 `node_id` | 实体详情，只读；不存在时抛 404，不缓存 |

**开关与观测.** `config.CACHE` 支持 `ASHARE_CACHE_ENABLED`（默认开）、
`ASHARE_CACHE_TTL_SECONDS`（默认 60）、`ASHARE_CACHE_MAX_ENTRIES`（默认 512）；
也可在 `config.local.json` 写 `cache_enabled` 等键。关闭后 `get()` 恒未命中、
`set()` 不落数据，接口行为与未接缓存一致。命中率／命中数／淘汰数随
`GET /api/health` 的 `cache` 区块返回，**未新增路由**。

**HTTP 实测（同类名端点，500 次请求＋20 次预热，持久连接）.** 缓存关闭与开启各起一次
后端进程测量；响应体 SHA-256 在两种模式下逐字节相同（每个端点只有 1 种响应体）。
脚本：`工具/实验_只读接口缓存.py`；底稿：
`交付物/05-系统实现/前后端系统集成/_工作底稿/只读接口缓存_第6轮.json`。
