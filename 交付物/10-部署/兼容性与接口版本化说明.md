## 二、输入格式兼容（十.1）

### 2.1 原始数据管线支持什么

入口：`数据准备/fetch.py`。

| 输入形态 | 处理函数 | 实测/结论 |
| --- | --- | --- |
| HTML 页面（财经网站） | `decode_html(resp)` → `make_soup()` → `pick_text()`／`extract_body()` | 支持；编码按「响应声明 → HTTP Header charset → `<meta>` → chardet → utf-8」逐级回退；解析器优先 lxml，缺失时回退 `html.parser` |
| PDF 公告 | `extract_pdf_text(blob: bytes)`（PyMuPDF） | 支持；正文按页拼接，供后续分块 |
| 纯文本（txt） | 无专用入口；若作为 HTML 响应交给 `decode_html`＋`make_soup`，可读出正文 | **非正式支持**；不建议作为生产输入 |
| Markdown（md） | 同上 | **非正式支持**；`#`、`**`、表格管道符等标记会原样保留，不转纯文本 |
| JSON 文档 | 管理端 `POST /api/admin/documents` 的 `content` 字段 | 支持；见 2.3 |
| 图片／扫描件 PDF | 无 OCR | **不支持**；扫描件会得到空文本或极少文本 |

### 2.2 实测样本（2026-10-18）

| 指标 | 读数 |
| --- | --- |
| 原始文档总数 | **747** |
| 解析方式 `pdf_pymupdf` | **591** |
| 解析方式 `html_bs4` | **156** |
| `raw_text` 非空 | **747 / 747** |
| 最短正文 | 83 字符 |
| 最长正文 | 49,853 字符 |

编码兼容实测（临时样本，不写入产品目录）：

- UTF-8 ＋ `<meta charset="utf-8">`：正确；
- GBK 正文、无 `<meta>`：经 chardet 回退正确；

- 声明与实际不符时，按上述回退链取第一个可解码且合理的方案。

PDF 实测：在临时目录生成一页中文 PDF，`extract_pdf_text()` 成功抽出文本。

### 2.3 管理端导入接口的输入契约

`POST /api/admin/documents` 接收 **JSON 对象**，不是 multipart 文件上传。

必填字段：`title`、`content`、`source`、`publish_time`。
可选字段：`url`、`category`、`company_list`。

校验规则（`admin._check_document_payload`）：

- 非对象 → **1003**；含未登记字段 → **1002**；
- 长度上限逐项对齐表结构：`title` 512／`source` 128／`url` 1024／`category` 64／
  `company_list` 512；`content` 配置上限为 `config.API_LIMITS["document_content_max_bytes"]`（16 MiB），
  **但经 HTTP 的实际可用上限是全局 64 KiB 请求体**，两处口径尚未统一，见 2.4；
- `category` 不限定在四类内：不在四类内时**记告警但照收**（检索侧不按 category 过滤）；
- 导入只写 `document` 与 `document_chunk`，**不重建向量索引**（`vectorized=false`），
  向量化仍需走离线建索引流程。

> 因此「文件格式兼容」的边界是：**原始数据管线支持 PDF/HTML；管理端只接收已抽好的纯文本**。
> 若要支持 docx/xlsx 等格式，需在管理端前增加转换层，当前**未实现**。

### 2.4 不支持/限制清单

| 输入 | 状态 | 原因/后续 |
| --- | --- | --- |
| 扫描件 PDF | 不支持 | 无 OCR；需引入 OCR 并处理版面 |
| docx / xlsx / pptx | 不支持 | 无解析器；可在导入前自行转文本 |
| Markdown 语义 | 不支持 | 仅按纯文本处理，标记保留 |
| 文件上传（multipart） | 不支持 | 管理接口只收 JSON；大文件粘贴受 64 KiB 请求体上限约束 |
| 超长单篇 | 受上限约束 | **口径差异（如实登记）**：`document_content_max_bytes=16 MiB`，而 Nginx `client_max_body_size 64k`＋后端 64 KiB 请求体上限使 HTTP 导入实际只能到 64 KiB；更大正文走离线导入。后续要么给该路由单独放开上限，要么把配置值改为 64 KiB |
| 非 UTF-8 的 JSON 请求体 | 按 HTTP 规范解析 | 建议客户端统一 UTF-8 |

## 四、接口兼容与版本化（十.3）

### 4.1 现状

- 所有接口路径为 `/api/<资源>`，**无版本号**；
- 响应信封：成功 `{data, meta}`（列表/详情）或业务对象；错误固定 `{code, message}`
  （唯一例外：2003 额外带 `retained_for_history`）；
- OpenAPI 3.1.0 由 FastAPI 自动生成：`/openapi.json`、`/docs`（Swagger UI）、`/redoc`；
- 前端通过同源 `/api/*` 调用，Nginx 反代到 `backend:8000`。

### 4.2 版本化策略对比

| 方案 | 示例 | 优点 | 缺点 | 本项目适配度 |
| --- | --- | --- | --- | --- |
| **路径前缀（推荐）** | `/api/v1/qa/ask` | 直观、可缓存、易网关路由、OpenAPI 天然分组 | URL 变长 | **高**：Nginx 一条 rewrite 即可，后端零改动 |
| Header 协商 | `X-API-Version: 1` | URL 稳定 | 调试/缓存不直观，易漏传 | 中 |
| Content-Type 参数 | `application/json; version=1` | 语义严格 | 生态支持弱 | 低 |
| 查询参数 | `?version=1` | 简单 | 污染业务参数、缓存键复杂 | 低 |

### 4.3 推荐方案：Nginx 层路径前缀重写（不改后端路径）

**目标**：对外提供 `/api/v1/*`，内部仍保持 `/api/*`，避免改动 31 个 path、34 个 operation 与
前端全部调用。

在 `nginx.conf` 的 `location /api/` **之前**增加：

```nginx
location /api/v1/ {
    rewrite ^/api/v1/(.*)$ /api/$1 break;
    proxy_pass http://backend:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Request-Id $request_id;
    proxy_read_timeout 320s;
    proxy_send_timeout 320s;
}
```

要点：

1. **`rewrite ... break`**：只改内部 URI，不改变 `proxy_pass` 的请求路径语义；
2. `/api/*` 旧路径**继续保留**，作为 v1 的别名；新客户端一律用 `/api/v1/*`；
3. 前端当前仍调 `/api/*`，无需改动；迁移期两套路径并存；
4. OpenAPI 文档可另起一份「对外契约」，标注版本前缀，但**不需要**改后端 `openapi.json`；
5. 若未来出现 v2，新增 `location /api/v2/` 指向新后端或新路由，v1 保持冻结。

> **本轮未实施**：按任务书要求「只写方案，不真的改接口路径」。以上为可执行的下一步。

### 4.4 版本生命周期与弃用

| 阶段 | 规则 |
| --- | --- |
| 新增兼容字段 | MINOR；调用方必须忽略未知字段 |
| 新增接口 | MINOR；需在《25》与验收脚本的 `REGISTERED_ADDITIONS` 登记 |
| 字段语义变更/删除、错误码语义变更 | MAJOR；新前缀，旧版本保留至少一个发布周期 |
| 弃用 | 响应头 `Deprecation: true`＋`Sunset: <HTTP-date>`；文档与变更日志同步 |
| 冻结口径 | K／N／预算／g／Prompt 版本／模型版本变更属 MAJOR，禁止在同一版本内静默切换 |

### 4.5 兼容性测试建议

1. **契约测试**：对 `/openapi.json` 做快照，检查 path／method／必填字段／错误码表的变化；
2. **双路径回归**：同一请求分别打 `/api/*` 与 `/api/v1/*`，断言响应 JSON 逐位相等；
3. **旧客户端回归**：前端 `npm run test` + 构建；后端 G/J 组路由测试；
4. **弃用演练**：在测试环境返回 `Deprecation`／`Sunset`，确认客户端日志可见。

### 5.2 现状评价

**优点**：

- 路径、方法、查询参数、请求体模型由 FastAPI 自动生成，不易与代码脱节；

2. **鉴权已声明（已落地）**：管理端使用 `APIKeyHeader(name="X-Admin-Token")`，OpenAPI 已能
   表达该 API Key 方案；运行期仍以 `hmac.compare_digest` 比较，未配置时失败关闭。
3. **契约快照已入门禁（已落地）**：`_契约快照.json` 已入库，`工具/契约快照.py` 支持差异比对

4. **示例值仍可增强**：关键接口的业务示例目前主要依赖 `/docs` 的运行时模型；可按需补
   `examples`，不属于兼容性阻断项。
5. **版本前缀仍未实施**：`info.version` 是内部阶段号（`stage9-t4-skeleton`）；对外发布前应改为
   语义化版本，并按 4.3 的 `/api/v1` 方案执行——当前只是方案。

## 七、结论与未落地项

**已确认可用**：

- PDF/HTML 原始解析、管理端 JSON 正文导入、UTF-8/GBK 编码回退；
- Python/前端依赖精确锁版，本机与 Dockerfile 同源；

**未落地（如实记录）**：

1. 接口版本前缀 `/api/v1` 仅为方案，**未修改 Nginx 与后端路由**；
2. 无 OCR、无 docx/xlsx 解析、无文件上传端点（只收 JSON 正文）；
3. 关键接口的业务 `examples` 仍可补充；`info.version` 仍是内部阶段号；
4. 文档正文配置上限（16 MiB）与全局请求体上限（64 KiB）口径尚未统一。
