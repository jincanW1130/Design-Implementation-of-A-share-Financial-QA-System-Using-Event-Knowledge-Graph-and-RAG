# 版本与分支约定

> 适用范围：本仓库的日常开发、联调与提交前检查。
> 本文只约定**工作方式**，不改变任何既有口径；写本文时**没有**新建分支、没有修改 git 配置、
> 也没有做任何 commit。作者首次启用时按本文执行即可。
>
> 互链：[性能与架构优化方案](../05-系统实现/性能与架构优化方案.md) §7.3、
> [工程化与可观测性方案](工程化与可观测性方案.md) §三、[优化方案核对表](../05-系统实现/优化方案核对表.md)。

## 一、分支模型（单人＋评审的最小集）

| 分支 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 可交付／可复现的稳定线；论文与答辩对应的读数只从这条线取 | 长期 |
| `develop` | 日常集成分支；功能与修复先合到这里，通过全部门禁后再合 `main` | 长期 |
| `feature/<编号>-<短名>` | 单个改动，例如 `feature/8.2-metrics` | 合并后删除 |
| `fix/<编号>-<短名>` | 缺陷修复，例如 `fix/c1-route-registration` | 合并后删除 |
| `release/<版本号>` | 提交／答辩前的冻结窗口，只收文档与阻断性修复 | 发布后删除 |
| `hotfix/<版本号>` | 稳定线上的紧急修复，修完同时回合 `main` 与 `develop` | 合并后删除 |

单人项目的简化规则：

1. 任何改动**不直接提交到 `main`**；至少经过一次本地门禁（见第四节）。
2. 合并前先 `git fetch`＋`git rebase develop`，保持线性历史；不强制要求 PR 模板。
3. `release/*` 期间**不改数据资产、不重建图谱／向量索引、不改冻结的 Prompt 与模型参数**。
4. `main` 上每个发布点打一个**附注标签**（`git tag -a v1.2.0 -m "…"`），标签只打不改。

## 二、语义化版本（SemVer 2.0）

版本号形如 `MAJOR.MINOR.PATCH`（可带 `-rc.N` 预发布后缀）：

* **MAJOR**：对外契约不兼容——接口路径／响应信封／错误码语义、六张表结构、冻结的实验口径
  （K／N／预算／g／Prompt 版本／模型版本）发生不兼容变更。
* **MINOR**：向后兼容的新增——新增接口（须先在《25》与 `验收第9阶段.py` 的
  `REGISTERED_ADDITIONS` 登记）、新增配置项（带缺省值且缺省行为不变）、新增运维脚本。
* **PATCH**：向后兼容的修复——缺陷修复、日志／指标完善、文档更正，不改变任何对外读数。

操作约定：

* 版本号只在 `release/*` 分支上改；仓库当前 `交付物/03-代码/前端/package.json` 的
  `version` 为 `0.1.0`（首版未定为 1.0），**不在日常提交里随手改版本号**。
* 预发布用 `v1.0.0-rc.1`、`v1.0.0-rc.2`；同一版本的 rc 只递增，不复用。
* 发布标签与《02-项目执行总控文档》的修订记录对应；标签说明写清本轮改动的任务 ID。
* 破坏性变更必须在提交信息里写 `BREAKING CHANGE:` 段，并在《02》登记迁移方式。

## 三、提交信息规范（Conventional Commits）

格式：

```text
<type>(<scope>): <一句话摘要>

<可选正文：为什么改、影响面、复验读数>

<可选脚注：Refs: 8.2；BREAKING CHANGE: …>
```

允许的 `type`：

| type | 用途 |
| --- | --- |
| `feat` | 新功能／新接口／新脚本 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化（须附前后读数） |
| `test` | 测试补强 |
| `docs` | 文档（含方案、README、过程记录） |
| `build` | 依赖、镜像、构建脚本 |
| `ops` | 部署、备份、监控、日志轮转 |
| `chore` | 仓库卫生等杂项 |

`scope` 用现有目录或模块名，例如 `backend`、`frontend`、`retrieval`、`qa`、`deploy`、
`gates`、`docs`、`observability`。

摘要用中文即可，但**不得**出现口令、令牌、连接串、真实用户路径；不得把 `config.local.json`
或 `.env` 的内容粘进提交信息。一次提交只做一件事；数据资产、论文成稿与代码改动分开提交。

## 五、发布流程（答辩／送审）

1. 从 `develop` 切 `release/<版本号>`，只改版本号、文档与阻断性修复。
2. 跑第四节全部检查，外加 `python 工具\启动自检.py`。
3. 打附注标签 `v<版本号>`；把标签、复验读数与已知限制写进《02》修订记录。
4. 合并回 `main` 与 `develop`；删除 `release/*`。
5. 备份留痕按 `工具\备份.ps1` 的约定落在 `交付物/10-部署/备份/`（**不入库**）。

## 六、不要做的事

* 不 `git commit` 任何凭据、令牌、数据库口令、模型 API Key、`.env`、`config.local.json`。
* 不 `--force` 推送 `main`／`develop`；不重写已发布的标签。
* 不把 `交付物/01-论文/` 与 `交付物/02-答辩/` 的定稿文件混进代码提交。
* 不在 `release/*` 上重建图谱／向量索引或改变冻结的实验口径。
