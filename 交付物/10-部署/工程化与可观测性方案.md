## 一、7.1 开发／测试／生产配置分层

### 1.1 实现

配置文件仍以 `交付物/03-代码/后端/config.local.json` 为准，加载顺序固定为：

```text
① 基配置        ASHARE_CONFIG_FILE（缺省 config.local.json）
② 环境叠加文件  config.<ASHARE_ENV>.local.json（存在才叠加；与基配置同文件则跳过）
③ 环境变量覆盖  ASHARE_* 白名单（只认下表，拼错的键不会被静默忽略）
```

`ASHARE_ENV` 只接受 `dev`／`test`／`prod`，缺省 `dev`；非法值在导入期直接 `SystemExit`。
环境变量白名单（15 项）：MySQL 的 host／port／user／password／database／charset、Neo4j 的
uri／user／password、backend_port／frontend_port、log_path、admin_token、
trust_proxy_headers、qa_runs_retention_days。整数与布尔键做类型校验，失败即退出。

**没有新增任何必填键**：`log_path`、`admin_token`、`trust_proxy_headers`、
`qa_runs_retention_days` 仍按原口径可选；因此所有现存 `config.local.json` 无需改动。
模板 `config.local.json.example` 只增加了说明性 `_环境分层说明`（以下划线开头的键在加载时
被过滤，不参与校验）。

### 1.2 缺省行为不变的实测

```text
# 不设任何 ASHARE_* 环境变量
ASHARE_ENV=dev；环境叠加文件存在=False；环境变量覆盖键=无
backend_port=8000；frontend_port=5173

# 只设 ASHARE_ENV=prod ASHARE_FRONTEND_PORT=5199
ASHARE_ENV=prod；环境叠加文件存在=False；环境变量覆盖键=frontend_port
backend_port=8000；frontend_port=5199
```

即：不配置时与分层前完全一致；配置时只改被点名的键。`config.py` 的导入期校验、凭据
「已配置／未配置」判定、`db_params()`／`neo4j_params()` 的延迟校验均未改变。

### 1.3 使用方式


## 五、8.1 结构化日志

### 5.1 现状与增量

既有 `errors.setup_logging()` 已提供 `RotatingFileHandler`（可选）与统一格式：

```text
2026-10-18 14:46:34,999 INFO [61daf27e79aa4cf9] ashare_qa.backend 问答链路完成：耗时 10.7s out_dir=…
```

第 4 轮新增 `observability.AccessLogMiddleware`，对每个 `/api/*` 请求写一行：

```text
access method=POST path=/api/qa/ask status=200 duration_ms=10758.3 route=/api/qa/ask
```

* `route` 用归一化模板（数字／UUID／`EVT-0006` 等标识段替换为 `{id}`），避免高基数；
* 请求 ID 由 `RequestIdFilter` 自动补在行首，访问日志不重复打印；
* 支持 `ASHARE_ACCESS_LOG=0` 关闭、`ASHARE_ACCESS_LOG_SAMPLE_RATE=0～1` 采样（缺省 1.0）；
* **不记请求体、不记问题原文、不记口令**；问答服务只额外记录 `out_dir`、`llm_calls`、
  `llm_seconds`、`graph_used`、`evidence` 等结构化字段。

### 5.2 校验

本次真实请求的日志只出现请求 ID、session_id（调用方 UUID）、question_id／answer_id、
`out_dir` 与耗时；未出现问题文本、MySQL／Neo4j 口令或后台令牌。最终扫描命令与结果见第十节。

## 六、8.2 指标

### 6.1 决策：挂在 `/api/health`，不新增 `/api/metrics`

新增路由会改变 OpenAPI 路径／操作数，需同步 `验收第9阶段.py` 的 `REGISTERED_ADDITIONS`
与《25》；而本项目的规模与单进程架构不需要独立的指标服务。故：

```json
GET /api/health
{
  "status": "ok",
  "mysql": {...}, "neo4j": {...}, "vector_index": {...}, "model_config": {...},
  "metrics": {
    "window_seconds": 60, "history_seconds": 300, "uptime_seconds": 83.6,
    "requests": {"total": 3, "window": 1, "qps": 0.02, "errors_window": 0, "error_rate": 0.0},
    "routes": {
      "POST /api/qa/ask": {"count_window": 1, "qps": 0.02, "errors_window": 0,
                           "error_rate": 0.0, "p50_ms": 10758.3,
                           "p95_ms": 10758.3, "p99_ms": 10758.3}
    },
    "qa": {"success": 1, "failure": 0, "success_rate": 1.0},
    "rate_limit": {"hits": 0}
  }
}
```

* `status` **仍只由四项依赖探针决定**；`metrics` 只是摘要，不参与就绪判定；
* 指标在进程内、线程安全（`deque` ＋ 锁），重启清零；单进程口径，多 worker 不聚合；
* 每路由最多 2000 个样本、最多 128 个路由键，超出归入 `__other__`，防止探测制造高基数；
* `metrics` 快照异常时只返回 `{"available": false, "info": "异常类型"}`，不返回堆栈或凭据。

**本轮指标口径 = 任务书点名的六类**（QPS、路由 P50／P95／P99、错误率、问答成功／失败、
限流命中）。召回数（`evidence` 条数）、LLM 调用次数／失败与耗时已由 `qa_service` 的
`问答链路耗时分解` 日志逐请求记录，**未在本轮做进程内聚合**；若后续需要 LLM 失败率／
知识库命中率的滚动指标，可在 `observability.py` 增加对应计数器，而不改变接口形状。

### 6.2 实测

真实请求后 60 s 窗口：`qa.success=1`、`POST /api/qa/ask` 的 P50／P95／P99 均为
10758.3 ms、错误率 0、限流命中 0；健康路由样本 P50 97.5 ms、P95 497.2 ms（含冷启动那次）。
与访问日志的 10758.3 ms 一致，说明指标记录与日志计时同源。

路由面复核：`GET /openapi.json` 实测 **30 条路径／32 个操作**，`/api/health` 在列、
`/api/metrics` 不在列；直接请求 `/api/metrics` 返回 **404**。即 8.2 的实现没有改变
OpenAPI 契约，也没有触发「未登记新增接口」的登记需求。

| 错误率 | `metrics.requests.error_rate` | 5 分钟窗口 > 5% | P2 | 查 `access status=5xx` 与错误日志的 request ID |
| `POST /api/qa/ask` P95 | `metrics.routes` | > 60 s 连续 3 次 | P2 | 查 LLM 调用与检索子进程；确认是否模型冷启动 |
| 问答失败数 | `metrics.qa.failure` | 10 分钟内 ≥3 | P2 | 按错误码 3001／3002／3003 分流 |
| 限流命中 | `metrics.rate_limit.hits` | 1 分钟内 > 20 | P3 | 判断是否压测／前端重试风暴；默认 60 次/60 s |
| 磁盘可用 | 巡检脚本 | < 5 GiB 或 < 10% | P1 | 清理备份历史（按保留策略）／扩容 |
| 内存可用 | 巡检脚本 | < 10% | P2 | 查残留子进程；重启后端 |
| MySQL／Neo4j 端口 | 巡检脚本 | 连续 2 次不可达 | P1 | 查 MySQL84 服务；Neo4j 见 README 的 WSL 保活 |
| 最近备份时长 | `备份/` 目录 | > 7 天 | P2 | 运行 `工具/备份.ps1` 并核对 manifest |
| 日志接近轮转阈值 | 巡检脚本 | 单文件 ≥90%×10 MiB | P3 | 属正常轮转；确认磁盘与 `backup_count` |

**告警内容纪律**：只带时间、指标名、阈值、当前值、请求 ID／路由模板；**不带问题原文、
不带口令、不带数据库连接串**。P1 在 15 分钟内响应，P2 在 1 小时内，P3 当日处理；
告警恢复需记录处置人与时间（可写在 `过程记录/`，不入公开仓库）。

## 十二、11.4 日志轮转

* 后端使用 `logging.handlers.RotatingFileHandler`：单文件 **10 MiB**、保留 **5** 个历史文件、
  UTF-8；`app.log` → `app.log.1`…`app.log.5`，不会无限增长；
* **只有配置了非空 `log_path` 才落文件**；未配置时行为与改动前一致（只出 stderr）；
* 容器形态把 `log_path` 指到挂载卷（`backend-logs`），否则容器删除即丢日志；
* `工具/运维巡检.py` 会报告当前文件占阈值百分比与已有轮转文件数；达到 90% 只提示，
  不手工删日志、不绕过 handler；
* 磁盘预算：单实例最多约 6×10 MiB＝60 MiB；备份目录按 10.3 的保留策略另行管理。

**不要做的事**：不在服务运行时手工重命名／删除日志文件（Windows 文件句柄会失败或造成
轮转错乱）；不把 `log_path` 指向网络盘；不在日志中记录问题原文、请求体或凭据。
