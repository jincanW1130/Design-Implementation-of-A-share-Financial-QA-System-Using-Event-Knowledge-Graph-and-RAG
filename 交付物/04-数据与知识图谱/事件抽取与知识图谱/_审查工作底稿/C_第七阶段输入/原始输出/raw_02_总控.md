## 九、数据设计概要

### 9.1 MySQL 核心表（六张）

MySQL 收敛为六张表，分别是 user、document、document_chunk、question、answer、answer_evidence。与 v1.0 相比，新增了 document_chunk 与 answer_evidence，删除了 history 表，question 与 answer 的职责保持稳定；v2.1 新增的 session_id 是 question 表的字段而不是新表，数据截止时间 data_cutoff_time 是数据集版本级属性、不属于任何表，因此表数量仍为六张。六张表**全部建立**：user 表在第一版不启用登录业务时保持为空、不写入数据，不采用"按条件决定是否建表"的做法，这样表数量、外键关系与 schema 在任何情况下都一致，论文口径与答辩口径统一为"六张表"。

| 表名 | 用途 | 关键字段 |
| --- | --- | --- |
| user | **始终建立**。仅在启用登录功能时使用，存储账号与登录信息；第一版不启用注册与登录，该表保持为空、不写入数据，以保证表数量恒为六张、schema 稳定 | user_id（主键）、username、password_hash、create_time |
| document | 存储导入的财经文本及其元数据，是向量化与事件抽取的数据来源 | doc_id（主键）、title、content、source、url、publish_time、ingest_time（入库时间）、category、company_list、create_time |
| document_chunk | 存储文档切分后的文本块，是向量检索与证据定位之间的中间层 | chunk_id（主键）、doc_id（外键）、chunk_index、content、token_count、vector_id |
| question | 存储用户提交的问题；task_type、gold_hop_depth、time_constraint 为测试集标注字段，非测试集题目留空 | question_id（主键）、user_id（外键，登录未启用时可为空）、session_id（浏览器生成的 UUID）、question_text、task_type、gold_hop_depth、time_constraint、ask_time |
| answer | 存储系统生成的回答及其生成信息 | answer_id（主键）、question_id（外键）、answer_text、graph_path（第一版以 JSON 文本存储，后续可归一化为独立表）、is_graph_extended（本次回答是否使用了图谱扩展，0／1；决定证据区域显示路径还是显式标注）、model_name、prompt_version、create_time |
| answer_evidence | 存储答案与证据文档、证据文本块之间的关联，是证据追溯的核心表 | answer_id（外键）、doc_id（外键）、chunk_id（外键）、rank、evidence_type |

各表的职责可以进一步理解为：document 保存原始文本与来源信息，是文本内容的权威来源，其中 publish_time 表示文档发布时间、ingest_time 表示该文档的入库时间，数据集版本级属性 data_cutoff_time 不存放在该表中；document_chunk 保存切分结果，使检索命中的粒度从整篇文档缩小到文本块；question 保存问题本身以及测试集标注信息，task_type、gold_hop_depth、time_constraint 三个字段为第 12.2 节的多标签测试集服务，普通用户提问时这三项留空，其中 gold_hop_depth（标注路径深度）是问题的金标准属性，记录该问题在客观上最少需要沿几条图谱关系才能完整得到答案，与 12.6 节消融实验中的检索深度不是同一概念；session_id 由前端首次访问时生成并存于浏览器，用于隔离不同匿名会话的历史记录；answer 保存回答正文、图谱路径与生成信息，其中 model_name 与 prompt_version 用于实验期间固定模型与 Prompt 版本；answer_evidence 保存答案引用了哪些文档与哪些文本块，以及它们的排序与证据类型，用于回答页面的证据列表与实验中的证据召回统计。

历史记录不需要独立的 history 表。用户查看历史问答时，系统按 question 与 answer 的关联关系查询：以 question_id 连接 question 与 answer，即可得到问题、提问时间、回答与生成信息；需要展示证据时再通过 answer_id 关联 answer_evidence，并进一步连接 document 与 document_chunk 得到文档标题、来源、发布时间与原文链接。第一版不启用登录，查询历史记录时按当前浏览器的 session_id 过滤，因此不同匿名会话之间不会互相看到彼此的问答历史，user_id 在该场景下为空。这样设计既避免了 history 表与 question、answer 表之间的信息重复，也避免了三张表之间出现不一致的可能，同时不需要新增会话表。

向量检索与原文之间的映射链路是证据追溯的数据基础，链路如下：

```text
Document（原始文章）
    ↓ 切分
Chunk（文本块，记录 chunk_id 与 doc_id）
    ↓ Embedding
Embedding（向量）
    ↓ 写入
向量索引（FAISS，向量附带 vector_id）
```

检索时的反向定位链路如下：

```text
用户问题向量
    ↓ 相似度检索
返回 vector_id
    ↓
chunk_id
    ↓
doc_id
    ↓
原始文章（标题、来源、URL、publish_time）
```

也就是说，向量索引中不保存权威文本，只保存向量与索引结构；向量与原文的对应关系由 vector_id、chunk_id、doc_id 三级编号串联。回答中的每一条文本证据都可以沿着这条链路定位到原始文章，这正是 9.1 节保留 document_chunk 表、并把 vector_id 写入该表的原因。

表中字段可以根据实现情况微调，但表的职责与数据来源保持一致。若在开发过程中新增字段，需要在论文的数据库设计章节同步说明，避免文档与实现不一致。

### 9.2 Neo4j 本体设计

#### 9.2.1 实体类型（6 类）

实体类型由 v1.0 的 8 类收敛为 6 类，标签统一使用英文命名，便于在 Neo4j 与 Cypher 中直接使用。

| 实体类型（标签） | 中文名称 | 说明 |
| --- | --- | --- |
| Company | 公司 | 上市公司及在财经信息中出现的其他企业主体，是图谱的核心节点，以 stock_code 作为稳定业务唯一标识 |
| Person | 人物 | 公司高管、监管机构人员等与事件相关的人物 |
| Industry | 行业 | 公司所属行业以及事件涉及的行业 |
| Institution | 机构 | 监管机构、交易所、中介机构等 |
| Event | 事件 | 财经事件，本课题的核心知识单元 |
| Policy | 政策 | 与公司或行业相关的政策文件及其主题 |

Product（产品）与 Location（地点）列为可扩展类型，不进入第一版的本体、抽取规则与评测范围。收敛的理由是工作量控制：每增加一类实体，都需要配套的抽取规则、消歧策略、数据来源与评测工作量，产品名称的边界尤其模糊（产品型号、服务名称、业务板块之间难以稳定区分），地点在财经事件中也往往不是回答问题的必要信息。把这些类型登记为可扩展项，可以在论文的"总结与展望"中说明后续扩展方向，而不占用第一版的开发与评测预算。

#### 9.2.2 核心事件类型（8 种）

- 业绩事件
- 监管事件
- 股权事件
- 投资并购事件
- 重大合同事件
- 产品事件
- 政策事件
- 重大经营事件

第一版固定为以上 8 种核心事件类型，作为抽取、标注与评测唯一的 schema，不再保留浮动的事件类型数量表述。理由：人工标注、抽取 Precision／Recall／F1 与分组统计都需要固定 schema，浮动范围会使标注与评测口径不可复现。事件类型与实体类型不同：实体类型收敛为 6 类，事件类型固定为 8 种，原因是财经问答中的问题大多围绕"发生了什么"展开，事件类型的细分直接决定问题分类与检索策略是否能够命中，因此这一维度保留必要的细度。

#### 9.2.3 核心关系清单

核心关系由 v1.0 的 9 条中文关系改写为 9 条英文命名的关系，并完成去重，最终清单如下：

```text
(Company)-[:BELONGS_TO {valid_from, valid_to, source_doc_id, source_chunk_id, confidence}]->(Industry)
(Company)-[:SUPPLIES {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:CUSTOMER_OF {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:COMPETES_WITH {source_doc_id, source_chunk_id, confidence}]->(Company)
(Company)-[:HAS_EXECUTIVE {source_doc_id, source_chunk_id, confidence}]->(Person)
(Company | Person | Institution)-[:PARTICIPATES_IN {role, source_doc_id, source_chunk_id, confidence}]->(Event)   // role ∈ {主体, 合作方, 涉及方, 监管方, 受影响方}
(Event)-[:ISSUED_BY {source_doc_id, source_chunk_id, confidence}]->(Institution)                                 // 仅政策事件与监管事件
(Event)-[:RELATED_TO {source_doc_id, source_chunk_id, confidence}]->(Policy)
(Event)-[:EVIDENCED_BY]->(Document)                                                                              // 事件与其证据文档；本身即证据关系，不重复携带 source_doc_id
```

各条关系的含义与用途如下表。

| 关系 | 方向 | 属性 | 说明 |
| --- | --- | --- | --- |
| BELONGS_TO | Company → Industry | valid_from、valid_to、source_doc_id、source_chunk_id、confidence | 公司所属行业，带有效时间区间，用于判断关系在查询时间点是否成立；若行业归属来自外部行业分类而非文本抽取，该分类文件同样作为一份 Document 入库，source_doc_id 指向它，保证证据链不断 |
| SUPPLIES | Company → Company | source_doc_id、source_chunk_id、confidence | 供应商关系，A 公司向 B 公司供货；方向按信息来源标注，不做双向冗余存储 |
| CUSTOMER_OF | Company → Company | source_doc_id、source_chunk_id、confidence | 客户关系，与供应商关系互为反向，本课题按抽取结果确定方向，避免同一条关系存两份 |
| COMPETES_WITH | Company → Company | source_doc_id、source_chunk_id、confidence | 竞争关系，通常为对称关系，第一版按抽取方向存一条 |
| HAS_EXECUTIVE | Company → Person | source_doc_id、source_chunk_id、confidence | 公司高管任职关系，必须带齐证据三元组，人物与公司之间的职务信息记录在文档与事件中 |
| PARTICIPATES_IN | Company／Person／Institution → Event | role、source_doc_id、source_chunk_id、confidence | 公司、人物或机构参与事件，role ∈ {主体, 合作方, 涉及方, 监管方, 受影响方}；同一机构为发布／作出方时只写 ISSUED_BY，不重复写本关系 |
| ISSUED_BY | Event → Institution | source_doc_id、source_chunk_id、confidence | 政策事件与监管事件中政策的发布机构或监管处罚的作出机构，表示该机构是发布／作出方；其他事件类型不产生该关系 |
| RELATED_TO | Event → Policy | source_doc_id、source_chunk_id、confidence | 事件与相关政策之间的关联，必须带齐证据三元组 |
| EVIDENCED_BY | Event → Document | 无（本身即事件到文档的证据关系，不再重复携带 source_doc_id） | 事件与其证据文档之间的关联，一个事件可以对应多份文档 |

v1.0 中的 (Event)-[:INVOLVES]->(Company) 已删除。删除的理由是：它与 PARTICIPATES_IN 表达同一信息，只是在方向上相反；同时保留两条方向相反的关系意味着同一条事实需要在图谱中写入两份，任何一次修正都必须同时修改两个位置，容易出现更新不一致，而且会让路径计数、事件参与主体统计与去重逻辑出现重复计算。反向查询并不需要额外的关系：需要查找"某个事件涉及哪些主体"时，用 Cypher 从 Event 节点反向遍历 PARTICIPATES_IN 即可得到，例如 MATCH (e:Event {event_id: $event_id})<-[:PARTICIPATES_IN]-(p) RETURN p。事件参与主体不再限定为公司：PARTICIPATES_IN 的定义域为 Company | Person | Institution → Event，role ∈ {主体, 合作方, 涉及方, 监管方, 受影响方}；participants 不再作为事件属性存储，事件参与主体统一由 PARTICIPATES_IN 关系与 ISSUED_BY 关系表达，角色信息写在关系属性 role 中；这样参与主体既不会在属性与关系之间重复，也可以在查询时按角色过滤。为避免同一条事实写两份，去重规则为：同一机构既是政策或监管事件的发布／作出方又参与该事件时，只写 ISSUED_BY，不再重复写 PARTICIPATES_IN；"监管方"这一 role 仅用于"参与事件但不是发布／作出方"的机构。

所有抽取事实统一保留证据，这是图谱从"关系图"变为"有证据的关系图"的关键。除 EVIDENCED_BY 外，其余 8 条核心语义关系统一携带 source_doc_id、source_chunk_id 与 confidence 三项证据属性，三项证据属性是必需属性而不是可选补充；EVIDENCED_BY 本身承担事件与证据文档之间的关联作用，因此不再重复携带 source_doc_id。其中 BELONGS_TO 另带 valid_from、valid_to，若行业归属来自外部行业分类而非文本抽取，该分类文件同样作为一份 Document 入库，source_doc_id 指向它，保证证据链不断；HAS_EXECUTIVE、ISSUED_BY、RELATED_TO 同样必须带齐三项证据属性。这样处理之后，系统对任意一条事实都能回答"来自哪篇文档、哪个文本块、置信度多少"，而不是只给出一个无法核查的结论，与第十三章"答案＋文本证据＋图谱路径"的闭环一致。

一个事件可以对应多份文档，公告、多篇报道与政策文件都通过 EVIDENCED_BY 挂在同一个事件节点上，示意如下。

```text
                     ┌──────────────────────────┐
                     │ Event：监管处罚事件       │
                     │ event_time = XXXX-XX-XX  │
                     └────────────┬─────────────┘
                                  │ EVIDENCED_BY
        ┌─────────────────────────┼─────────────────────────┐
        ↓                         ↓                         ↓
┌───────────────┐        ┌───────────────┐        ┌───────────────┐
│ Document：公告 │        │ Document：报道 │        │ Document：报道 │
│ publish_time   │        │ publish_time   │        │ publish_time   │
│ = XXXX-XX-XX   │        │ = XXXX-XX-XX   │        │ = XXXX-XX-XX   │
└───────────────┘        └───────────────┘        └───────────────┘
```

该结构同时完成了时间归一化：事件发生时间存放在 Event 节点，公告、媒体报道与政策文件的发布时间统一存放在各自 Document 节点的 publish_time 上，来源类型由 Document.source 与 category 区分，不再单独定义"信息发布时间"；事件不再被压缩到一个文档上，也不再只保留一个时间字段。同一事件的多篇文档可以按发布时间排序，用户看到的是"事件发生时间 + 各来源的发布时间"这一组完整的时间信息。

#### 9.2.4 事件属性

事件不能只做一个节点。如果图谱中只写成"A 公司 → 监管处罚"，那么系统无法回答事件发生的时间、涉及哪些主体、由哪个机构发布、依据什么来源，也无法进行时间约束检索，更无法追溯到原始公告，所谓"事件驱动"就只剩一个空标签。因此事件必须作为带属性的知识单元存在。v2.0 对事件属性做了瘦身，核心属性只有以下六项。

| 属性 | 含义 | 监管处罚事件示例 |
| --- | --- | --- |
| event_id | 事件的唯一标识 | EVT-0001 |
| event_type | 事件类型，取值来自核心事件类型 | 监管事件 |
| event_name | 事件名称 | 某公司因信息披露违规被出具警示函 |
| event_time | 事件发生时间 | XXXX-XX-XX |
| description | 事件描述 | 一句话说明事件经过 |
| confidence | 抽取置信度 | 0.0～1.0 之间的数值 |

除以上六项核心属性外，trigger（触发词）作为可选辅助字段保留，仅用于抽取调试与错误分析，不作为查询依据，也不进入检索与实验的判定逻辑。participants 与 publish_time 已从事件属性中移除：participants 由 PARTICIPATES_IN 关系（含 role 属性）与 ISSUED_BY 关系共同表达，事件与参与主体的对应关系不再以数组形式存放；publish_time 与 source、url 一起归属 document，事件与文档之间用 EVIDENCED_BY 关系表达，从而支持一个事件挂多份文档。这样处理之后，事件节点的属性数量可控，属性与关系各司其职，同一信息不会在图谱中出现两个互相矛盾的副本。

以"监管处罚事件"为例，事件节点的展开形式如下：

```text
监管处罚事件
│
├── 事件主体：A公司（PARTICIPATES_IN，role = 主体）
├── 处罚机构：某监管机构（ISSUED_BY，本事件属监管事件，该机构为处罚作出方，不再重复写 PARTICIPATES_IN）
├── 事件时间：XXXX-XX-XX
├── 事件类型：监管处罚
├── 事件描述：……
└── 证据文档：公告（EVIDENCED_BY → document.doc_id）
```

补充说明：事件中的具体日期在最终数据集确认后填写，本文件不提前填入未经核实的数字。confidence 字段用于标记抽取结果的可靠程度，在问答与实验分析中可以据此过滤低置信度事件。

#### 9.2.5 实体消歧与事件去重

实体消歧解决"同一个实体被抽成多个节点"与"不同实体被合并成一个节点"两类问题。财经文本中，同一家公司在不同来源中可能以全称、简称、别名或历史名称出现，例如公司更名前后两个名称同时出现在数据集中；反过来，不同公司也可能因为简称相似而被误判为同一家企业。本课题的实体对齐以 stock_code 为锚：Company 节点以 stock_code 作为稳定业务唯一标识，属性包括 stock_code、company_name、short_name、aliases（数组，含历史名称）与 exchange。抽到的公司名称先与别名表匹配，匹配成功则归并到对应的 stock_code 节点；匹配失败进入待消歧列表，人工确认后再写入图谱。

公司唯一标识之所以必须用股票代码，是因为 A 股公司存在更名、简称变化、同名与全称／简称不一致的情况：名称会随时间变化，而股票代码在数据集覆盖的时间范围内保持稳定。图谱内部以股票代码定位公司，名称与别名作为属性用于展示与匹配，这直接影响实体对齐、去重、图谱准确性与检索准确性。若直接用公司名称当主键，一旦公司更名，图谱中旧名称节点与新名称节点会同时存在，供应商、客户、事件参与主体等关系会被拆到两个节点上，多跳查询与事件统计都会出现遗漏或重复。

事件去重解决"同一个事件被抽成多个事件节点"的问题。同一件事通常同时出现在公告与多篇报道中，如果不去重，图谱中会出现多个描述相同、时间相近、参与主体相同的事件节点，导致事件数量统计虚高、检索结果重复、多跳路径出现多条等价路径，最终影响实验结论。本课题的事件去重规则是：按 event_type + 参与主体 + 时间窗口 + 触发词相似度判定同一事件的多来源描述，四项条件同时满足时判定为同一事件并合并；合并后保留全部证据文档，通过 EVIDENCED_BY 关系全部挂在合并后的事件节点上，发布时间最早的一份作为主要来源展示，其余来源作为补充证据保留。合并动作记录在抽取日志中，便于失败案例分析时核查。

实体消歧与事件去重是财经知识图谱构建中必须单独处理的一环，不能寄希望于后续查询阶段自动解决。这一环节的工作量计入第 6 阶段"事件抽取与知识图谱"的工期，评价方式与 12.3 节的抽取评测集共用同一套人工标注数据：Dev 集（50～100 条，建议 60 条）用于迭代核查，Test 集（200 条）在规则冻结后一次性评测；实体层面检查是否合并正确，事件层面检查是否多抽或漏并。

## 十、时间维度设计

### 10.1 四种时间及其归属层级

财经信息的时间信息往往不止一个。本课题至少区分以下四种时间，并明确每种时间存放在哪一层，避免把不同含义的时间混在同一个字段上。

| 时间类型 | 归属层级 | 含义 | 示例 | 主要用途 |
| --- | --- | --- | --- | --- |
| 事件发生时间 | Event 节点的 event_time | 事件实际发生的时间 | 2025-03-01 | 按事件时间做时间范围过滤，并作为"最新／最近／近期"的判定依据 |
| 文档发布时间 | Document 节点的 publish_time | 公告、媒体报道或政策文件的发布时间 | 2025-03-05 | 判断信息何时进入公开渠道，并区分原始信息与二次报道 |
| 关系有效时间 | 关系属性 valid_from、valid_to | 关系成立与失效的时间区间 | 某年度内的行业归属 | 判断关系在查询时间点是否有效 |
| 数据截止时间 | 数据集版本级属性 data_cutoff_time | 数据集版本人为确定的覆盖截止边界 | 2026-09-25（v1.0 实际取值） | 作为"最新／最近／近期"等相对时间表述的基准 |

四种时间的归属层级是 v2.0 的重点：事件发生时间存放在 Event 节点；公告、媒体报道与政策文件的发布时间统一存放在 Document 节点，由 publish_time 表示，来源类型由 Document.source 与 category 区分，不再单独定义"信息发布时间"；关系有效时间以关系属性 valid_from 与 valid_to 表达，目前用于 BELONGS_TO 这类随时间变化的关系；数据截止时间是数据集版本级属性，与 dataset_version 成对记录在数据集元信息中，不属于任何表，详见 10.3 节。时间信息按层级分开存放之后，同一份文档可以支撑多个事件，同一个事件也可以挂多份文档，事件时间不再被压成单值，文档发布时间也不会被误当作事件发生时间。

### 10.2 时间线示例与时间约束检索

一条典型的时间线如下：

```text
2025-03-01
事件发生

2025-03-05
公司发布公告

2025-03-06
媒体报道
```

当用户提出"2025年3月以后发生了哪些相关事件？"时，系统需要按照以下步骤处理：第一步，问题分析识别出时间约束（2025 年 3 月以后）与查询目标（相关事件），必要时识别问题中的实体；第二步，用问题与实体关键词进行文本检索，得到候选文档；第三步，进入知识图谱，按事件发生时间（event_time）过滤事件节点，并沿 PARTICIPATES_IN、RELATED_TO 等关系做扩展；第四步，对同一事件的多条来源按文档发布时间排序并去重，因为同一事件可能同时存在公告与多篇报道；第五步，把时间信息随证据一起送入证据融合与答案生成环节。

需要强调的是，"最新""最近""近期"这类相对时间表述一律以 event_time 判定，不以 publish_time 判定：最新取符合条件的、event_time 最大的事件，最近取 event_time ∈ [data_cutoff_time − 30 天, data_cutoff_time]，近期取 event_time ∈ [data_cutoff_time − 90 天, data_cutoff_time]，具体规则见 10.3 节；答案中需注明所用判定区间与数据截止时间。

如果缺少时间维度的建模，系统只能按语义相似度返回文本，无法回答"某时间之后发生了什么"，也无法区分事件发生与文档发布的时间差。因此答案中的每一条证据都需要标注其对应的时间类型，避免把文档发布时间当作事件发生时间；相对时间表述按 event_time 判定，而"某份材料何时公开"按 publish_time 判断，两者不得混用。对于示例中的情况，若用户询问的是公告发布之后公开的材料，2025-03-05 的公告与 2025-03-06 的报道都应被纳入；若用户询问的是 2025-03-01 至 2025-03-04 期间发生的事件，则只能命中 event_time 落在该区间的事件，不能被后续报道误导。

### 10.3 数据截止时间 data_cutoff_time

系统不是实时行情数据库，也不承诺数据持续更新，因此在时间维度中设置数据截止时间 data_cutoff_time，作为所有相对时间表述的基准。具体做法如下。

第一，data_cutoff_time 不属于任何表，而是数据集版本级属性，与 dataset_version 成对记录在数据集元信息中（配置文件 ＋ 数据集说明文档），例如 dataset_version = v1.0、data_cutoff_time = 2026-09-25。document 表不存放该字段，只记录每篇文档的入库时间 ingest_time；数据集边界是构建数据集时人为确定的版本属性，不再采用"取所有文档中的最晚时间"的推导口径。界面固定显示"数据截至：YYYY-MM-DD"；第 5 阶段封版的数据集 v1.0 取 2026-09-25，已据此填入，本文件不再以 YYYY-MM-DD 占位。

第二，"最新""最近""近期"等相对时间表述，一律以 event_time 判定，并以数据截止时间为基准解释，而不是以系统运行当天为基准，也不是以 publish_time 判定。判定规则如下表。

| 表述 | 判定规则 |
| --- | --- |
| 最新 | 符合条件的、event_time 最大的事件（并列时全部返回） |
| 最近 | event_time ∈ [data_cutoff_time − 30 天, data_cutoff_time] |
| 近期 | event_time ∈ [data_cutoff_time − 90 天, data_cutoff_time] |

例如用户询问"A 公司最近发生了哪些事件"时，系统按上表把"最近"解释为 event_time 落在数据截止时间前 30 天以内，并在答案中注明所用判定区间与数据截止时间，避免用户误以为系统掌握当下的实时信息。

第三，提示词、检索与答案生成一律以该版本属性为相对时间基准：data_cutoff_time 与 dataset_version 一起写入提示词，要求模型不得使用数据截止时间之后的信息，也不得在证据不足时用训练语料中的时间信息补全答案。

第四，论文与答辩中明确说明数据的时间边界：数据集覆盖的时间范围、数据截止时间、数据来源的发布时间分布都需要写清楚。这样处理可以避免答辩时被追问"你的数据最近到什么时候"，也可以避免把离线数据集包装成实时系统。

| 最近 | event_time ∈ [data_cutoff_time − 30 天, data_cutoff_time] |
| 近期 | event_time ∈ [data_cutoff_time − 90 天, data_cutoff_time] |

例如用户询问"A 公司最近发生了哪些事件"时，系统按上表把"最近"解释为 event_time 落在数据截止时间前 30 天以内，并在答案中注明所用判定区间与数据截止时间，避免用户误以为系统掌握当下的实时信息。

第三，提示词、检索与答案生成一律以该版本属性为相对时间基准：data_cutoff_time 与 dataset_version 一起写入提示词，要求模型不得使用数据截止时间之后的信息，也不得在证据不足时用训练语料中的时间信息补全答案。

第四，论文与答辩中明确说明数据的时间边界：数据集覆盖的时间范围、数据截止时间、数据来源的发布时间分布都需要写清楚。这样处理可以避免答辩时被追问"你的数据最近到什么时候"，也可以避免把离线数据集包装成实时系统。

### 12.2 测试集（多标签）

v2.0 取消 v1.0 的六分类表格，改为多标签体系。每道题打三个标签：任务类型（事实型／事件型／关系型）、路径深度（gold_hop_depth：0-hop／1-hop／2-hop）、时间约束（无／有）。测试集规模为：完整版 120 题（核心 108 + 压力 12），缩减版 60 题（核心 54 + 压力 6）。

路径深度标签使用 question 表的 gold_hop_depth 字段（标注路径深度），定义为：该问题在客观上最少需要沿几条图谱关系才能完整得到答案。判定规则如下。

- 0-hop：仅凭原始文本证据即可完整回答，不需要任何图谱关系。
- 1-hop：至少需要沿 1 条图谱关系才能完整回答。
- 2-hop：至少需要沿 2 条图谱关系才能完整回答。

标注约定：以"最少必需证据"为判据；存在多条可行路径时取最少跳数；若图谱中虽有关系但文本证据已足以回答，标 0-hop。必须明确区分：gold_hop_depth 是问题的金标准属性；消融实验 B／C 组的 1-hop／2-hop 是实验自变量（系统的检索深度）。两者不得使用同一字段、同一术语或同一统计口径；原设计把两者都叫"路径深度"，是方法泄漏风险来源，已在 v2.1 中消除。

完整版 120 题的构成为：9 个"任务类型 × 路径深度"组合各 12 题（3 × 3 × 12 = 108 题），构成核心测试集；另加 12 题"关系型 + 2 跳 + 有时间约束"压力测试子集，合计 120 题。缩减版 60 题的构成为：9 个组合各 6 题（核心 54 题），另加 6 题同一压力测试子集，合计 60 题。

之所以改为多标签，是因为 v1.0 的六分类彼此重叠，会导致分组统计口径歧义。例如"某公司被处罚后其供应商有哪些相关事件"这一道题，同时属于事件问题、关系问题、两跳问题、时序问题与综合问题，在六分类体系下只能被放进其中一类，一旦放入某一类，其他类别的统计就会漏掉这道题，不同的人在复现实验时也可能给出不同的归类结果。采用多标签之后，每道题可以同时计入多个子集，分组分析才严谨：同一道题既进入"关系型"子集，也进入"2 跳"子集，还进入"有时间约束"子集，各子集之间允许重叠，统计时分别按子集计算指标，不再需要人为决定"这道题主要算哪一类"。

测试集中每道题记录以下内容：题干、三个标签、参考答案、应命中的证据文档编号与文本块编号。证据以 document 与 document_chunk 的编号记录，与第 9.1 节的映射链路一致，这样检索指标与证据召回指标可以直接计算，不需要在实验阶段重新人工判断"应该命中哪些文档"。测试集从真实财经文本出发构建，题目、参考答案与证据编号在实验开始前固定，对比实验与消融实验重复使用同一套题目，避免不同实验使用不同题目导致结果不可比。若进度紧张，按 12.2 节的缩减版执行，先把 60 题（核心 54 + 压力 6）做扎实，再按同一套标签规则扩充到 120 题（核心 108 + 压力 12），但不得改变标签体系与题目记录格式。

每道测试题标注的 gold 证据文本块数量不得超过实验设定的 K（Top-K 的取值，见 12.4 节）。若某题的原始证据数量超过 K，则在测试集构建阶段合并相邻证据块或重新定义证据粒度，使 Complete Evidence Recall@K 在定义上可达；不得保留 gold 证据数大于 K 的题目，否则该题的这一指标必然为 0，会系统性压低指标并造成误判。

### 12.3 抽取评测集

抽取评测集用于验证 RQ1，回答"财经事件能否被稳定地结构化表示"这一问题。评测集分为开发集 Dev 与测试集 Test 两段，从最终数据集中抽取，规格与规则如下表。

| 集合 | 规模 | 用途与规则 |
| --- | --- | --- |
| 开发集 Dev | 50～100 条（建议 60 条） | 从最终数据集中抽取，用于抽取规则与 Prompt 的迭代调优；调优过程在论文中说明 |
| 测试集 Test | 200 条 | 独立于 Dev，在抽取规则与 Prompt 冻结后一次性评测，只测一次；Test 结果不得反馈用于再调优 |

两集合不得重叠，均记录文本编号；若确需修改规则，必须另行划定新的 Test 并在论文中说明，不得用原 Test 反复调参。标注总量约 250～300 条，计入"事件抽取与知识图谱"阶段的工期。

**"条"的口径（v2.7 澄清）**：本节所称"条"指**标注条目**，其单位是**文本块**（一个文本块一条），不是整篇文档。理由是：抽取评测要把金标准对齐到证据的最小单位，而 第12.7节 已把文本块定为"证据的最小单位"；若按"篇"计，250～300 条将要求同等数量的文档，与 第17节 的第一版 100 篇／第二版 500 篇口径无法自洽。据此，Dev 与 Test 的"不重叠"指**文本块不重叠**，Dev 与 Test 各自记录的"文本编号"即 `chunk_id`。第一版数据集已有 707 个文本块，容量充分。

标注内容为由作者人工标注六类实体、事件类型与论元、关系以及时间信息，作为金标准，然后用系统抽取结果与金标准对比，分别计算实体、事件、关系、时间四类任务的 Precision、Recall 与 F1。

评测集的字段与 9.2 节的本体保持一致：实体标注 Company、Person、Industry、Institution、Event、Policy 六类标签；事件标注 event_type、event_time 与参与主体及其角色；关系标注 9.2.3 节的 9 条核心关系及其方向；时间标注事件发生时间与文档发布时间。标注过程中发现的本体边界问题（例如某条文本中的关系无法归入 9 条核心关系）记录在标注说明中，用于在论文中讨论本体的适用边界，而不是临时增加关系类型。

没有抽取评测集，RQ1 无法成立：如果没有金标准，抽取质量只能靠零散的例子说明，无法给出可核查的数字，也无法解释后续问答实验中出现的错误有多少来自抽取环节。因此 Dev 与 Test 的人工标注工作必须完成，标注总量约 250～300 条，并计入"事件抽取与知识图谱"阶段的工期。标注完成后，评测集（Dev 与 Test）与被标注文本的编号一并保存在数据集目录中，作为交付物的一部分。

系统支持多模型切换，Embedding 模型与大语言模型都通过配置项接入，更换模型不需要修改前端代码。但实验期间必须固定同一套模型、参数与 Prompt：所有对比组与所有消融组使用相同的 Embedding 模型、相同的大语言模型与版本、相同的 temperature、相同的 Prompt 版本、相同的 Top-K 与相同的 Context Token Budget，否则实验不可复现，指标差异也无法归因到知识图谱这一变量上。每次实验运行记录配置快照与运行时间，配置快照随实验结果一并保存。

上下文预算的裁剪规则必须固定并写入论文：证据总量超出预算时，按固定优先级裁剪——先裁剪与问题实体无关的远端图谱路径，再按**向量检索的原始排名**从后往前裁剪文本块。关键约束是：裁剪必须发生在"证据排序"这一实验变量**之前**，且裁剪依据不得使用 E 组的证据排序结果，否则 D 组与 E 组最终送入模型的证据集合会不同，"E 只改变顺序"就不再成立。正确顺序是：候选证据生成 → 按固定规则裁剪到预算之内 → 得到 D 组与 E 组**完全相同**的证据集合 → D 组按固定的原始顺序送入大模型，E 组只在这一集合内部重新排序。所有对比组与消融组使用同一预算与同一裁剪规则。理由是：若不控制上下文预算，KG-RAG 会天然获得更多 token，无法把效果差异归因到"图谱结构"这一变量；若只规定不超过同一 token 上限而不规定超限时裁掉什么，不同组的裁剪结果同样不可比。

### 12.5 实验设置

| 编号 | 设置 | 说明 |
| --- | --- | --- |
| Baseline 1（闭卷 LLM，辅助基线） | 直接调用 LLM，不接入检索 | 辅助基线；因其依赖参数化知识且与数据集的时间边界不一致，不作为"KG-RAG 有效"的主要证据 |
| Baseline 2 | 普通 Vector RAG | KG 是否提供额外价值的主要对照 |
| Method | Vector RAG + 2-hop Event KG（**即 12.6 节的 C 组**） | 本课题方法。为使 Baseline 2 与 Method 的对比只改变"是否使用事件知识图谱"这一个变量，Method 采用 2-hop 图谱扩展，**不启用时间过滤、不启用 E 组的证据排序**；系统本身支持 D／E 两组的配置，那两组作为消融与进一步优化实验单独报告，不计入 Method 的定义 |

三组设置使用同一套测试集与同一评测口径，用于回答"是 LLM 本身有效、是 RAG 有效，还是知识图谱确实提供了额外价值"。**三组实验与消融 A～E 的对应关系必须写清楚：Baseline 2 ＝ A 组（Vector RAG），Method ＝ C 组（Vector RAG + 2-hop KG）。**因此 Baseline 2 与 Method 的对比等价于 A 与 C 的对比，唯一变量是"是否使用事件知识图谱"；在它之上再加时间过滤得到 D、再加证据排序得到 E，那两步的贡献分别由 C→D 与 D→E 回答，不混入 H1 的判定。回答 RQ2／H1 的主要证据是 Baseline 2 与 Method 的对比，Baseline 1 仅作辅助观察：它依赖参数化知识，且其训练语料的时间边界与数据集不一致，不能作为"KG-RAG 有效"的主要证据。三组实验的结果都按 12.2 节的多标签子集分别统计，而不是只给一个总体平均值：总体平均值会把不同难度、不同类型的题目混在一起，掩盖知识图谱在关系型、多跳型与时序型问题上的作用，也无法回答 H1 提出的问题。

### 12.6 消融实验

| 编号 | 配置 | 继承关系 | 目的 |
| --- | --- | --- | --- |
| A | Vector RAG | 基线 | 作为消融基线 |
| B | Vector RAG + 1-hop KG | A + 1-hop 图谱扩展 | 观察一跳图谱关系的贡献 |
| C | Vector RAG + 2-hop KG | A + 2-hop 图谱扩展（含 1-hop 结果） | 观察两跳关系扩展的贡献 |
| D | Vector RAG + 2-hop KG + 时间过滤 | D = C + 时间过滤，其余不变 | 观察时间约束的贡献 |
| E | Vector RAG + 2-hop KG + 时间过滤 + 证据排序 | E = D + 证据排序，其余不变 | 观察证据融合与排序的贡献 |

五组实验使用同一测试集、同一大模型、同一 Prompt 模板、同一 Context Token Budget 与同一裁剪规则、同一评分标准，逐项增加模块，记录每一步的效果变化。继承关系必须明确：C ⊆ D ⊆ E，D 在 C 的基础上只增加时间过滤，其余不变；E 在 D 的基础上只增加证据排序，其余不变。所有对比结果需要保留原始输出，便于在论文中给出可核查的数据。

关于路径深度的口径需要澄清：这里的 1-hop 指查询目标实体的直接关系，例如从 A 公司出发沿一条关系边找到其供应商；2-hop 指允许沿两条关系边扩展，例如从 A 公司出发先找到供应商，再沿第二条关系边找到供应商参与的事件或其他关联企业。2-hop 的检索结果包含 1-hop 的结果，也就是说 C 组是在 B 组的基础上继续扩展，而不是把 B 组的结果排除之后只看第二条边新引入的部分。这一口径决定了 B 组与 C 组的指标差异表示"在直接关系基础上继续扩展两跳带来的变化"，而不是"两跳独有的关系带来的变化"，在论文中必须明确写出。同时必须强调：B／C 组的 1-hop／2-hop 是实验自变量（系统的检索深度），与 12.2 节 question 表的 gold_hop_depth（标注路径深度，问题的金标准属性）不是同一概念，不得使用同一字段、同一术语或同一统计口径。

A～D 四组对应 RQ2 与 RQ3：A 为基线，B 与 C 观察系统检索深度的影响（对应 H2）；H3 由 C 与 D 的对比回答，因为这一对比的唯一变量是时间过滤，且两组的检索深度都固定为 2-hop；A 与 C 的对比**就是** 12.5 节 Baseline 2（＝A）与 Method（＝C）的对比，它为 RQ2／H1 提供主要证据，与三组对比实验是同一件事的两种表述，论文中不得写成两组互不相干的证据。

E 组单独列为"进一步优化实验"，不归入 RQ3。E = D + 证据排序：上下文预算的裁剪在排序之前完成，因此 D 与 E 使用**完全相同**的证据集合，E 只改变该集合内部的顺序与呈现顺序，不改变证据集合本身，也不改变图谱检索路径的深度，也不改变时间约束是否启用。如果把它并入 RQ3，就会把"图谱结构与时间约束带来的效果"与"排序策略带来的效果"混在一起，无法判断差异的来源。因此本课题在论文中把 E 组与 A～D 分开报告，作为一个独立的优化实验说明证据融合与排序的作用，并在结论中明确它不属于 RQ3 的研究范围。

### 12.7 评价指标与定义

评价指标分为检索指标、问答指标与系统指标三组，每一项都给出明确定义，评分标准在实验开始前固定。

检索指标四项，主口径统一为文本块级（document_chunk）：向量索引检索的单位是文本块，且测试集已记录 gold 证据的 document 与 chunk 编号，因此不再混用文本块级与文档级两种口径。定义如下。Recall@K（chunk 级）：Top-K 中命中的 gold 证据文本块数 ÷ 该问题 gold 证据文本块总数，按问题取平均。Precision@K（chunk 级）：Top-K 中属于 gold 证据的文本块数 ÷ K，按问题取平均。MRR（chunk 级）：第一个 gold 证据文本块所在排名的倒数，按问题取平均；前 K 内无 gold 证据则该问题记 0。Complete Evidence Recall@K（问题级）：该问题的 gold 证据文本块全部出现在 Top-K 中记 1，否则记 0，按问题取平均（原"Evidence Recall"更名为本名）。

两个层次的分工必须写明："召回了多少"由 Recall@K 承担，"是否全部召回"由 Complete Evidence Recall@K 承担，因此不再另设同义指标。文档级只在需要诊断时作为辅助口径使用，且必须在论文中单独标注，不得与 chunk 级混算。

**Top-K 证据集合的形成规则必须固定，四项检索指标都在这个集合上计算。**规则共五步。第一步，文本候选来自两路：向量检索按配置项返回候选文本块（候选数量记为 N），图谱扩展按关系的 source_chunk_id 指向的文本块并入候选。**D 组与 E 组另在本步对候选集合施加时间过滤（按组启用，规则见 第11.3节）；时间过滤作用于候选集合的成员，必须先于第二步的合并与去重**，否则 C 组与 D 组的最终证据集合将恒等、H3 失去可观察差异。N 与 K 在预实验中一起固定，且保证 N ≥ K。第二步，两路候选统一映射到 chunk_id 并按 chunk_id 去重：**同一个文本块无论被哪一路命中都只算一个证据**，重复命中既不重复计数、也不合并加权，避免同一个 chunk 在 Precision 与 Recall 中被算两次。第三步，去重后的候选集合按 12.4 节的固定裁剪规则裁剪到 Context Token Budget 之内；该规则与 K 的关系是——"先裁剪与问题实体无关的远端图谱路径"作用于图谱路径与事件三元组部分，"再按向量检索的原始排名从后往前裁剪文本块"就是本节的"按向量原始排名保留文本块"，其保留上限即 K。第四步，**保留到 K 个文本块这一步必须发生在 D／E 分组排序之前**，因此 D 组与 E 组得到**完全相同**的最终证据集合（大小不超过 K），E 组只改变该集合内部的顺序——若在排序之后才截取到 K，D 与 E 截出的前 K 个就可能不同，"E 只改变顺序"将不再成立。**本步与第一步的分工必须分清（v2.5 澄清）**：第一步的时间过滤作用于候选集合的成员，因此 C 组与 D 组的最终证据集合**可以不同**，这是 H3 可测的前提；本步的截取位置保证 D 组与 E 组的最终证据集合**必然相同**，这是 E 组单变量的前提。两条约束作用在不同的组对上，互不冲突，不得因为"E 只改变顺序"而把时间过滤也放到截取之后。第五步，最终证据集合既是四项检索指标的计算对象，也是送入大模型的文本证据上下文；图谱路径与事件三元组计入 Context Token Budget，但不计入检索指标的 K（检索指标只统计文本块级证据）。为保证 Precision@K 的分母为 K 且可跨题比较，预实验需固定 K、N 与 Context Token Budget，并保证每个问题的候选证据数不少于 K、预算至少能容纳 K 个文本块；候选证据不足 K 的题目在测试集构建阶段调整，不进入正式实验。**该约束只适用于测试集构建阶段（v2.5 澄清其边界）**：题目一旦入库，不得因该题实验时的实际候选数少于 K 而将其排除，空缺位置记为未命中并按原指标定义计算；否则会出现"系统没搜到 K 个就把题删掉"的选择偏差，使正式测试集因系统表现差而变简单。

问答指标三项，由人工按统一标准评分，每项取值为 0、1、2。Answer Accuracy：0 = 错误，1 = 部分正确，2 = 完全正确。Completeness：0 = 关键信息大量遗漏，1 = 基本覆盖，2 = 信息完整。Faithfulness：0 = 存在明显无依据事实，1 = 少量不严谨，2 = 完全基于证据。

评分方式：由作者按上述统一标准评分，并对不少于 20% 的样本间隔 3 天以上做二次复评，报告前后评分一致率，用于检验评分稳定性（intra-rater consistency）。两次评分不一致的样本由作者重新核对证据后给出最终分，并在实验记录中保留两次评分与不一致原因。本课题以单人复评（评分稳定性）作为既定设计，不得表述为"评分者一致性"或"评分信度"——单人复评无法证明评分者间信度（inter-rater reliability）。条件增强：若能有第二名评分者，则对同样的 20% 样本独立评分，计算加权 Cohen's Kappa（线性权重，0/1/2 为序数尺度），作为评分者间信度证据；无第二名评分者时不得声称信度。评分标准在实验开始前固定，不得在看到结果之后调整。若确实需要修改评分标准，必须在修改后重新执行全部评分，并在论文中说明修改原因与重评范围。

系统指标沿用第 7 章非功能需求的口径，并补足一项：响应时间一项沿用第 7 章"在统一的测试环境下记录平均回答耗时与 P95 耗时，并分别记录向量检索、图谱查询与大模型生成的耗时"的记录方式；并发能力一项沿用第 7 章"10 个并发用户下接口成功率不低于 95%"；此外本节新增一项补充口径"连续 100 次请求的成功率不低于 95%"，用于观察非并发条件下的接口稳定性，该项**不属于**第 7 章已有条目。两项口径均以"系统不崩溃、不出现数据错乱"为前提。三组指标同时覆盖检索方法、问答质量与软件系统表现，既满足方法层面的评价，也满足软件工程专业的系统评价要求。

### 12.8 图谱增强效果的判定规则

为了避免"看到结果再决定怎么解释"，知识图谱是否提供额外检索价值按以下规则判定，且**判定按子集分别进行**：对**关系型子集**（任务类型为"关系型"的题目）、**多跳型子集**（路径深度为 1-hop 或 2-hop 的题目，即 gold_hop_depth ≥ 1）、**时序型子集**（时间约束为"有"的题目）各自独立应用同一条规则——若 KG-RAG 在该子集上的 Complete Evidence Recall@K 高于 Vector RAG，且该子集的 Answer Accuracy 不下降（持平或提升），则判定知识图谱在该类问题上提供了额外检索价值。三个子集按 12.2 节的标签定义，**允许重叠**（同一道题可以同时属于多个子集）；"互不牵连"指判定与结论各自独立、不因一个子集的结果而改变另一个子集的判定，不指三个集合互斥。可以只有一个子集满足、两个满足或三个都不满足，不得把三个子集合并成一个整体来判定，否则"知识图谱只对某类问题有效"这一可能结果会被整体判定掩盖。该判定以核心测试集的 108 题为依据，压力测试子集仅作为附加观察参与讨论，不作为本节主体判定的依据。

该规则只规定判定方式，不预设提升幅度。本课题不预设"知识图谱一定能提升多少"，也不预设"哪一类问题上必然有效"：实验可能出现三种结果，一是多个子集上同时满足判定条件，说明知识图谱在这些子集上提供了额外价值；二是只有部分子集满足判定条件，说明知识图谱的作用集中在特定类型的问题上，论文按子集分别报告；三是没有任何子集满足判定条件，说明在该数据集与配置下知识图谱没有带来可观察的额外价值，这一结果同样按 12.7 节的指标如实报告，并按第十八章的分类归因方法分析原因。三种结果都是有效的实验结论，区分点在于是否用同一套指标、同一套配置与同一套判定规则给出结论。

### 12.9 定量实验问题与开放性问题的区分

定量实验只使用可核验、有明确证据的事实型问题，即答案能够在数据集文档中找到直接依据、可以人工判定正确与否的问题。示例包括：A 公司的供应商有哪些；A 公司什么时候发生该事件；A 公司参与了哪些事件；A 公司与 B 公司是什么关系；某事件之后又发生了哪些事件。这类问题有唯一的证据集合与可核查的参考答案，适合计算 Recall@K、Precision@K、MRR、Complete Evidence Recall@K 与 Answer Accuracy，也适合作为多标签子集分组统计的对象。

开放式分析问题不进入定量实验，只用于 Demo 展示与案例分析，最多保留 1～2 例。示例包括：A 公司被处罚后对 B 公司的潜在影响；该政策对某行业的长期影响如何判断。这类问题没有唯一答案，回答质量依赖模型的分析角度与措辞，无法用 12.7 节的 0/1/2 评分稳定衡量；同时这类回答必然包含模型分析成分，容易与公开事实混淆。因此这类问题必须在页面与答案中同屏标注"模型分析（非公开事实）"，只用于答辩演示、页面展示与失败案例分析，不作为核心准确率依据，也不参与 12.8 节的判定，不计入任何指标。

答辩演示与页面展示以事实型、事件型、关系型、时序型四类可核验问题为主，每类至少 2 例；上述开放式分析问题最多保留 1～2 例，并必须按前一段的要求标注"模型分析（非公开事实）"，不计入任何指标。

区分的意义在于保证实验结论可核查：定量实验部分报告的数字都有明确证据与人工参考答案支撑，开放式部分只展示系统的表达能力与证据追溯能力，不把开放性回答的效果折算成准确率。论文中两部分分开报告，实验章节给出定量结果，案例分析章节给出开放性问题与失败案例。

### 12.2 测试集（多标签）

v2.0 取消 v1.0 的六分类表格，改为多标签体系。每道题打三个标签：任务类型（事实型／事件型／关系型）、路径深度（gold_hop_depth：0-hop／1-hop／2-hop）、时间约束（无／有）。测试集规模为：完整版 120 题（核心 108 + 压力 12），缩减版 60 题（核心 54 + 压力 6）。

路径深度标签使用 question 表的 gold_hop_depth 字段（标注路径深度），定义为：该问题在客观上最少需要沿几条图谱关系才能完整得到答案。判定规则如下。

- 0-hop：仅凭原始文本证据即可完整回答，不需要任何图谱关系。
- 1-hop：至少需要沿 1 条图谱关系才能完整回答。
- 2-hop：至少需要沿 2 条图谱关系才能完整回答。

标注约定：以"最少必需证据"为判据；存在多条可行路径时取最少跳数；若图谱中虽有关系但文本证据已足以回答，标 0-hop。必须明确区分：gold_hop_depth 是问题的金标准属性；消融实验 B／C 组的 1-hop／2-hop 是实验自变量（系统的检索深度）。两者不得使用同一字段、同一术语或同一统计口径；原设计把两者都叫"路径深度"，是方法泄漏风险来源，已在 v2.1 中消除。

完整版 120 题的构成为：9 个"任务类型 × 路径深度"组合各 12 题（3 × 3 × 12 = 108 题），构成核心测试集；另加 12 题"关系型 + 2 跳 + 有时间约束"压力测试子集，合计 120 题。缩减版 60 题的构成为：9 个组合各 6 题（核心 54 题），另加 6 题同一压力测试子集，合计 60 题。

| 核心测试集 | 9 个"任务类型 × 路径深度"组合各 12 题 = 108 题 | 主结果以 108 题为准 |

测试集中每道题记录以下内容：题干、三个标签、参考答案、应命中的证据文档编号与文本块编号。证据以 document 与 document_chunk 的编号记录，与第 9.1 节的映射链路一致，这样检索指标与证据召回指标可以直接计算，不需要在实验阶段重新人工判断"应该命中哪些文档"。测试集从真实财经文本出发构建，题目、参考答案与证据编号在实验开始前固定，对比实验与消融实验重复使用同一套题目，避免不同实验使用不同题目导致结果不可比。若进度紧张，按 12.2 节的缩减版执行，先把 60 题（核心 54 + 压力 6）做扎实，再按同一套标签规则扩充到 120 题（核心 108 + 压力 12），但不得改变标签体系与题目记录格式。

每道测试题标注的 gold 证据文本块数量不得超过实验设定的 K（Top-K 的取值，见 12.4 节）。若某题的原始证据数量超过 K，则在测试集构建阶段合并相邻证据块或重新定义证据粒度，使 Complete Evidence Recall@K 在定义上可达；不得保留 gold 证据数大于 K 的题目，否则该题的这一指标必然为 0，会系统性压低指标并造成误判。

### 12.7 评价指标与定义

评价指标分为检索指标、问答指标与系统指标三组，每一项都给出明确定义，评分标准在实验开始前固定。

检索指标四项，主口径统一为文本块级（document_chunk）：向量索引检索的单位是文本块，且测试集已记录 gold 证据的 document 与 chunk 编号，因此不再混用文本块级与文档级两种口径。定义如下。Recall@K（chunk 级）：Top-K 中命中的 gold 证据文本块数 ÷ 该问题 gold 证据文本块总数，按问题取平均。Precision@K（chunk 级）：Top-K 中属于 gold 证据的文本块数 ÷ K，按问题取平均。MRR（chunk 级）：第一个 gold 证据文本块所在排名的倒数，按问题取平均；前 K 内无 gold 证据则该问题记 0。Complete Evidence Recall@K（问题级）：该问题的 gold 证据文本块全部出现在 Top-K 中记 1，否则记 0，按问题取平均（原"Evidence Recall"更名为本名）。

两个层次的分工必须写明："召回了多少"由 Recall@K 承担，"是否全部召回"由 Complete Evidence Recall@K 承担，因此不再另设同义指标。文档级只在需要诊断时作为辅助口径使用，且必须在论文中单独标注，不得与 chunk 级混算。

**Top-K 证据集合的形成规则必须固定，四项检索指标都在这个集合上计算。**规则共五步。第一步，文本候选来自两路：向量检索按配置项返回候选文本块（候选数量记为 N），图谱扩展按关系的 source_chunk_id 指向的文本块并入候选。**D 组与 E 组另在本步对候选集合施加时间过滤（按组启用，规则见 第11.3节）；时间过滤作用于候选集合的成员，必须先于第二步的合并与去重**，否则 C 组与 D 组的最终证据集合将恒等、H3 失去可观察差异。N 与 K 在预实验中一起固定，且保证 N ≥ K。第二步，两路候选统一映射到 chunk_id 并按 chunk_id 去重：**同一个文本块无论被哪一路命中都只算一个证据**，重复命中既不重复计数、也不合并加权，避免同一个 chunk 在 Precision 与 Recall 中被算两次。第三步，去重后的候选集合按 12.4 节的固定裁剪规则裁剪到 Context Token Budget 之内；该规则与 K 的关系是——"先裁剪与问题实体无关的远端图谱路径"作用于图谱路径与事件三元组部分，"再按向量检索的原始排名从后往前裁剪文本块"就是本节的"按向量原始排名保留文本块"，其保留上限即 K。第四步，**保留到 K 个文本块这一步必须发生在 D／E 分组排序之前**，因此 D 组与 E 组得到**完全相同**的最终证据集合（大小不超过 K），E 组只改变该集合内部的顺序——若在排序之后才截取到 K，D 与 E 截出的前 K 个就可能不同，"E 只改变顺序"将不再成立。**本步与第一步的分工必须分清（v2.5 澄清）**：第一步的时间过滤作用于候选集合的成员，因此 C 组与 D 组的最终证据集合**可以不同**，这是 H3 可测的前提；本步的截取位置保证 D 组与 E 组的最终证据集合**必然相同**，这是 E 组单变量的前提。两条约束作用在不同的组对上，互不冲突，不得因为"E 只改变顺序"而把时间过滤也放到截取之后。第五步，最终证据集合既是四项检索指标的计算对象，也是送入大模型的文本证据上下文；图谱路径与事件三元组计入 Context Token Budget，但不计入检索指标的 K（检索指标只统计文本块级证据）。为保证 Precision@K 的分母为 K 且可跨题比较，预实验需固定 K、N 与 Context Token Budget，并保证每个问题的候选证据数不少于 K、预算至少能容纳 K 个文本块；候选证据不足 K 的题目在测试集构建阶段调整，不进入正式实验。**该约束只适用于测试集构建阶段（v2.5 澄清其边界）**：题目一旦入库，不得因该题实验时的实际候选数少于 K 而将其排除，空缺位置记为未命中并按原指标定义计算；否则会出现"系统没搜到 K 个就把题删掉"的选择偏差，使正式测试集因系统表现差而变简单。

问答指标三项，由人工按统一标准评分，每项取值为 0、1、2。Answer Accuracy：0 = 错误，1 = 部分正确，2 = 完全正确。Completeness：0 = 关键信息大量遗漏，1 = 基本覆盖，2 = 信息完整。Faithfulness：0 = 存在明显无依据事实，1 = 少量不严谨，2 = 完全基于证据。

评分方式：由作者按上述统一标准评分，并对不少于 20% 的样本间隔 3 天以上做二次复评，报告前后评分一致率，用于检验评分稳定性（intra-rater consistency）。两次评分不一致的样本由作者重新核对证据后给出最终分，并在实验记录中保留两次评分与不一致原因。本课题以单人复评（评分稳定性）作为既定设计，不得表述为"评分者一致性"或"评分信度"——单人复评无法证明评分者间信度（inter-rater reliability）。条件增强：若能有第二名评分者，则对同样的 20% 样本独立评分，计算加权 Cohen's Kappa（线性权重，0/1/2 为序数尺度），作为评分者间信度证据；无第二名评分者时不得声称信度。评分标准在实验开始前固定，不得在看到结果之后调整。若确实需要修改评分标准，必须在修改后重新执行全部评分，并在论文中说明修改原因与重评范围。

系统指标沿用第 7 章非功能需求的口径，并补足一项：响应时间一项沿用第 7 章"在统一的测试环境下记录平均回答耗时与 P95 耗时，并分别记录向量检索、图谱查询与大模型生成的耗时"的记录方式；并发能力一项沿用第 7 章"10 个并发用户下接口成功率不低于 95%"；此外本节新增一项补充口径"连续 100 次请求的成功率不低于 95%"，用于观察非并发条件下的接口稳定性，该项**不属于**第 7 章已有条目。两项口径均以"系统不崩溃、不出现数据错乱"为前提。三组指标同时覆盖检索方法、问答质量与软件系统表现，既满足方法层面的评价，也满足软件工程专业的系统评价要求。

### 12.8 图谱增强效果的判定规则

为了避免"看到结果再决定怎么解释"，知识图谱是否提供额外检索价值按以下规则判定，且**判定按子集分别进行**：对**关系型子集**（任务类型为"关系型"的题目）、**多跳型子集**（路径深度为 1-hop 或 2-hop 的题目，即 gold_hop_depth ≥ 1）、**时序型子集**（时间约束为"有"的题目）各自独立应用同一条规则——若 KG-RAG 在该子集上的 Complete Evidence Recall@K 高于 Vector RAG，且该子集的 Answer Accuracy 不下降（持平或提升），则判定知识图谱在该类问题上提供了额外检索价值。三个子集按 12.2 节的标签定义，**允许重叠**（同一道题可以同时属于多个子集）；"互不牵连"指判定与结论各自独立、不因一个子集的结果而改变另一个子集的判定，不指三个集合互斥。可以只有一个子集满足、两个满足或三个都不满足，不得把三个子集合并成一个整体来判定，否则"知识图谱只对某类问题有效"这一可能结果会被整体判定掩盖。该判定以核心测试集的 108 题为依据，压力测试子集仅作为附加观察参与讨论，不作为本节主体判定的依据。

该规则只规定判定方式，不预设提升幅度。本课题不预设"知识图谱一定能提升多少"，也不预设"哪一类问题上必然有效"：实验可能出现三种结果，一是多个子集上同时满足判定条件，说明知识图谱在这些子集上提供了额外价值；二是只有部分子集满足判定条件，说明知识图谱的作用集中在特定类型的问题上，论文按子集分别报告；三是没有任何子集满足判定条件，说明在该数据集与配置下知识图谱没有带来可观察的额外价值，这一结果同样按 12.7 节的指标如实报告，并按第十八章的分类归因方法分析原因。三种结果都是有效的实验结论，区分点在于是否用同一套指标、同一套配置与同一套判定规则给出结论。

### 12.9 定量实验问题与开放性问题的区分

定量实验只使用可核验、有明确证据的事实型问题，即答案能够在数据集文档中找到直接依据、可以人工判定正确与否的问题。示例包括：A 公司的供应商有哪些；A 公司什么时候发生该事件；A 公司参与了哪些事件；A 公司与 B 公司是什么关系；某事件之后又发生了哪些事件。这类问题有唯一的证据集合与可核查的参考答案，适合计算 Recall@K、Precision@K、MRR、Complete Evidence Recall@K 与 Answer Accuracy，也适合作为多标签子集分组统计的对象。

开放式分析问题不进入定量实验，只用于 Demo 展示与案例分析，最多保留 1～2 例。示例包括：A 公司被处罚后对 B 公司的潜在影响；该政策对某行业的长期影响如何判断。这类问题没有唯一答案，回答质量依赖模型的分析角度与措辞，无法用 12.7 节的 0/1/2 评分稳定衡量；同时这类回答必然包含模型分析成分，容易与公开事实混淆。因此这类问题必须在页面与答案中同屏标注"模型分析（非公开事实）"，只用于答辩演示、页面展示与失败案例分析，不作为核心准确率依据，也不参与 12.8 节的判定，不计入任何指标。

答辩演示与页面展示以事实型、事件型、关系型、时序型四类可核验问题为主，每类至少 2 例；上述开放式分析问题最多保留 1～2 例，并必须按前一段的要求标注"模型分析（非公开事实）"，不计入任何指标。

区分的意义在于保证实验结论可核查：定量实验部分报告的数字都有明确证据与人工参考答案支撑，开放式部分只展示系统的表达能力与证据追溯能力，不把开放性回答的效果折算成准确率。论文中两部分分开报告，实验章节给出定量结果，案例分析章节给出开放性问题与失败案例。

## 十三、最终回答形态与证据追溯

系统输出不能只有一句结论，必须同时给出答案与可追溯证据。这里需要区分两种情形：对于使用了知识图谱检索的问题（1 跳或 2 跳扩展），答案必须同时展示对应的图谱路径；对于 0 跳问题（仅凭文本检索即可回答）以及未启用图谱扩展的实验组（Baseline 1、Baseline 2 与消融 A 组），客观上不存在图谱路径，此时页面与答案中显式标注"本次回答未使用图谱扩展"，**不得强行生成或展示虚构的图谱路径**。以供应链关联为例（该例使用了图谱扩展），最终回答形态如下：

```text
回答：

A公司于XXXX年发生监管处罚事件。

相关公开信息显示，A公司与B公司存在供应链关系。

因此，从公开信息关联角度看，B公司可能属于需要进一步关注的相关企业。

证据来源：

[1] A公司监管处罚公告
[2] A公司年度报告
[3] B公司公告

知识图谱路径：

A公司
  ↓
供应商关系
  ↓
B公司
```

其中，每条证据都需要能够定位到具体文档，展示来源类型（公告或新闻）、发布时间与文档编号，用户可以点击查看原文；图谱路径以可视化方式展示，说明答案中的关系是如何被检索到的；若本次回答未使用图谱扩展（0 跳问题或未启用图谱的实验组），该区域显示"本次回答未使用图谱扩展"，而不是留空或展示虚构路径。"因此，从公开信息关联角度看"这类表述属于模型分析，必须与前面的公开事实明确区分，不能写成由图谱关系直接推导出的因果结论。

回答页面同时固定显示"数据截至：YYYY-MM-DD"，并向用户说明"最新／最近／近期"类问题的判定基准是数据截止时间而不是系统运行当天，并一律按 event_time 判定，答案中同时注明所用的判定区间。证据列表中的每条记录都来自 answer_evidence 表，包含文档编号与文本块编号，因此可以沿着 9.1 节的映射链路一路定位到原始文章；图谱路径中的每条关系都可以回溯到 9.2.3 节定义的 9 条核心关系之一；其中除 EVIDENCED_BY 外的 8 条核心语义关系带有 source_doc_id 与 source_chunk_id，指向产生该关系的文档与文本块，confidence 表示抽取置信度；EVIDENCED_BY 不带这三项属性，其证据就是该关系指向的 Document 节点本身。

这类带证据的回答是本系统的重点展示功能，也是答辩现场演示的主要流程：输入问题、得到答案、查看证据、查看图谱关系。演示问题以事实型、事件型、关系型、时序型四类可核验问题为主（每类至少 2 例），开放式分析问题最多保留 1～2 例，并必须在页面与答案中同屏标注"模型分析（非公开事实）"。

## 十七、数据"先小后大"推进策略

数据准备阶段不要一开始就设想"做 10000 家公司、100 万条新闻"，而应该按照"先小后大"的方式推进：

| 版本 | 规模 | 目的 |
| --- | --- | --- |
| 第一版 | 10 家公司 / 100 篇文本 | 跑通数据导入、清洗、事件抽取、图谱写入、向量检索与问答的完整流程 |
| 第二版 | 50 家公司 / 500 篇文本 | 检验流程在规模增加后的稳定性与抽取质量 |
| 第三版 | 100+ 家公司 / 1000+ 篇文本 | 用于最终对比实验与消融实验 |

这样安排的意义在于控制风险：第一版就是一个完整的小闭环，即使中途出现问题，也不会导致整个项目推倒重来，而是可以退回上一版继续工作。本科毕业设计的关键是数据能够稳定跑通、流程能够重复执行，而不是数据量越大越好。因此第三版的 100+ 家公司 / 1000+ 篇文本是努力目标而不是硬性验收指标：若进度紧张，可以在保证问题覆盖完整、标注完整与实验可复现的前提下停留在第二版规模，并在论文中如实说明实际数据规模、时间范围与数据截止时间。

数据来源限定为上市公司公告、监管机构公开信息、政策文件与正规财经新闻。数据准备的基本流程为：原始数据、数据采集、去重、清洗、格式统一、分词与切分、实体与事件抽取、实体消歧、事件去重、图谱写入与保存；每条文本至少保留标题、正文、发布时间、来源、URL、涉及公司与入库时间（ingest_time）等字段；数据集版本级属性 dataset_version 与 data_cutoff_time 记录在数据集元信息中（配置文件 ＋ 数据集说明文档），不存放在文档表中。与 v1.0 相比，v2.0 的流程补充了三点。

第一，在数据准备流程中增加"实体消歧"与"事件去重"两个环节。这两个环节放在抽取之后、图谱写入之前执行，实体按 stock_code 对齐并归并名称与别名，事件按类型、参与主体、时间窗口与触发词相似度判定并合并，合并后保留全部证据文档。这两个环节的产物（待消歧列表、合并日志）一并保存，用于失败案例分析。

第二，在事件抽取阶段同步构建 Dev 与 Test 两段式人工标注评测集，消除"用测试集调 Prompt"的数据泄漏。开发集 Dev 50～100 条（建议 60 条）用于抽取规则与 Prompt 的迭代调优，每迭代一轮在 Dev 上重新计算实体、事件、关系、时间的 Precision、Recall 与 F1，用数字判断规则或提示词的调整是否有效，而不是凭单条样例的主观感受决定是否继续调整；测试集 Test 200 条独立于 Dev，在规则与 Prompt 冻结后一次性评测、只测一次，Test 结果不得反馈用于再调优，若确需修改规则必须另行划定新的 Test 并在论文中说明。两集合不得重叠，均记录文本编号，标注总量约 250～300 条，标注工作与抽取工作在同一阶段完成，避免实验阶段才发现没有金标准。

第三，数据集版本级记录 data_cutoff_time 与 dataset_version：每篇文档在入库时记录 ingest_time（入库时间），而 data_cutoff_time 是数据集版本级属性，与 dataset_version 成对记录在数据集元信息中（配置文件 ＋ 数据集说明文档），不属于任何表，也不采用"取所有文档中的最晚时间"的推导口径。界面固定显示"数据截至：YYYY-MM-DD"，该属性同时写入检索与生成环节，用于按 event_time 解释"最新／最近／近期"类问题。

第一版不引入股吧。股吧的数据噪声太大，用户观点、猜测、传闻与事实混杂在一起，会显著增加知识图谱构建的难度，也会让事件抽取的时间与主体难以确认，同时股吧内容中大量存在主观判断与情绪表达，与本文件 5.3 节"公开事实与模型分析必须区分"的要求冲突。因此在本课题中把股吧写作"后续扩展的数据源"，不作为第一版的数据来源，也不进入实验数据集。

### 20.3 答辩问题预案

以下问题需要在第 2 阶段开始同步准备，并在后续各阶段持续补充证据与数据：

- 为什么需要知识图谱？回答要点：多实体、多事件、多跳关系与时间约束问题仅靠文本相似度检索容易遗漏证据，图谱提供关系与路径。
- 为什么不用普通 RAG？回答要点：普通 RAG 作为 Baseline 2 与消融实验 A 组保留并参与对比，本课题要验证的是在其基础上图谱是否提供额外价值。
- 你的主要工作与特色是什么？回答要点：面向财经事件的事件中心化知识表示、融合实体关系与时间约束的知识图谱增强混合检索方法、面向财经事件多跳问答的证据追溯与系统化评测机制。
- 数据从哪里来？回答要点：上市公司公告、监管机构公开信息、政策文件与正规财经新闻，规模按第一版到第三版逐步扩展。
- 你的数据最近到什么时候？回答要点：系统不是实时行情数据库，data_cutoff_time 是数据集版本级属性，与 dataset_version 成对记录在数据集元信息中，界面固定显示"数据截至：YYYY-MM-DD"；"最新"取符合条件的、event_time 最大的事件（并列时全部返回），"最近"取 event_time ∈ [data_cutoff_time − 30 天, data_cutoff_time]，"近期"取 event_time ∈ [data_cutoff_time − 90 天, data_cutoff_time]，答案中注明判定区间与数据截止时间，论文中写明数据的时间范围。
- 事件怎么抽取？回答要点：先做实体识别，再做事件识别与关系抽取，最后抽取时间信息并与证据来源关联；抽取结果经过实体消歧与事件去重后写入图谱并保留置信度，抽取质量用 Dev（50～100 条，建议 60 条）调优、Test（200 条）在规则与 Prompt 冻结后一次性评测得到的实体、事件、关系、时间 Precision、Recall、F1 说明（标注总量约 250～300 条）。
- 知识图谱怎么构建？回答要点：6 类实体、8 种事件类型、9 条核心关系与六项事件核心属性，通过数据抽取、实体对齐（以 stock_code 为锚）与事件去重写入 Neo4j；除 EVIDENCED_BY 外其余 8 条核心语义关系均携带 source_doc_id、source_chunk_id 与 confidence 证据属性，事件参与主体由 PARTICIPATES_IN（Company／Person／Institution → Event）表达，政策事件与监管事件的发布／作出机构由 ISSUED_BY 表达。
- RAG 怎么实现？回答要点：文本切分与 Embedding 写入向量索引（FAISS），检索结果与图谱检索结果经过时间过滤、证据融合与排序后交给大模型生成答案。
- 如何评价系统？回答要点：检索指标、问答指标与系统指标三组指标，检索指标统一为 chunk 级主口径（Recall@K、Precision@K、MRR、Complete Evidence Recall@K），配合抽取实验、功能测试、接口测试与性能测试；评分标准实验前固定，不少于 20% 的样本间隔 3 天以上二次复评并报告前后评分一致率，即评分稳定性。
- 知识图谱有没有真正提升效果？回答要点：以 Baseline 2 与 Method 的对比结果（回答 RQ2／H1 的主要证据）以及消融实验 A 至 E 的数据作答，Baseline 1 仅作辅助观察；按 12.8 节的判定规则说明在哪些子集上满足判定条件，H3 由 C 与 D 的对比回答，E 组作为进一步优化实验单独报告。
- 如果 KG-RAG 效果不好怎么办？回答要点：按 12.7 节的指标与 12.8 节的判定规则如实报告结论，把"在什么条件下有效、在什么条件下无效"作为实验结论，失败案例按抽取错误、实体消歧错误、检索漏召回、时间判断错误、生成不忠实五类归因，并以可复现的数据与口径说明结论。
