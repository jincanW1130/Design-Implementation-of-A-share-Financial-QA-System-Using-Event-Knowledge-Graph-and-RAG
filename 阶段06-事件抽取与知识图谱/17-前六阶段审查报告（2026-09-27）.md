### 3.2 三条破坏试验

**试验 ①：改《13》的切分参数（`target_chars` 400 → 401）**

* 破坏方式：把临时根里 `_抽取缓存\v2.1_v1_2\1001.json` 的 `input_sha256` 改成 64 个 0（只在临时副本里），跑 `python 工具\验收第6阶段.py`（默认 profile，含镜像重跑）。

* 结论：**变红（退出码 1）**，且缓存命中由 709 掉到 708、**仍 0 次模型调用**——上游单点指纹一变，extract→dedup→write_graph 整链硬失败，符合"宁可硬失败，不静默重问模型"的设计意图。

**试验 ③：删掉导出物 `edges.csv` 的最后一行**

* 破坏方式：把临时根里 `图谱导出\v2.1_v1_2\edges.csv` 的最后一行（`PER-0400,PARTICIPATES_IN,EVT-0098,1076,1076000,0.7,涉及方,,`）删掉，跑 `python 工具\验收第6阶段.py`。

* 结论：**变红（退出码 1）**，定位精确到文件。这条试验同时暴露了守卫边界（见 3.3）。

### 3.3 由此暴露并补强的守卫盲区

**盲区**：破坏试验 ③ 在 `--no-replay` 下**原本不会变红**。原因是 B11 项只看"关系／事件类型的覆盖集合"，不看条数——删掉一行后它如实打印"关系 2735 条、PARTICIPATES_IN=1251"，仍判 OK；而 `--no-replay` 会跳过带镜像重跑的 J 组，于是整轮验收以 `检查项 101 项，通过 81，失败 0、退出码 0` 结束。也就是说，**默认（带镜像重跑）才会拦住它，`--no-replay` 属"静态预检"口径**——在只跑静态预检的场景（例如快速自查）里，导出物被删一行是无人发现的。

**补强**：把 B11 的同一个检查项扩展为三重交叉核对——交付物导出与**同一次 `write_graph.py` 写出**的 `graph_stats.json` 逐项对照：`counts.edges_total`、`counts.nodes_total`、逐关系 `edges_by_relation` 与逐标签 `nodes_by_label`（统计文件缺键按 0 条处理；文件读不到则由总数兜住、直接红）。**只加判定条件，不加检查项，检查项总数仍为 101**；判定集合与其它组一律未放宽（补强内容同时写进 `工具\README.md` 的对应小节）。

### 3.4 守卫有效性的结论

**守卫在本次审查中由"绿地"变成"被证明会红的地"**：三条破坏试验全部按预期变红，其中一条还暴露并修好了一个"删行不留痕"的盲区。由此得到两条可复用的结论：① **验收项存在 ≠ 验收项有效**——同一个 B11，补强前会在删行时打 OK；② **默认口径与快速口径必须写明边界**——`--no-replay` 是静态预检，不覆盖逐字节一致性，凡涉及"产物是否被改过"的放行都必须跑带镜像重跑默认口径。

#### 4.3.1 两条静默错误的细节

1. **`extract.py` 的顺序缺陷（F1）**：写盘顺序为"写 `verify.json` → 写 manifest → `append_run_history(stats)`"，于是 `build_verify_payload(...)` 在计算复现性时看到的还是**上一轮**的 `run_history.jsonl`。任何一次正常抽取（`run_extraction`）都会命中这条路径；单跑一轮会得到 `runs=1`，跑两轮时第二条是上一次——本批的实际表现就是 `runs=2` 而 `compared_runs=[2]`（只有一条），在"根本没比较"的情况下返回 `identical_across_runs=false`。这是"字段取值看似合理、含义却是假的"的典型静默错误。
2. **`isolated_nodes.count` 的字段类型（F2）**：`write_graph.py` 的 `_isolated(nodes, edges)` 返回的是节点 id 的**列表**，却直接放进了叫 `count` 的键。触发条件是任何一次导出；后果是下游若按名字取数（例如判断 `graph_stats["isolated_nodes"]["count"] == 435` 或参与算术），拿到的是 435 个 id 的列表；控制台还把整张列表打了一行 5412 字符的日志。《16》正文按 `len()` 的读法写"435 个"没错，错的是**字段名**。

#### 4.3.2 F1 的真实结论（不是原先登记的「680 vs 709」）

整改后的 `verify.json` 复现性块真实取值：

| 字段 | 整改后的真实取值 |
| --- | --- |
| `runs` | `3` |
| `documents` | `[3, 709, 709]` |
| `compared_runs` | `[2, 3]` |
| `compared_manifest_sha256` | 两个值：`e2d8efc67705…` 与 `ed5b048b336a…`（**不相等**） |
| `identical_across_runs` | `false`（如实报 false） |

**比较的是哪两次**：run 2（首跑 709 篇、749 次调用、29 篇失败）与 run 3（补齐轮 709 篇、31 次调用、失败 0）**两条同规模运行**的产物清单；两条的 `manifest_sha256` 分别覆盖"680 篇成功的 `extracted.jsonl`"与"709 篇补齐后的 `extracted.jsonl`"，所以不同。run 1（3 篇冒烟）不参与比较（`same_scope` 只保留 `documents == 709` 的记录）。**原先登记的"首跑 680 篇 vs 补齐轮 709 篇"与产物不符**——那是按"两条记录里的篇数"想当然写出来的；真实口径是"两条同规模运行的产物清单不同"。

**顺序修复真的生效的旁证**：默认 profile 的镜像重跑里，写 `verify.json` 的那一轮（`run_index = 6`）进入了自己的比较集——`compared_runs=[5, 6]`、两条清单哈希相同（均为 `ed5b048b336a…`）→ `identical_across_runs=true`。旧代码下这一轮绝对不会出现在自己的比较集里。v1.1 侧（`_全量\v2.1\verify.json`）未动。

### 6.3 环境事实与工程约束

* **FAISS 的中文路径坑（工程硬约束）**：`faiss.write_index`／`faiss.read_index` 走 C++ 的 `fopen`，在含中文的路径下会报 "could not open ... for writing"；现有实现用 `faiss.serialize_index`／`deserialize_index` 绕开，落点是 `代码\数据准备\embed.py` 第 127～155 行（`write_faiss_index`／`read_faiss_index`），序列化格式与 `write_index` 逐字节一致。**第 7 阶段加载 `faiss.index` 必须沿用这条读法**（或先复制到 ASCII 路径再 `read_index`），不得直接对中文路径调 `read_index`；若第 7 阶段自己要落盘新索引（如筛子集重建），必须复用同一封装。
* **环境实测（2026-09-27，Python 3.12.10）**：`neo4j` **未装**、7687 端口**不通**；`pymysql` **未装**；`jieba` **未装**；`faiss`、`numpy`、`torch`、`transformers` 已装。前两项决定 6.2 的第 8 条裁定；`jieba` 与 `pymysql` 的缺装留给第 8／9 阶段按需处理，不属第 7 阶段阻塞。
* **输入只读与版本不可变**（《13》第9.4节 第 1 条）：第 7 阶段只能只读数据集与图谱导出物；任何"为检索方便"的预处理产物必须落到第 7 阶段自己的目录，不得回写 v2.1。
* **六张表不变**（《10》第4.4节；《16》第9.1节）：检索命中结果只经 `chunk_id` 与 `doc_id` 落地，不新建表、不新增状态列。
