### 1.3 密钥与可重放性

- 密钥只经环境变量注入：`config.py` 只写读取方式（`config.LLM["api_key_env"]` 取值为 `LLM_API_KEY`），不写取值；本文件、导出物与全部交付物都不含密钥取值，仓库内也没有任何凭据。缓存命中时**一次模型调用都不发生**，复跑因此不需要密钥（缺席即硬失败，不降级、不编造）。
- **v1.2 复跑读数**：v1.2 的整链重放由 `python 工具\验收第6阶段.py`（默认 profile）在系统临时目录**镜像重跑**承担——把 v1.2 缓存与管线产物整份镜像过去、删掉镜像里的导出物，按 `run_all.py --profile v21_v1_2 --force` 与各环节单独执行复跑；K 组实测：`cache_hits == 709`、`fetched == 0`、模型调用 0 次，子进程环境显式摘掉 `LLM_API_KEY`（缺席即硬失败）；J 组实测 nodes.csv／edges.csv／replay.cypher 逐字节一致，graph_stats.json 排除 `generated_at`／`cache_fingerprint` 后一致。该镜像只读工作区，过程不向任何交付目录写一个字节。
- **v1.1 归档复跑读数**（数字来源：`阶段05-数据准备\数据集\_抽取缓存\v2.1\图谱管线\运行日志_复跑.txt`，2026-09-26T02:06 的那一次）：参数 `--force=True --allow-api-calls=False`；四环退出码全为 0，耗时 extract 1.200 s／disambiguate 0.259 s／dedup_events 8.369 s／write_graph 1.263 s；709 篇全部缓存命中、模型调用 0 次；产物清单 713 个文件、清单哈希 `9e6ae89eaf942b53`；输入抽取结果指纹 `4cd9bcceb40e3c75…`（709 篇）。该日志只作为 v1.1 归档的留痕，不再逐字节对应当前（v1.2）产物。
- **v1.2 抽取的运行结构（如实登记）**：709 篇在 2026-09-27 分两轮完成——首跑（13:30～16:55）成功 680 篇、**失败 29 篇**（27 篇因提示词升 v1.2 后旧缓存指纹不一致而阻断、2 篇模型返回 `bad_json`），补齐轮（16:56～17:05）重取 29 篇、失败 0。`run_history.jsonl` 因此留有三条记录（3 篇冒烟／709 篇首跑（成功 680、失败 29）／709 篇补齐轮（失败 0）；记录里的 `documents` 字段是 709，「680」是首跑逐篇成功数）。其自检 `verify.json` 的 `reproducibility` 按**整改后的真实取值**为：`runs=3`、`documents=[3,709,709]`、`compared_runs=[2,3]`、`identical_across_runs=false`——**比较的是 run 2（首跑 709 篇、749 次调用、29 篇失败）与 run 3（补齐轮 709 篇、31 次调用、失败 0）两条同规模运行的产物清单**，两轮的 `manifest_sha256` 分别覆盖「680 篇成功的 `extracted.jsonl`」与「709 篇补齐后的 `extracted.jsonl`」，所以不同；`false` 的含义是**两条同规模运行的产物清单不同**，不是同一产物的两次重放。**本文件旧版曾把该字段登记成「首跑 680 篇与补齐轮 709 篇的比较」，而那批产物里 `runs=2`、`compared_runs=[2]`（只有一个运行进入比较集，等于没有比较）——那是顺序缺陷造成的伪比较**：`extract.py` 曾在 `append_run_history()` 之前写出 `verify.json`，本轮记录进不了自己的复现性块；该缺陷已在整改第一步修复（先落 `run_history` 再算并写复现性块，比较逻辑本身未改），修后旁证见 8.7。本阶段的可重放凭据以镜像重跑（上一条）与导出物逐字节比对为准，见 3.1 与 6.5。补抽这一级有自己的复跑口径：`_抽取缓存\v2.1_v1_2\时间补抽\` 全部命中时**零模型调用**、不需要密钥与网络（见 1.7）。

## 二、Prompt 与规则设计

### 2.1 提示词结构

- 提示词＝SYSTEM_PROMPT（系统提示）＋ USER_TEMPLATE（用户模板）。**默认口径**＝v1.2 变体：USER_TEMPLATE_V1_2 ＝ v1.1 的 USER_TEMPLATE 原文 ＋ 本体定义块（`<<ONTOLOGY_DEFS>>` 在渲染时注入 8 类事件定义，内容取自 `config.ontology_definitions_text()`）；模板摘要 sha256 为 `7db7a091c357…`，逐篇写入缓存记录。**v1.1 归档口径**＝`LLM["prompt_version"]` 的 `stage6-extract-v1.1`（原文，摘要 `13b4522b7d4a17…`），用 `--profile v21`／`--profile pilot` 复现。改其中任何一个字都必须同步升版本号。
- 系统提示钉死四件事：只输出一个 JSON 对象（不输出解释、不输出 Markdown 代码块、不输出多余字段）；字段名与枚举之外一律不输出；每条实体／事件／关系都必须给出**正文逐字引用** `quote`；实体 `name` 必须是正文里连续出现的写法（正文只写简称就写简称，不补全成公司全称、不改标点）。
- 用户模板分四段：【文档元信息】（doc_id／category／source／publish_time／title）／【正文】（整篇文档正文）／【只输出下面这一个 JSON 对象，字段名照抄】（entities／events／relations 三个数组及其字段）／【规则】1～7 条。
- 枚举与上限一律以占位符从 config 注入模板（实体类型、事件类型、模型侧关系、role 取值、四个上限），脚本内不重复写字面量；这样「枚举改了而模板没改」的静默漂移在结构上不可能发生。v1.2 的附加块只注入**8 类事件定义**（`config.ontology_definitions_text()` 与 `ontology_definitions_digest()` 是唯一来源），不改 v1.1 原文的其余部分。

### 2.2 七条输出规则（逐条）

1. `entities` 只输出 5 类（Company／Person／Industry／Institution／Policy）；事件由 `events` 数组给出，不在 `entities` 里重复；EVIDENCED_BY 不由模型输出，由程序按 doc_id 生成；同一实体只输出一次。
2. `events` 按正文出现顺序编号 E1、E2…，关系里用 E1 这样的引用指事件；`event_type` 只能取冻结的 8 种。
3. `relations` 只输出 8 类，端点类型必须符合 schema；ISSUED_BY 只用于「政策」或「监管」事件、终点必须是 Institution，且同一机构既是发布／作出方又参与该事件时只写 ISSUED_BY、不再写 PARTICIPATES_IN。
4. `quote` 必须来自正文、逐字连续、长度 12～200 字；引用标题或改写过的文字会被程序判为无法定位并**整条丢弃**。
5. `event_time` 只在正文写明到「日」时填写；只写到月、或需要靠推断的，一律写 null；`valid_from`／`valid_to` 只在正文给出明确日期时填写。T3.5 的补抽（1.7）同守这道门，只是把可核对的上下文从「证据引文」扩到「有界窗口」，并**额外**给出 `event_time_basis`：年份靠 `publish_time` 锚定时记 `year_from_publish`，**绝不当成正文写出的日期**。
6. 没有把握的条目一律不输出——**宁可少抽，不可编造**。
7. 输出紧凑：事件描述限一句话，不复述提示词、不输出解释或推理过程。

### 2.3 证据定位由代码完成，不由模型给编号

- 模型只给逐字引用，代码做「折空白 ＋ 精确子串」匹配；比对键**去掉全部空白**（含全角空格），其余字符照原样。理由可查：来源 PDF 存在词内空格（doc_id 1018 的正文写作「公 司将」），若把空白折成单空格，合法引用会被误判为无法定位（`config.EVIDENCE["normalize"]`）。
- 定位顺序：在该文档的文本块序列里按 chunk_index 升序查；命中多块时取 **chunk_index 最小**的一块，并累计 `quote_match_count`。
- 引文长度门 12～200 字；标题永不作为证据（`title_is_not_evidence` 为 true）；跨块边界的引文一律拒绝。
- 抽取以**文档**为上下文、以**文本块**为证据单位：一篇文档一次调用，事件不会被块边界切断；每条事实的 `source_chunk_id` 由代码定位得到，模型不给编号。

## 四、实体消歧实现

### 4.1 三条匹配规则（《10》第4.5.4节 的落地）

- **比较键**：先归一化——去掉全部空白、剥掉最外层包裹字符（书名号、引号、括号等，`strip_outer_chars`），再比较。归一化**只作匹配键，不改抽取结果里的实体名**。
- **R1_exact_name_or_code**：书写面等于别名表里某公司的归一化全称／简称／注册全称，或等于 6 位股票代码。
- **R2_full_name_contains_short_name**：书写面包含某公司的归一化书写面，且**残余部分不含区分性标记**（控股／投资／实业／资本／集团控股 共 5 个，`distinct_entity_markers`）。残余含标记时记 `distinct_entity_marker` 并拦住、不合并——这是「母公司 ≠ 子公司」的最小代价写法。简称最短 2 字（`min_short_name_chars`）。

- **多解**：命中多个公司时记 `ambiguous_alias`（本批 0 条）。
- **匹配失败**：留在待消歧列表，策略为 `pending_confirmation_exclude_from_graph`——按《10》第4.5.4节 的原话「匹配失败进入待消歧列表，人工确认后再写入图谱」，本阶段不猜、不合并、也不写图。

## 五、事件去重实现

### 5.1 四项条件（全部满足才合并）

1. **event_type 相同**。
2. **参与主体集合相等**：PARTICIPATES_IN 的 head 集合 ∪ ISSUED_BY 的 tail 集合，按**集合判等**（不看顺序、不看重复）。
3. **时间窗 ≤ 7 天**（`time_window_days`），且**两个日期都必须可解析**——任一为空，该条件不成立（`time_window_requires_both_dates`）。
4. **触发相似度**：`event_name` 的字符二元组 Jaccard ≥ 0.5（`similarity_min`），相似度保留 3 位小数（`similarity_round`）。T3 不产出独立的 trigger 字段，故用 event_name 作触发面（`similarity_field`）。

- **连接方式**：并查集单链（`union_find_single_linkage`）——两两满足即同组，组内不要求两两互满（传递闭包）。
- **代表元**：最早 publish_time，其次 doc_id，再次 local_event_id（`representative_rule`）。
- **合并后取值**：event_time 取成员中最早的非空值；confidence 取成员最大值（保留 3 位小数）；证据为成员证据文档的**并集**（`evidence_rule`）。
- **自检**：把 doc_id 整体平移 900000 造「同文异号」夹具，四项条件应不成立；夹具只用于自检，不进导出物、不进合并日志，只写 `dedup_self_test.json`。

### 5.4 去重的边界（如实登记）

- 去重只作用于**事件**：不合并实体、不合并关系（实体的合并靠消歧，见第四章）。
- 合并是保守的：1114 条里只合并掉 14 条（1.3%）。主要原因是条件 3 要求两个日期都可解析，而 event_time 为空的 **544** 条之间**永远不合并**（宁可漏合、不可错合）；触发相似度门 0.5 也会放过表述差异较大的同一事件。T3.5 补抽把 173 条 null 事件变成有日期，可直接参与时间窗条件的候选因此变多（时间窗条件要求两个日期都可解析）：本版分档是「参与主体 94449／时间窗 384／触发相似度 54／全部满足 14」。与 v1.1 归档（时间窗 1376／全部满足 34、合并 30 组／33 条）相比，v1.2 的事件基数由 1649 降到 1114，时间窗档由 1376 对降到 384 对，合并组由 30 组降到 14 组。
- 合并组的证据是并集，**不丢证据文档**；同一合并组有多篇证据文档时，导出物会出现多条 EVIDENCED_BY（见 6.2）。
- **两套编号不得混用**：去重阶段的合并组编号是 `MEVT-xxxx`，导出物的事件编号是 `EVT-xxxx`，二者由不同环节按各自的确定性排序分配，序号**不对应**（例如 MEVT-0036 是「2026年员工持股计划证券账户开立完成」，而 EVT-0036 是「乌干达工业园及自贸区电气化项目商务合同正式生效」，两者不是同一件事）。跨文档引用事件时必须写明编号属于哪一套。

## 六、图谱写入与导出

### 9.4 第 10 阶段时间过滤组（D／E）的可测性前置条件

适用范围：任何用 C 组与 D 组对比来检验 H3（时间过滤是否带来可观察差异）的实验，包括时序型子集与 D／E 组的全部条目。**在跑对比之前必须先验证这条前置条件；不满足的题不得进入 H3 的统计。**

1. **差异在哪一步产生**：时间过滤在**候选合并与去重之前**、按 `event_time` 过滤图谱侧的事件节点与关系，作用于**候选集合的成员**——被过滤掉的图谱路径所携带的 `source_chunk_id` 不再进入候选（《02》第11.3节 的 v2.5 澄清；《10》第4.6.4节 第一步）。因此「启用／不启用时间过滤」只有在**题目的候选里含图谱侧路径、且这些路径上事件的 `event_time` 落在题目时间窗口之外**时，才会让 C 组与 D 组的证据集合不同；把过滤放到「保留到 K 个文本块」之后会让两组恒等，H3 在定义上不可检验（《工具\README.md》执行纪律 2「可测性前置检查」，第 4 阶段缺陷的成因）。

   2. 该路径上事件的 `event_time` **落在题目时间窗口之外，或为空**（按第 2 条的裁定，空值候选在 D／E 组的时间过滤中被一并剔除，因此「窗口外日期」与「空值」都能产生差集；据此入题前必须确认该题候选确实含图谱侧路径）；
   3. 两个候选集合**不相等**（打印差集与条数）。若相等，该题不得进入 H3 的统计，改题或换题，不得用「过滤前后指标没变」当结论。
   逐题的差集读数记入实验记录；只报指标、不留这一步的题，视为未验证前置条件。
5. **一句话判据**：「过滤开／关时候选集合的成员有没有变化」是 H3 的**前置条件**，不是 H3 的结论；没有这条变化，C 与 D 的对比只能得出「在该题上不可测」，不能得出「时间过滤无贡献」。
