六层逻辑架构 系统总体架构图 A 股财经信息智能问答

基于事件知识图谱与 RAG 的 A 股财经信息智能问答系统

六层逻辑架构：用户交互层 → 业务服务层 → 智能问答层 →（向量检索模块 ∥ 图谱检索模块）→ 数据知识层

内容依据：《项目执行总控文档 v2.0》第 8 章“系统总体架构”，即 8.1 六层架构图、8.2 各层职责、8.3 技术栈、8.4 明确不引入的技术；三存储分工依据第 9 章 9.1 MySQL 核心表、9.2 Neo4j 本体设计、9.3 向量索引；在线问答链路依据 11.3 一次用户提问的完整执行流程。

①用户交互层

Vue 3
Web前端 / 智能问答界面

负责与用户直接交互，提供问答输入、答案展示、证据查看、图谱可视化、数据查询与历史记录等页面；该层只负责界面与交互逻辑，不直接访问数据库与模型。

↓前端请求下发：提问、财经数据查询、图谱可视化与历史记录查看

②业务服务层

Python + FastAPI
用户管理 / 问答管理 查询管理 / 历史记录

接收前端请求、校验参数、组织业务流程并返回结果；用户的每一次提问、回答与引用证据都由该层落库。

↓进入智能问答流程：问题分析 → 检索 → 证据融合 → Prompt 构建 → 大模型生成

③智能问答层

Embedding 模型 + 大语言模型 API
问题分析→ 检索→ 证据融合→ Prompt构建→ LLM生成

系统的核心处理单元；问题分析负责判定问题类型与是否需要图谱扩展，证据融合负责把向量检索结果与图谱检索结果合并排序。

↓向量检索请求：问题向量 → FAISS
↓图谱检索请求：实体与关系 → Neo4j
↑ 检索结果汇入证据融合：候选文本块 + 图谱路径合并排序

④向量检索模块

FAISS 向量索引
FAISS

基于 FAISS 完成文本语义检索，输入是问题的向量表示，输出是候选文本块及其对应文档编号，用于提供原始文本证据。

⑤图谱检索模块

Neo4j
Neo4j

基于 Neo4j 完成实体、事件与关系的多跳查询，输出实体路径、事件属性与关联关系，用于补充文本检索难以覆盖的关系信息与时间信息。

↓读取文本块向量与索引结构
↓查询实体、事件与关系及其证据文档
文本内容与结构化知识是向量检索与图谱检索共同的数据来源

⑥数据知识层

MySQL + Neo4j + FAISS 向量索引
新闻 / 公告 / 政策 / 财经信息 事件 / 公司 / 行业 / 人物 / 时间

统一管理新闻、公告、政策等原始财经信息，以及从文本中抽取的事件、公司、行业、人物、时间等结构化知识，是向量检索与图谱检索共同的数据来源。

MySQL关系数据库

负责业务数据与文档元数据，是文本内容的唯一权威来源；用户的提问、回答与引用证据均由此留存。

Neo4j图数据库

负责实体、事件与关系，支撑多跳路径与时间查询。

FAISS向量索引

只负责文本语义相似度检索，不保存权威文本，只保存向量与索引结构；FAISS 是向量相似度检索库（向量索引库），与独立的向量数据库系统定位不同。

在线问答链路一次用户提问的完整执行流程

用户问题→ 问题分类→ 实体识别→ 判断是否需要图谱→ 向量检索 ∥ Neo4j 图谱检索→ 文本证据 + 图谱路径→ 时间过滤→ 证据排序→ Prompt 构建→ LLM→ 答案 + 来源 + 图谱路径

“∥”表示向量检索与图谱检索两条路径并行或先后执行，两者结果统一经过时间过滤与证据排序后进入 Prompt 构建，最终输出答案、来源与图谱路径。

技术栈（8.3） 前端 Vue 3 后端 Python + FastAPI 关系数据库 MySQL 图数据库 Neo4j 向量索引 FAISS 模型 Embedding 模型 + 大语言模型 API 数据处理 Python 部署 Docker
明确不引入（8.4）：不同时使用 LangChain 与 LlamaIndex，不引入多个向量数据库，也不引入多个图数据库；检索、图谱扩展、时间过滤与证据排序流程由后端代码直接实现，便于在消融实验中逐项控制变量。
