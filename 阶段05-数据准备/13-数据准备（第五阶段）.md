### 1.2 抓取节奏与访问纪律

* **请求间隔**：`config.HTTP["min_interval_seconds"] = 1.2` 秒为全局下限，每次 HTTP 请求之间至少间隔该时长；各来源另按上表的 `rate_limit_seconds`（公告 1.2／监管 1.5／政策 1.5／财经新闻 2.0）限流。公告列表接口的**翻页**请求同样走这一限流路径，不构成请求突发。
* **失败重试**：`max_retries = 3`，按 `backoff_seconds = 2.0` 指数退避；超时 `timeout_seconds = 30`。
* **浏览器标识**：统一使用 `config.HTTP["user_agent"]`；巨潮 PDF 另带 `Referer`。**不使用**无头浏览器（四类来源均已用 HTTP 接口或静态 HTML 解决）。
* **单次请求耗时实测**（来自 `raw\_fetch_log.jsonl` 携带 `doc_id` 的 100 条成功记录，`elapsed_ms`）：公告 50 次，1235～1578 ms（均值 1354）；监管公开信息 10 次，1235～1281 ms（均值 1257）；政策文件 15 次，1250～1484 ms（均值 1289）；财经新闻 25 次，1280～1547 ms（均值 1349）。即实际发出的每一次请求都耗时 1.2 秒以上，与上表的限流口径一致。
* **审计留痕**：每次运行按类别向 `raw\_fetch_log.jsonl` 追加 `ok:true` 的审计行，逐条给出"标题排除规则"与"正文长度上限过滤"的检查条数、排除条数与示例标题；**某类别零排除也照写**，作为"过滤已执行"的凭据。

### 1.3 使用范围

* 数据集**仅用于本次本科毕业设计的学术研究**，不用于任何商业用途、不对外提供批量下载、不再分发原文。
* **第三方财经新闻正文刻意不进入公开仓库**：`meta\sources.csv` 中三家站点逐条写明"仅用于学术研究，正文不进入公开仓库"。仓库内保留其标题、来源、URL 与发布时间等元数据供核验，正文本身只存在于本地数据集目录与论文附件的受限部分。
* 公告、监管公开信息与政策文件均为**依法公开的披露文件或政府文件**，其原文可公开引用；即便如此，本文件仍只引用统计量与口径，不逐篇贴正文（《12》§六 第三项格式决策）。
* 数据管线**不得引入**《02》§8.4"不引入的技术"清单中的任何一项（清单以《02》§8.4 为准，本文件不重复罗列）；密钥不入仓库、不入前端。
* 若某类来源整体不可访问，按《12》§十 守卫处理并回到本文件登记，**收窄要登记，不得静默缩减**（本轮四类来源均可访问，未发生收窄）。

## 二、采集与清洗口径

### 2.1 采集（T3，`代码\数据准备\fetch.py`）

* **产物**：`raw\{doc_id}.json`（一篇文档一个文件，**采集后不再修改**）与 `raw\_fetch_log.jsonl`（一行一次尝试）。
* **目标规模**（`config.py`）：`TARGET_DOC_COUNT_V1 = 100`；公告按公司配额 `ANNOUNCEMENT_PER_COMPANY = 5` × 10 家 = 50；财经新闻 25；政策文件 15；监管公开信息 10。
* **公告的时段分层抽取**（`ANNOUNCEMENT_STRATA_V1 = {"recent": 3, "earlier": 2}`）：每家公司先从 `BUCKET_RECENT` 取 3 篇、再从 `BUCKET_EARLIER` 取 2 篇；某一时段不足时由另一时段补足，补足情况登记到 `raw\_fetch_log.jsonl`（本轮 2 家发生回填，见 §八）。
* **编号方案**（《12》§五 硬约束 7）：`doc_id` 按类别分块显式分配，块内序号按 `(publish_time 降序, url 升序)` 排序后从 1 起——公告 1000+ ／ 财经新闻 2000+ ／ 政策文件 3000+ ／ 监管公开信息 4000+。**不依赖数据库自增**，测试集的 gold 证据按编号记录时不会漂移。
* **实测**：`raw\` 下 100 个文档文件（1001～1050、2001～2025、3001～3015、4001～4010）；`_fetch_log.jsonl` 共 131 行，其中 `ok:true` 130 行、`ok:false` 1 行，携带 `doc_id` 的成功记录 100 条，`http_status` 非 200 的 0 条。**采集捕获 100 篇**，经标题级去重后封版为 **99 篇**（见 §八）。

### 2.2 语料排除规则：整篇排除，绝不截断

三条排除规则在**候选阶段**执行（先于时段分层配额与时间铺开），因此被丢弃的候选由后续合规候选顶替，配额不会被抽空。**三条规则一律"排除整篇"，绝不截断正文**——截断等于改写证据，《10》§4.4.6 要求证据按原文展示、权威文本不被改写，故本阶段宁可整篇不收，也不产出一段被裁剪过的正文。

### 2.3 去重口径（T4a，`代码\数据准备\dedup.py`；统计见 `reports\dedup_log.jsonl`、`reports\clean_stats.json`）

三条**精确**判重键（`config.DEDUP`；第一版不做近似去重，`minhash_similarity_threshold = None`）：

1. **url 唯一**——同源同链接只入一次；
2. **title 规范化后唯一**——规范化＝去除首尾空白、去除全角空格、合并连续空白；
3. **正文 SHA-256 前 16 位唯一**——排除"同文转载、链接不同"的重复。

监管公开信息的标题按 **"原标题（当事人）"** 构造后再判重（当事人取自来源文档自身正文，**不得臆造标题**）；若仍冲突，只允许用来源文档自身已有的文号／索引号消歧。本轮 `clean_stats.json` 的 `regulator_title_disambiguation` 记录为 `applied = false`、`groups = 0`——10 篇行政处罚决定书构造后的标题互不相同，无需用索引号二次消歧。

tie-break 顺序：`earlier_publish_time > shorter_content_url/page_url > smaller_doc_id`。

### 2.4 清洗口径（T4b，`clean.py`）

* **编码与全半角**：只做**全角 ASCII 区定向归一**（`normalize_fullwidth_ascii = true`），**不做整段 NFKC**（`normalize_unicode_nfkc = false`）。原因：NFKC 会把中文全角标点 `，；：！？（）` 折成 ASCII 的 `,;:!?()`，而 `。`、`、` 属 CJK 标点不受影响，同一句话里会出现 `,` 与 `。` 混排；更关键的是折标点等于改写证据（《10》§4.4.6）。因此 `preserve_cjk_punctuation = true`，中文标点逐字保留。
* **空白规范**：`collapse_blank_lines = true` 把连续空行折叠成**单个空行**并保留段落边界 `\n\n`（这是切分边界优先级的第一选择）；`strip_control_chars = true` 去掉控制字符。**去模板行模式不含 `^\s*$`**——若把空行整行删掉，`collapse_blank_lines` 会变成空操作、`\n\n` 段落边界永远不可能命中。
* **去模板**：按行匹配删除 10 类公告页眉页脚与导航（如 `^本公司及(董事会|监事会)全体成员保证.*$`、`^证券代码[:：].*$`、`^证券简称[:：].*$`、`^公告编号[:：].*$`、`^(特此公告|特此通知)[。．.]?$`、`^扫一扫.*$`、`^分享到.*$`、`^责任编辑[:：].*$`、`^上一篇[:：].*$`、`^下一篇[:：].*$`）。
* **实测**：进入清洗 99 篇，`chars_before = 218102` → `chars_after = 215916`，净删 **2186 字符**；这 2186 字符**全部来自公告类**（112883／115069），监管公开信息、政策文件、财经新闻三类的删除量为 0（正文页天然不含公告页眉页脚）。
* **跳过原因与判定优先级**：`dedup_dropped` → `too_short`（清洗后正文 < `MIN_DOC_CHARS = 80`）→ `too_long`（> `MAX_DOC_CHARS_FOR_INCLUSION = 60000`，兜底守卫）→ `empty_company_list`（公告／财经新闻的 `company_list` 为空）。本轮 `dedup_dropped = 1`，其余三项均为 **0**（`raw_docs = 100` → `cleaned = 99` → `emitted = 99`，`skipped = 1`）。
* `url` 取 `content_url`，缺失时回退 `page_url`；本轮 `url_fallback_to_page_url_doc_ids = []`。

## 三、切分口径与参数

### 3.1 固化参数（`config.CHUNK`，本阶段固化的 TBD 之二）

单位一律为**字符数**（中文按字符计，不按词计）。以下参数**封版后不得更改**；改参数等于换数据集版本（《12》§五 硬约束 5）。

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `target_chars` | 400 | 目标长度 |
| `max_chars` | 512 | 单块上限（与 Embedding 的 `max_seq_length = 512` 对齐） |
| `min_chars` | 128 | 单块下限；整篇正文短于 `target_chars` 的文档豁免（登记在 `chunk_stats.json` 的 `min_chars_exemptions`） |
| `overlap_chars` | 50 | 重叠窗口，`50 / 400 = 12.5%` |
| `boundary_priority` | `["\n\n", "\n", "。", "！", "？", "；", "…", ".", "!", "?", ";"]` | 边界优先级：**段落 > 换行 > 句末标点 > 分号 > 省略号 > 半角句末标点**；按序试探，全部落空才硬切 |
| `strip_rules` | true | 切分前剥离行内空白与规则行 |
| `DOC_ID_STRIDE` | 1000 | `chunk_id = doc_id * 1000 + chunk_index` 的步长 |
| `MIN_DOC_CHARS` | 80 | 低于该长度的文档整篇跳过（清洗环节） |
| `MAX_CHUNKS_PER_DOC_WARN` | 120 | 单篇文本块数的**告警**阈值，只报告、不截断 |

**重叠窗口与"一个文本块只算一个证据"**：`overlap_chars(50) < min_chars(128)`，重叠区只用于衔接上下文，**不足以在相邻两个文本块里各自构成完整证据**。这直接满足《12》§五 硬约束 5 与《02》§12.7 第二步（一个文本块只算一个证据），也避免 Complete Evidence Recall@K 在定义上不可达。

**切分前的编号步长预检**：`chunk.py` 在写盘前先逐篇投影文本块数，只要有一篇超过 `DOC_ID_STRIDE`（单篇 1000 块），就点名 `doc_id`／标题／字符数／投影块数并以非零码中止——**只报告，绝不截断正文、绝不丢弃文档**。投影与实际切分共用同一实现，故投影块数即落盘块数。本轮 `over_long_documents = []`。

### 3.2 编号规则（《12》§五 硬约束 6、7、8）

* `chunk_id = doc_id * DOC_ID_STRIDE + chunk_index`（`config.chunk_id_for`）。例：`doc_id = 1001` 的第 0 块是 `1001000`、第 1 块是 `1001001`。
* 该式是**双射**：`config.split_chunk_id` 可反查出 `(doc_id, chunk_index)`；本轮 `split_chunk_id_roundtrip_ok = 707/707`，`mismatched = 0`。
* `chunk_index` 在文档内**从 0 连续递增且不重复**（对应唯一键 `uk_chunk_doc_index(doc_id, chunk_index)`）；每篇文档**至少 1 个文本块**。
* 三级映射链路 `vector_id → chunk_id → doc_id` **双向可查**：`index\vector_map.jsonl` 给出正向（vector_id → chunk_id → doc_id），`chunks.jsonl` 的 `vector_id` 给出反向（chunk_id → vector_id）。

## 四、向量化口径

### 4.1 Embedding 模型与版本（本阶段固化的 TBD 之一）

本阶段必须在向量化之前固化 Embedding 模型并写入元信息（《12》§2.3、§五 硬约束 10），原因是向量索引一旦建立，换模型就要**全量重建**，而《02》§12.4 又要求所有对比组与消融组用同一个 Embedding 模型——它不能拖到第 7 阶段。

| 项 | 取值 | 出处 |
| --- | --- | --- |
| 模型名称 | `BAAI/bge-small-zh-v1.5` | `config.EMBEDDING`；实测记录见 `index\build_meta.json` |
| 模型版本（revision） | `7999e1d3359715c523056ef9478215996d62a620` | 同上；`revision_matches_config = true`、`pinned_revision_in_cache = yes` |
| 向量维度 | 512 | `build_meta.json` 的 `dim` |
| 池化方式 | `cls` | `build_meta.json` 的 `pooling` |
| 相似度 | 余弦（向量 L2 归一化后内积等价） | `normalize_embeddings = true`、`similarity = cosine`、`metric = inner_product` |
| 最大序列长度 | 512 | 与 `CHUNK.max_chars = 512` 对齐；`chunks_over_embedding_max_seq_length = []` |
| 查询指令前缀 | 空（文档与查询同向编码） | `query_instruction = ""` |
| 运行设备／批大小 | CPU ／ 32 | `device = cpu`、`batch_size = 32` |

**选型理由**：中文检索的常用基线、CPU 可跑、维度小、索引可全量重建；模型已下载至本地 HuggingFace 缓存，**离线可加载**（`local_files_only = true`），符合"实验期间不得更换"的固定配置要求。

### 4.2 向量索引与三级映射链路

* **索引类型**：`IndexFlatIP`（归一化向量 + 内积 = 余弦相似度；第一版规模小，用**精确检索**）。构建用的 `faiss-cpu = 1.15.1`、`numpy = 2.5.1`。
* **索引文件**：`index\faiss.index`，实测 `ntotal = 707`、`dim = 512`。
* **映射文件**：`index\vector_map.jsonl`，707 行 `{"vector_id", "chunk_id", "doc_id"}`，双向可查；`vector_id = 向量索引行号`，按 `chunk_id` 升序分配，故 `vector_id` 取值域恰为 `0..706`，无缺号、无越界。
* **元信息文件**：`index\build_meta.json`（模型名与 revision、维度、条数、构建时间、索引类型、`build_time = 2026-09-25T15:46:54+08:00`、`build_seconds = 19.763`）。
* **统计口径**：《02》§9.3 要求的一致性检查（向量条数 = 文本块条数）在本阶段**只做条数一致性检查**，不做检索、不排序、不算任何指标（《12》§七 非目标 7）。实测：向量条数 = 文本块条数 = **707**，无 `vector_id` 为空的文本块，去重后 `distinct_vector_ids = 707`。
* **术语口径**：本项目一律称 FAISS 为"**向量索引**"或"**向量检索组件**"，向量索引中**不保存权威文本，只保存向量与索引结构**——权威文本在数据库的 document 表中（《10》§4.4.6 的三处存储分工）。

### 4.3 本阶段向量化的边界

本阶段向量化**只覆盖数据准备所需的三件事**：固化 Embedding 模型与版本、建立向量索引、落盘 `vector_id ↔ chunk_id ↔ doc_id` 映射。**N（向量检索候选数量）、K（Top-K）与 Context Token Budget 在本阶段保持 TBD**，由第 7 阶段做检索预实验时一并固化（《12》§2.3）；本阶段不写死任何检索参数。

* **取值规则**：`url = content_url`，缺失时回退 `page_url`（`clean.py`）。因此 `url` 只在 `content_url` 与 `page_url` **同时为空**时才为空。

### 8.2 清洗侧的跳过

**(f) 1 篇文档因标题级去重被淘汰：`doc_id = 1012`。**
`reports\dedup_log.jsonl` 的完整记录：

```json
{"rule": "title", "key": "恒瑞医药关于药品上市许可申请获受理的提示性公告", "key_kind": "normalized_title",
 "candidates": [1012, 1027], "winner": 1027, "dropped": [1012], "winner_publish_time": "2026-08-25",
 "winner_url_len": 64, "dropped_detail": [{"doc_id": 1012, "publish_time": "2026-09-10", "url_len": 64,
 "decided_by": "earlier_publish_time"}], "tie_break": "earlier_publish_time > shorter_content_url/page_url > smaller_doc_id"}
```

`reports\skipped.jsonl` 对应行：`{"doc_id": 1012, "category": "公告", "source": "巨潮资讯网", "reason": "dedup_dropped", "detail": "与 doc_id=1027 冲突（rule=title，保留方 publish_time=2026-08-25）", "rule": "title", "winner": 1027}`。

**具体情形**：恒瑞医药（`600276`）就同一事项提交了两份标题规范后完全相同的公告——`doc_id = 1012`（发布 `2026-09-10`）与 `doc_id = 1027`（发布 `2026-08-25`）。三条判重键中 `title` 命中（url 不同、正文指纹不同，故只有 `title` 判重命中），按 `earlier_publish_time` 保留发布时间较早的 `1027`，淘汰 `1012`。

**后果必须写明**：① 采集捕获 100 篇，封版数据集为 **99 篇**；② 公告类计数是 **49 而非 50**；③ 恒瑞医药的公告数是 **4 而非 5**（见 §6.3 公司清单）；④ 编号块保留 `doc_id = 1012` 的缺口（`max_seq = 50`、实际 49 篇），**不回填、不重排**。

**这一条不是可以顺手抹平的瑕疵。** 它正是《12》v1.1 修订要处理的情形之一：如果不做标题判重，数据集里会出现两篇同题公告，按题目检索时会重复计入证据；如果改了判重口径去凑 50 篇，编号与统计又会漂移。本阶段选择**如实保留 99 篇并登记**，不为了对齐"100 篇"这个整数而放宽判重。

## 九、对下游阶段的使用说明

### 9.1 给第 6 阶段（事件抽取与知识图谱）

* **消费入口**：`clean\documents.jsonl` 与 `chunks\chunks.jsonl`。二者的字段名与 `document`／`document_chunk` 表**逐字段对应**（§5），第 6 阶段写库时按同名映射即可，不需要改名、不需要推导。
* **编号是稳定的，可以直接记录 gold 证据**：`doc_id` 与 `chunk_id` 由本阶段一次性分配并固化，**不依赖数据库自增**，所以标注阶段记下的 `chunk_id` 不会因为换一次运行而漂移。证据的最小单位是**文本块**——一个文本块只算一个证据（重叠窗口 50 < 下限 128，相邻块不构成两个完整证据）。
* **本阶段不做的事，第 6 阶段才开始做**：不做实体识别与事件抽取、不做实体消歧与事件去重、不写图谱、不做标注、不建测试集（《12》§七 非目标 1～5）；本阶段只交付"干净且可被消费"的语料。
* **Dev／Test 候选文本池可以分层抽样**：74 篇的 `company_list` 非空（公告 49 + 财经新闻 25，按公司分层）、25 篇为空数组（政策文件 15 + 监管公开信息 10，可作独立层）；同时可按 `category`（4 层）、`source`（6 层）、两个时间桶（`recent` 50 ／ `earlier` 49）交叉分层，使 Dev 与 Test 不重叠有可操作的划分依据。注意公司—文档关联数 79 > 文档数 74，分层时按文档抽样、不按关联抽样，否则多公司文档会被重复抽到。
* **语料对本体的覆盖性：已按《12》§三 补做实测，结论是"部分类型证据不足"，不是"8 类全覆盖"**。第 6 阶段规划标注与评测题量时请按 §9.1.1 的实测分布分配，**不要把 8 种事件类型与 9 条核心关系当作证据等量**。

### 9.1.1 语料对本体的覆盖性实测（补做《12》§三 的检查项）

**公司间关系边的实测**：`SUPPLIES`、`CUSTOMER_OF`、`COMPETES_WITH` 成立的前提是同篇出现两家以上公司。实测全库**只有 2 篇**文档同时出现 2 家以上目标公司（`doc_id` 为 2021 与 2023），而这两篇分别是券商专访与"A 股千亿元市值公司超 200 家"的市场统计稿，**都不是公司间业务关系的陈述**。`company_list` 长度分布为：长度为 0 的 25 篇、长度为 1 的 72 篇、长度为 2 的 1 篇、长度为 5 的 1 篇。

**对第 6 阶段的三条结论**：

* 本语料能支撑的链路是"公司参与事件、事件由机构发布"，以及"公司拥有高管"；**三条公司间关系（供应、客户、竞争）在本语料中没有可用证据**。《02》§12.9 的示范题型"A 公司的供应商有哪些""A 公司与 B 公司是什么关系"在 v1.0 上无法建立 gold 证据。
* "重大合同"事件类型无证据；"产品"只有单一公司为主。
* 这是 **v1.0 的覆盖性事实，不是数据缺陷**：v1.0 的交付判据是"自包含、可重复生成、可被第 6 阶段直接消费"（《12》§一），不是"8 类证据均衡"。若第 6 阶段需要均衡覆盖，应回到《02》§17 的规模推进策略扩样，而不是在本版内就地调整。

**另有一处下游必须注意的口径**：财经新闻的 `company_list` 采用"正文提及即关联"的规则（见 §5.1），因此**一篇行业稿可能被标上多家公司**（如 `doc_id` 为 2023 的那篇标了 5 家）。实测 25 篇财经新闻中约有 12 篇，被标记公司在正文中出现不足 3 次且不在标题中，其中数篇的主题其实是**另一家公司**（例：`doc_id` 为 2009 的那篇标记比亚迪，正文主角是山东朗进科技；`doc_id` 为 2021 的那篇标记宁德时代与中芯国际，正文主角是招商证券）。**第 6 阶段建"参与"边时不得直接采信 `company_list`，必须回正文判定。**
* **抽取时直接可用的元数据**：`publish_time`（归属 Document 节点一侧）与 `source`／`url`／`title`。`ingest_time` 只用于统计与一致性检查，**不作为相对时间的判定依据**（《10》§4.4.5）；`event_time`、`valid_from`、`valid_to` 三种时间由第 6 阶段产生。

### 9.2 给第 7 阶段（向量检索）

* **直接可用的资产**：`index\faiss.index`（`IndexFlatIP`，707 条，512 维，已 L2 归一化）、`index\vector_map.jsonl`（`vector_id → chunk_id → doc_id`）、`index\build_meta.json`（模型与 revision、条数、构建时间）。**三级映射链路双向可查**，由向量反查文本块只经一次映射查询。
* **Embedding 已固化，不得更换**：所有对比组与消融组必须共用同一个 Embedding 模型（《02》§12.4）。**换 Embedding 等于全量重建索引**，并且必须新建 `dataset_version` 目录而不是就地重写 v1.0。
* **N、K、Context Token Budget 本阶段保持 TBD**，由第 7 阶段在检索预实验里与三者一起固化（《12》§2.3）。本阶段没有写死任何检索参数，也没有做任何检索、排序或指标计算（《12》§七 非目标 7）。
* **候选规模的下限约束**：`document_chunk` 共 707 块、单篇最多 33 块，构建期的候选数不少于 K 这一约束在数据侧是成立的；但**单个问题的 gold 证据是否会天然超过 K 个文本块**，需要第 7 阶段用手工挑的典型问题试算，本阶段不代替该实验。
* **`token_count` 已按同一 Embedding 模型的 tokenizer 统计**（不含特殊标记），可直接用于上下文预算裁剪的估算；取值 90～497，均值 314.96。

### 9.3 给第 10 阶段（测试集与实验）

* **相对时间题目的两个桶都有内容**：`recent`（`[cutoff − 30 天, cutoff]`）50 篇、`earlier`（窗口剩余部分）49 篇，两桶都远高于 5 篇下限；`[cutoff − 90 天, cutoff]` 内共 86 篇。**"时间约束＝有"的题目在数据侧有可用的 gold 证据**，且完整的 `[cutoff − 90, cutoff]` 落在数据集内部而不是骑在边界上（窗口下界取 cutoff − 100 天，见 §6.2）。
* **`data_cutoff_time` 是版本级属性，出题与判定都以它为准**：`2026-09-25`。相对时间表述（最新／最近／近期）按《02》§10.3 以 `event_time` 判定，不与 `publish_time` 混用（《10》§4.4.5）；`dataset_version` 与 `data_cutoff_time` 作为一对写入 Prompt 构建环节。
* **必须绕开的数据空洞**：**财经新闻类别在 2026 年 9 月 0 篇**（§8.1c），最晚一篇停在 `2026-08-28`。因此凡"用新闻来源 + 时间落在 2026 年 9 月"的题目在数据集里**没有 gold 证据**，出题时应避开，或改用公告／政策文件／监管公开信息三个类别（这三类 9 月分别有 18／8／3 篇）。
* **公告在 9 月共 18 篇、8 月共 19 篇**，是 recent 桶的主体；`earlier` 桶由公告 12 篇、财经新闻 25 篇、政策文件 7 篇、监管公开信息 7 篇构成。抽题分层时按这些实际分布设计，不要按"理想均匀分布"假设。
* **恒瑞医药的公告只有 4 篇**（§8.2f），若题目按"每家 5 篇公告"均摊证据，该公司会短一篇。
* **原始文本与索引作为论文附件打包**，不逐篇贴进论文正文（《12》§六 第三项格式决策）。

### 9.4 各阶段通用纪律

1. **版本目录封版不可变**：`数据集\v1.0\` 不得就地修改；扩充规模新建 `v1.1`／`v2.0` 目录并变更 `dataset_version`（§6.5）。
2. **六张表恒为六张**：本阶段只产出 `document` 与 `document_chunk` 的内容，`user` 表保持为空，不新增表、不新增字段；`content_sha256_16` 等数据集内部字段**不入库**（§5）。
3. **不引入《02》§8.4 的技术**：清单以《02》§8.4 为准，本文件不重复罗列；FAISS 一律表述为"**向量索引**"或"**向量检索组件**"（《12》§五 硬约束 11）。
4. **大语言模型仍是 TBD**：本阶段与数据集内**没有任何大语言模型型号**被写死；型号在第 8 阶段选定后固化（§6.4）。
5. **密钥不入仓库、不入前端**（《12》§五 硬约束 10）。
6. **不越界**：数据集的边界由本文件与 `meta\dataset.json` 界定；下游若要修改数据（删文档、删文本块），必须遵守《10》§4.4.2 的历史证据保护规则——**已被回答引用的文档与文本块禁止物理删除**，只允许使其"不可再用于新检索"。
