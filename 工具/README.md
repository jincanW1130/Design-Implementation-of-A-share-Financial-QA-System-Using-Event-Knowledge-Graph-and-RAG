# 工具

本目录存放项目自用的脚本，不属于交付物，也不参与文档编号。

| 脚本 | 用途 |
| --- | --- |
| `跨文档核验.py` | 对工作区全部 Markdown 做 14 项一致性核验（A～N），**每次产出新文档后都要重跑** |
| `验收第4阶段文档.py` | 《10》的专项验收：逐条对应《09》§七 的验收标准与 §四 的 13 条硬约束 |
| `验收第5阶段数据.py` | 《13》与数据集 v1.0 的专项验收：逐条对应《12》§八 的 19 行验收标准（共 99 项，含真实重跑时 103 项；S 组是索引集中度守卫） |
| `拼装第四阶段文档.py` | 把 `阶段04-系统总体设计\_分节源文件\` 的 7 个分节源文件拼装为交付文档 `阶段04-系统总体设计\10-系统总体设计（第四阶段）.md` |

## `跨文档核验.py`

对工作区里的 Markdown 文档做一遍机器可复现的一致性核验。**每次产出新文档后都应重跑**，尤其是第 4 阶段及以后每次新增 `NN-` 文档时。

运行：

```powershell
python 工具\跨文档核验.py
```

不带参数时，工作区取本脚本所在目录的上一级；也可以传入其它路径：

```powershell
python 工具\跨文档核验.py "C:\Users\15129\Desktop\毕业设计"
```

退出码 `0` 表示全部通过，`1` 表示存在失败项（明细在输出里）。

### 参与核验的文档范围

根目录的 `*.md` ＋ 每个 `阶段NN-…\` 目录**一层**内的 `*.md`。**不参与核验**的两类：`阶段04-系统总体设计\_分节源文件\` 内的分节稿（它们是《10》的输入，不是独立文档）与 `阶段02-…\_归档_…\` 内的归档过程文件。分节稿不参与核验，因此改完分节稿必须重跑拼装脚本，否则交付文档与源文件会不一致。

### 检查项

| 编号 | 检查内容 |
| --- | --- |
| A | 文档规模（行数按文本行计，不含文件末尾换行产生的空行；KB＝字节÷1024），并检查文件名互不重名 |
| B | 表格列数一致性（跳过 ```` ``` ```` 代码块），统计表格块总数 |
| C | 跨文档节号引用可解析性：每个 `《0N》§x.y` 是否真的存在于被引文档中（含中文序号章节） |
| D | 《07》§1.3 来源清单覆盖：正文引用的节是否都在表中，**按文档分别归属节号** |
| E | 需求追溯矩阵的来源是否都被对应条目的"来源追溯"覆盖 |
| F | §3.8 功能需求汇总表 与 §7.2 追溯矩阵 的 FR 来源是否逐字一致 |
| G | 需求编号覆盖（FR-01～06／UC-01～07／NFR-01～06） |
| H | 作废术语残留（裸 `Evidence Recall`，排除修订留痕） |
| I | 未限定范围的证据属性表述（"每条关系…source_doc_id"一类，须带"除 EVIDENCED_BY 外"） |
| J | 边界禁用词出现在"引入／使用"语境（仅报告，需人工确认语境） |
| K | 文档内以反引号提到的 `.md/.py/.html/.csv/.docx/.pdf/.png/.svg` 路径是否存在（含阶段目录、归档目录与旧路径别名） |
| L | 工作区内的 `0N-` 文档是否都登记在《00-项目总览与索引》中 |
| M | 目录结构：五个阶段目录齐全、`_分节源文件\` 存在、根目录只留《00》与《02》、每份带号文档都在阶段目录里、`10-` 同名目录与旧 `文献调研\` 目录已消除 |
| N1 | 《02》的版本号在**标题末尾**、文档信息表的**版本字段**与 §1.2 **修订记录末行**三处是否一致（**门禁项**；2026-09-25 新增：v2.4／v2.5 两次登记只改了 §1.2、没有回改表头，版本号漂移了两个版本而无人发现） |
| N2 | **引用方版本审计**：只审计**依据声明行**（含"依据／上游／需求来源"），且版本号须紧跟在《02…》之后、中间不再出现其他《》引用；被引版本非当前版本时，同一行必须带版本链说明，否则计为过期引用。记录类文件（`05-`／`06-`／`08-`／`11-`）按留痕排除。**默认只报告**（`[WARN]`），加 `--strict-citations` 转为门禁 |

## `验收第4阶段文档.py`

`跨文档核验.py` 查全工作区的通用一致性，本脚本查 **《10》自身**是否满足《09》写下的验收标准。两者分工不重叠，每次改完《10》都要两个都跑。

运行：

```powershell
python 工具\验收第4阶段文档.py
```

三组检查：一、《09》§七 的验收标准（7 个小节标题与《02》§15 第四章逐字一致、六层名称与顺序、六个模块名称与顺序、6／8／9 口径、六张表、Method＝C 与 Baseline 2＝A、Top-K 四句契约逐字、FR／UC／NFR 落点）；二、《09》§四 的 13 条硬约束；三、图与表编号连续性与**文档头声明的图表数量与实测一致**（第三组是为了防止拼装脚本里的陈述与正文脱节——`10-` 曾出现"表 4-12 共 12 张"与实际 13 张不符）。

## `验收第5阶段数据.py`

`跨文档核验.py` 查全工作区的通用一致性；本脚本查**第 5 阶段的数据侧交付**是否满足《12》§八 写下的验收标准，即《13-数据准备（第五阶段）.md》与数据集 v1.0 本身。两者分工不重叠，第 5 阶段的收口结论以两个脚本的退出码均为 0 为准。

运行：

```powershell
python 工具\验收第5阶段数据.py
python 工具\验收第5阶段数据.py --with-idempotence    # 另在临时目录真实重跑 T4a→T5
python 工具\验收第5阶段数据.py --dataset <数据集目录> --doc <《13》路径>
```

共 19 组、99 项检查（`--with-idempotence` 时 103 项；脚本里 "检查项合计（A～S）" 一行是 97 的中间计数，另有 2 项在收尾阶段计入，**以末行 "最终：检查项" 为准**）：文档结构、《13》必备小节、目录自包含、`meta\dataset.json` 逐项重算比对、必需字段、三个判重键、监管标题构造规则、`company_list` 口径、公司集合、编号公式、块长与重叠、向量条数、时间口径、类目与来源、幂等、越界排除、禁用术语、《00》登记，**以及 S 组的索引集中度守卫**（单篇 ≤ 25%、前 5 篇合计 ≤ 60%、同一标题不得跨公司复用）。**凡是能从数据集文件重算的数值一律重算后比对**，不拿 `reports\consistency_report.json` 当独立证据（个别处读报告比对的，输出里明确标注）。

S 组的两条阈值是**本工具的守卫阈值**，刻意不读 `代码\数据准备\config.py`：一篇文档吃掉索引是**数据集缺陷**，必须让验收失败；而合理的块长均值／最大值属于数据集参数，归 config。这一条是本文件里"参数一律取自 config"的**唯一例外**，写在这里以免下次被当成疏漏。

## `拼装第四阶段文档.py`

```powershell
python 工具\拼装第四阶段文档.py
```

读 `阶段04-系统总体设计\_分节源文件\` 的 7 个分节源文件，加文档头（元信息表、导言 §0.1～§0.3）与交付说明附录，写出 `阶段04-系统总体设计\10-系统总体设计（第四阶段）.md`。**《10》要改内容时改分节源文件再重跑本脚本，不要直接改交付文档**，否则下一次拼装会覆盖。

## 编写约定（改脚本时请遵守）

1. **检查项必须输出证据**（文件名加行号），不能只给结论——否则无法回溯。
2. **按文档分别归属节号**：`《02》§8.4` 与 `《04》§8.4` 是两个不同的节，不能放进同一个集合比较。第 3 阶段曾因混用集合而漏报一处未覆盖引用。
3. **修订留痕要排除**：`《02》` 的版本记录行与 `《05》`《06》 的"原为…"表述中会出现已作废的旧写法，那是留痕，不是缺陷。脚本据此把 **`05-`／`06-`／`08-` 三个记录类文件整体排除**在 `H`、`I` 两项之外——它们会逐字引用旧写法，不能当缺陷报。
4. `J` 与 `K` 是启发式检查，允许出现需要用人工判断的行，但**不允许静默跳过**——不确定就打印出来。
5. **计划产出要登记**：任务书一类文档会提到"将要创建"的文件（例如曾经登记过的 `13-数据准备（第五阶段）.md` 与 `验收第5阶段数据.py`），它在检查时必然还不存在。这类文件名写在脚本顶部的 `PLANNED` 集合里；**文件一旦创建就把它从 `PLANNED` 删掉**，否则会掩盖真正的悬空路径。当前 `PLANNED` 为**空集**——第 5 阶段的两个计划产出均已落盘。
6. **查路径要知道数据集的存在**：第 5 阶段起文档会按**数据集内的相对路径**写文件（`meta\sources.csv`、`reports\consistency_report.md` 等）。`K` 项的 `SEARCH` 因此追加了 `阶段05-数据准备\数据集\<版本>\` 与 `_试跑\`；带省略号的 token（如正则片段 `cs.com.cn/….html`）由 `WHITE` 排除，因为它描述的是模式而不是具体文件。
7. **不要在自己写的文档里逐字引用被 `I` 项禁止的那类句式**，哪怕是"未出现……"这种否定式引用：`I` 的判据是"含『每条关系』＋含证据属性字段名＋不含『除 EVIDENCED_BY 外』"，不区分引用与断言。第 4 阶段的交付说明里原有一张自检表逐字列出了该句式，因此被误报，最终把自检表从交付文档移到交付回复里。
8. **表格单元格里不要出现未转义的竖线**：`跨文档核验.py` 的表格列数检查按朴素切分计数，写成正则片段（如 `内部控制(评价|自我评价|审计)报告`）即使转义成 `\|` 也会被计成多列。第 5 阶段的《13》因此把完整模式集移到表格下方的代码块里，单元格只留文字说明。
9. **改《02》的版本号要改三处，并回头查引用方**：标题末尾、文档信息表的 `| 版本 |` 字段、§1.2 修订记录新增一行——三处必须同时改，`N1` 项会核对。此外**引用《02》的文档**若声明了所依据的版本，该声明由 `N2` 审计：升了基线就要么同步引用方、要么在其依据行补版本链说明。这是 2026-09-25 补上的守卫：此前 v2.4／v2.5 只改了 §1.2，标题与版本字段停在 v2.3，漂移了两个版本都没被任何检查发现；而 v2.6 升版当天又立刻让《09》《10》《12》的依据行过期——**这类问题靠人记是守不住的**。
10. **分段正则要能匹配到真正的结尾**：检查 `D`／`E`／`F` 依赖 `### 1\.3 需求来源清单` 的分段，原写法要求以 `\n---\n` 结尾，而《07》§1.3 之后是 `## 二、` 标题、没有分隔线，**这三项曾长期静默跳过并报 OK**。现已改为 `(?:\n---\n|\n## )`。改动类似的"取段落"正则后，务必先确认段落真的非空再判定通过。
11. **移走或改名的文件由别名表兜底，不要回改历史记录**。2026-09-25 工作区按阶段重组后，`K` 项里有两张表：`LEGACY` 把旧目录前缀映射到新位置，`RENAMED` 把旧文件名映射到新文件名。记录类文档（《05》《06》《08》）里逐字保留着重组前的路径与文件名，那是历史留痕，**判据是"按别名能找到"而不是"把历史记录改成现在的样子"**。新增一次迁移时，先在这两张表里登记，再补《00》4.9 的对照行。

## 执行纪律（跨阶段通用，源自 2026-09-25 的历史复盘）

对照《05》（四轮评审）、《08》（两轮复核）、《11》（两轮复审）与第 5 阶段的实现记录，项目至今约 **110 项修正**可以归成八类。其中"同一口径多处不同步"约占四分之一，是最伤效率的一类，而且**机械可查**。下面七条是能固化成动作的部分，其余由本目录的脚本守住。

1. **改口径必须回归**（对应"修订本身引入新错误"，历史上栽过两次）。改任何一条冻结口径后必须做三件事：① 用关键字在**全部**文档里搜一遍它的旧写法，不许凭记忆；② 跑本目录的三套脚本；③ 在修订记录里写明"这条口径还被谁依赖"。教训：《08》§四第 1 项为消除"六类／五项"不一致把计数改成"五类"，回原文核实后**真值是六类，改错了**；第 5 阶段为补窗口空洞引入分时段铺开，反而让最早一篇漂到 cutoff 前 86 天、违反了硬约束 13。

2. **可测性前置检查**（对应"设计了机制，却没验证它真能产生差异"）。任何进入实验设计的机制或开关，必须写出"打开与关闭时，**在哪一步**产生可观察差异"；写不出的不许进设计。教训：时间过滤被排在 K 截取之后、又写"不改变证据集合成员"，使 C 组与 D 组恒等，**H3 在定义上无法检验**——这是第 4 阶段最实质的缺陷；第 5 阶段又在数据侧犯了同构的错（时间窗中间整月为空，时序型题目没有 gold 证据）。

3. **数据集质量不只看条数**（对应"一篇文档吃掉整个索引"）。条数达标不等于数据集可用：第 5 阶段一度出现一篇 39.7 万字符的报告占全库 51.7% 的字符、单篇 1135 个文本块，会让 Recall@K／Precision@K 失去区分度。现由 `验收第5阶段数据.py` 的 `S` 组守卫（单篇 ≤ 25%、前 5 篇合计 ≤ 60%、跨公司同名标题）。

4. **篇幅预算前置**（对应"先写后压"）。动笔前先定图／表／行数上限，不要写完再压。教训：《10》一度写到 12 张图、55 张表，经两轮复审才压到 8 图 13 表，且最后仍留 1 张超出原定上限、需专门写裁决理由。

5. **开工先侦察**（对应"能力假设没有先验证"）。进入新阶段前，先把**环境能力 ＋ 外部依赖可达性 ＋ 数据源取数方式**验一遍再定方案。教训：第 5 阶段的四类数据源里三类是 JS 空壳（需另找 JSON 接口）、巨潮接口每页只回 30 条、FAISS 在中文路径下**必然失败**（须用 `serialize_index` 绕开）——这三条都直接影响架构选择，且都是先探查才发现的。

6. **脚本报错不等于文档有错**（对应"检查器也会误报"。与"编写约定 4"同源，但用在读结果时）。核验脚本本身是代码。判定前必须回原文。教训：《08》§三 D5 的核验器报"矩阵来源越界 2 处"，回原文后确认 1 处是误报；`N2` 初版把同一行里不相干的版本号也算成《02》的版本，报出 19 处、实际只有 4 处——**守卫自己也要被校准，噪声大的守卫会被忽略**。

7. **"已完成"必须独立复现**（对应"自测在自己的夹具上做，夹具与实现可能同错"）。接受任何完成结论前，验收方要另走一条路径复现，不得采信自测报告。教训：第 5 阶段有执行者自报"幂等比对通过"，其中 `count 1` 其实是它脚本自身的 bug；FAISS 中文路径那条结论也是经独立复现才采信的。
